# YouPlanner

PWA-трекер привычек: таблица недели и карточки дня, каза-намазы с очередью,
времена молитв по координатам, счётчик уразы, цикл сна, статистика,
ИИ-ассистент с чтением PDF.
Работает офлайн, синхронизируется через Firebase Realtime Database (REST).

## Стек

- Чистые ES-модули (ES2020), без сборки и сторонних библиотек.
  Единственная вендорная зависимость — pdf.js 4.10.38 (Apache-2.0),
  локальные копии в `js/vendor/`, офлайн через прекэш SW.
- Service Worker: HTML/JS/CSS — network-first с кэшем на офлайн,
  Firebase не кэшируется, vendor-файлы pdf.js — в прекэше ASSETS.
- Тесты — стандартная библиотека Node (`node --test`), песочница `node:vm`
  и настоящее исполнение модульного графа; браузерные прогоны — Playwright
  (постоянные наборы `tests/e2e/`: chaos, user-crash, assistant-features).

## Структура

```
index.html          # разметка + 16 стилей + единственный <script type="module">
styles/             # CSS по секциям исходного монолита (порядок = каскад)
js/
├── app.js          # точка входа: главный экран, таблица, привычки, статистика,
│                   # init/bindEvents, проводка шины событий
├── core/           # bus (события), dates, dom, storage, db (IndexedDB)
├── data/           # домены: habits, records, qaza, prayer, fast, sleep,
│                   # stats, schedule, backup, migrations, ui (константы),
│                   # background (сжатие фото фона + настройки)
├── sync/           # state (syncPending/saveNormalized), validators,
│                   # sync (Firebase: сверки, PUT, бэкапы, single-flight)
├── ui/             # state (appState, ui, isMobileView), вьюхи assistant/
│                   # prayer/fast/sleep/qaza/schedule, main-table, stats
└── vendor/         # pdf.js 4.10.38: pdf.min.mjs + pdf.worker.min.mjs
tests/              # 60 наборов *.test.mjs: smoke (граф, id, импорты), bus,
                    # backup, sync (CAS If-Match/412), merge, planner-узел,
                    # tombstones, матрица (8 наборов), router, dates/dom,
                    # xss, timers, assistant, sw-assets/sw-offline, csp…
                    # tests/e2e/ — chaos, user-crash, assistant-features,
                    # firebase-rules
sw.js               # service worker (версия кэша растёт с каждым релизом)
```

Слои общаются через шину событий (`js/core/bus.js`): правка данных —
`data:changed`, применённый снимок сервера — `sync:applied`, замена бэкапом —
`data:replaced`, изменение очереди каза — `qaza:changed`, отказ хранилища —
`storage:error`. Прямых вызовов между слоями нет, граф импортов
однонаправленный и проверяется тестами.

Ассистент (§11ad спецификации): чат с api.neuraldeep.ru, ключ и модель —
только на устройстве (в синхронизацию и копии не входят), история последних
50 реплик, системный промпт со снимком трекера, прикрепление PDF
к каждому запросу, офлайн-разбор через локальный pdf.js. Длинные PDF
(больше 50 000 символов) не обрезаются, а нарезаются на фрагменты по абзацам
(до 200 000 символов чтения): в запрос уходят только фрагменты, отобранные
по ключевым словам вопроса, — нужное место видно в документе любой толщины.

Фон приложения (§11ae): фото с устройства сжимается под экран (Canvas,
≤ 800 КБ) и хранится Blob'ом в IndexedDB; фиксированные слои фото
и белого скрима включаются классом `body.has-app-bg`, затемнение —
ползунок с авто-подбором по яркости фото. Локальная настройка
устройства — в синхронизацию и копии не входит.

## Зависимости

- **Runtime:** внешних библиотек нет; единственная вендорная — pdf.js 4.10.38
  в `js/vendor/` (офлайн через прекэш SW). Сборки нет: ES-модули грузятся
  браузером напрямую.
- **Тесты:** Node.js (стандартный `node --test`), devDependency
  `playwright ^1.64.1` для chaos-E2E. `npm test` браузер не запускает.
- **Локальный просмотр:** любой статический сервер, например
  `python -m http.server 8000`; Service Worker работает только по http(s).
- **Деплой:** GitHub Pages, ветка `main`; PWA обновляется после закрытия
  и повторного открытия иконки.

## Запуск

- Локально: `python -m http.server 8000` (или `npx serve .`) и открыть
  `http://localhost:8000`. Service Worker работает только по http(s).
- Деплой — GitHub Pages, PWA устанавливается на iPhone («На экран Домой»).
  При изменении списка файлов поднимайте версию `CACHE` в `sw.js`.

## Ключевые правила проекта

- `safeSetItem` защищает от `QuotaExceededError`; все `save*` возвращают
  `boolean`, обработчики обязаны проверять и не перерисовывать UI при `false`.
- `loadRecords` кэшируется; прямые `localStorage.setItem` по этому ключу
  обязаны вызывать `invalidateRecordsCache()`.
- Снимок с сервера валидируется `validCloud*` — битый не затирает локальные
  данные; бэкапы лежат в соседнем узле Firebase (PUT данных их не трогает).
- Корневой PUT — условная запись (CAS): If-Match по ETag последней сверки;
  412 — серверный снимок изменился: перечитать, слить, повторить.
  Контрольный GET перед PUT убран — гонку двух устройств закрывает сервер,
  а не второй запрос клиента.
- Бэкап-снимок троттлится: не чаще раза за `BACKUP_MIN_INTERVAL_MS`
  (5 минут, js/sync/core.js), в пропущенные обмены уходит null.
- Общие хелперы живут в core, не в копиях: `pluralDays` (js/core/dates.js),
  `midnightArcMinutes` (js/data/records.js), `timeoutGuard` (js/core/dom.js;
  предел свой у слоя: синхронизация 20 с, auth 30 с, ассистент 60 с).
- `BACKUP_VERSION = 11`; импорт старых копий отвергается.
- Обновление ассетов — вместе с бампом версии кэша в `sw.js`.

## Безопасность Firebase

Аутентификация через REST identitytoolkit — без Firebase SDK (сторонних
библиотек в проекте нет). Два режима (`js/data/firebase-auth.js`):

* **анонимный** (по умолчанию): новое устройство делает `accounts:signUp`,
  знакомое — обмен refresh-токена; uid у анонимного аккаунта свой на каждое
  устройство;
* **аккаунт владельца**: `accounts:signInWithPassword` одного постоянного
  аккаунта на всех устройствах. Пароль не хранится нигде, кроме времени
  самого запроса; в localStorage живут refresh-токен (`youplanner.fb.refresh`)
  и запись `{email, uid}` (`youplanner.fb.owner`). Пока эта запись есть,
  анонимный signUp запрещён: он дал бы токен с чужим uid, правила ответили бы
  403, а синхронизация пропала бы без причины.

Токен прикладывает единственная обёртка `fetchWithTimeout`
(`js/sync/sync.js`): каждый запрос синхронизации уходит с параметром `?auth=`.
Refresh-токен и запись владельца — локальная механика устройства, как api_key
ассистента: в синхронизацию, копии и экспорт не входят.

Деградация намеренная: любая неудача аутентификации (нет ключа, нет входа,
офлайн, отказ сервера, битый ответ) даёт null — приложение продолжает работать
на локальных данных. После неудачи пауза 5 минут, чтобы офлайн не платил
сетевой попыткой на каждый обмен. Отказ по правам (401/403) от сетевой ошибки
отличается: `fetchWithTimeout` ставит `deniedStatus` и эмитит `sync:denied`,
Настройки показывают код и советуют войти, а не «нет связи».

### Правила: пин по `auth.uid`

`database.rules.json` — публичный шаблон с заглушкой `OWNER_UID`. Живой uid в
открытом репозитории не живёт, поэтому правила собираются скриптом в
gitignore-ный `database.rules.local.json`:

```
node _tools/set-owner-uid.mjs --uid <UID>     # собрать файл
node _tools/set-owner-uid.mjs --check         # сверить: один uid во всех 4 разрешениях
```

Где взять UID: Firebase Console → Authentication → Users → колонка UID, либо
в Настройках YouPlanner сразу после входа (он показан там нарочно).

Порядок раскатки — строгий, потому что правила по uid отсекают устройства,
которые ещё живут анонимно:

1. Firebase Console → Authentication → Sign-in method → Anonymous включён ✅,
   Web API Key вписан ✅ (оба — 2026-10-31).
2. Console → Authentication → Users → **Add user**: email + пароль (режим
   Password). Это и есть «аккаунт владельца».
3. Собрать правила: `node _tools/set-owner-uid.mjs --uid <UID>` →
   `node _tools/set-owner-uid.mjs --check`.
4. **Сначала войти, потом публиковать.** На каждом устройстве: Настройки →
   Аккаунт владельца → email/пароль → Войти. Пока все устройства не вошли,
   публикация правил выключает синхронизацию (приложение продолжит работать
   локально и покажет код отказа).
5. Publish правил — **отдельно для обоих инстансов**: узел данных
   `youplanner-d8aaea12-…` и соседний `youplanner-d8aaea12-…-backups`.
   Публикация — руками в Console (Realtime Database → Rules); в сеть из
   кода этого репозитория правила не выкладываются.
6. Проверка живьём: `node tests/e2e/firebase-rules.e2e.mjs` (чистый node, без
   playwright; скрипт пишет только служебный `__rules_probe` и тут же удаляет).
   Ожидание: PUT без auth — 401/403, PUT с анонимным токеном — 401/403,
   PUT с токеном владельца — 200, uid аккаунта = uid в правилах.
7. Откат, если что-то пошло не так: в Console вернуть предыдущую версию правил
   (Rules → история версий) либо `auth != null` — база снова открыта любой
   сессии проекта, данные при этом не теряются.

Закрепление по uid — сужение области поражения, а не «защита от всех»: узел
данных лежит в клиентском бандле, а настоящий контроль владельца (custom-токен
с claim) требует сервера, которого в этом проекте нет.
