Трекер привычек: недельный планировщик, вкладка каза-намазов,
вкладка «Молитвы», раздел «Расписание», PWA для iPhone,

## 2a. Ключевые решения проекта

- Правки — в `index.html`, `styles/` и `js/`; сборки нет, модули — источник
  правды, Service Worker кэширует их по списку `ASSETS`.
- Палитра iOS-blue `#0062CC`.
- Синхронизация: Firebase Realtime Database, REST без SDK.
- Хранение: `localStorage` + зеркало на сервере.
- Три уровня защиты данных: пустое не затирает непустое, не прошедший
  `validCloud*` проверку раздел из облака не применяется (§10), тесты на `/test`,
  автобэкап в отдельном корне Firebase `FIREBASE_BACKUPS_URL`. Старый вложенный
  путь `youplanner-a7x9k2/backups` не используется: основной `PUT` заменяет
  синхронизируемый узел целиком и стёр бы его дочерние копии.
- Навигация: таб-бар из четырёх вкладок (Главное / Каза / Расписание / Настройки)
  на телефоне, кнопки «Расписание» и «Настройки» в шапке на ПК.
- Режим «Главное» на мобильном: День / Неделя.

## 2b. Решения по вкладке Задачи

*Снято 2026-10-14. Раздел „Задачи“ заменён на „Расписание“ (§11ac). Решения ниже — история, не действуют.*

Зафиксированы с автором задачи до написания кода (2026-09-28, §11j — журнал).

| Вопрос | Решение |
|--------|---------|
| Приоритет | Выводится из времени при создании: со временем → `high`, без → `low`. Ручной выбор (высокий/низкий) — вторым меню из кнопки формы (этап Б, §11k — журнал). |
| Точки в календаре | Красная — есть невыполненная `high`; зелёная — только `low`; синяя — все выполнены; нет задач — точки нет. |
| Иконка вкладки | SVG-календарь с числом «17» (фиксированное, личное пожелание). |
| Лимит на день | 10 невыполненных. Больше — кнопка «+» неактивна, как и на прошедшем дне; снятие отметки при десяти также не возвращает задачу в работу. |
| Порядок задач в дне | Невыполненные → `high` (time ASC, затем createdAt) → `low` (time ASC, затем createdAt) → выполненные. |
| Форма | На телефоне — bottom sheet снизу; на ПК — центрированное окошко. Открывается на создание («Новая задача») и на правку по тапу на текст («Редактировать»). |
| Действия формы | «Сохранить» и «Удалить» живут в меню «⋯» в шапке формы (доработка этапа Б, §11l — журнал). В самой форме они не дублируются: строки действий под полями нет. |
| Дата в форме | Своя шторка-пикер в стиле Apple Reminders (чипы быстрого выбора + календарь + строка срока с колесом времени + Очистить). Работает и при создании, и при правке: задача переносится между днями. У выполненной задачи перенос снимает `done` по подтверждению. Перенос на день с 10 невыполненными блокируется. В прошлое задача не встаёт: прошедший день вкладки гасит «＋», прошедшая дата в пикере сохранением не принимается (2026-09-29, §11.4в). |
| Ручной приоритет | Меню из кнопки формы. Выбранное значение сильнее вывода из времени и хранится в поле `manualPriority`. |

## 5. Схема данных

### `youplanner.qaza` — новый ключ

```js
{
  version: 3,
  cursor: 3,
  remaining: { fajr: 305, zuhr: 306, asr: 306, maghrib: 305, isha: 305 },
  history: []   // только за сегодня: [{ namaz: 'fajr', date: '2026-09-13', source: 'done' }]
}
```

- `version` — версия схемы. Версия 1 ставила стартовый курсор на Фаджр; версия 2
  задаёт его вручную (см. §6.5); версия 3 добавила в запись истории поле `source`.
- `history[].source` — `'done'` (обычное выполнение) либо `'manual'` (ручное добавление
  пропуска, §6.6). Записи версий 1–2 поля не имеют и при загрузке считаются `'done'`.
- `cursor` — целое 0…4, индекс текущего намаза в `NAMAZ_ORDER`. Задаётся пользователем
  в блоке «Откуда продолжаем?», а не угадывается при инициализации.
- `remaining` — остаток по каждому намазу, целое ≥ 0.
- `history` — стек записей за сегодня в порядке появления. Нужен только для отмены: обычные
  выполнения и ручные добавления лежат в одном стеке, поэтому «Отменить последнее» снимает
  верхнюю запись любого типа (см. §6.6). При загрузке записи не за сегодня отбрасываются,
  поэтому стек не растёт бесконечно.

### Начальные данные

При первом запуске (ключа нет) записывается:

```js
remaining: { fajr: 305, zuhr: 306, asr: 306, maghrib: 305, isha: 305 }  // сумма 1527
cursor: 3   // Магриб
history: []
```

Обоснование: всего 1530, поровну по 306. Сегодня уже выполнены Фаджр, Магриб и Иша —
отсюда 305 у них и 306 у Зухра и Асра. Курсор — на **Магрибе**: это точка, откуда
очередь продолжается, поэтому план на сегодня равен `Магриб → Иша → Фаджр`.
Ставить курсор на Фаджр нельзя — Фаджр уже выполнен.

### Связь с `youplanner.records`

Растущий журнал по датам у каза теперь **есть** — `youplanner.qaza.log` (§5,
ниже), но он заводится не с начала времён, а с `since`, и нужен статистике.
Основным источником о том, сколько каза сделано в конкретный день, остаётся
существующее поле `h6` в `youplanner.records` — до `since` статистика читает
только его, а `qazaStreak` и прогресс-круги не смотрят в журнал никогда:

```js
{ "2026-09-13": { "h6": 1 } }
```

Следствия:

- `calcProgress` и рендер прогресс-круга **не меняются** — `h6` остаётся привычкой типа
  `number` с `goal: 3`, и круг недели/месяца считается существующим кодом.
- Рассинхрон невозможен, потому что ячейка `h6` перестаёт быть редактируемой
  (см. §8): вкладка — единственный, кто пишет это значение.
- В счётчик входят только записи `source: 'done'`. Ручное добавление пропуска
  (`source: 'manual'`, §6.6) остаток увеличивает, а счётчик дня — нет: намаз не выполнен,
  а вспомнен, и прогресс-круг за это не начисляется.
- `h6` продолжает писаться и после заведения журнала: так же, как писался до него.
  Журнал — второй свидетель того же события, а не замена: границу между источниками
  задаёт `since`, и только статистика каза её видит (§11y).

### `youplanner.schedule` — расписание дня (§11ac)

Ключ `youplanner.schedule`. Пока человек не редактировал расписание, ключа в
хранилище нет и `loadSchedule()` подставляет `DEFAULT_SCHEDULE`. Структура:

```js
{
  weekday: [{ time: '04:30', text: 'Подъём' }],
  weekend: [{ time: '04:30', text: 'Подъём' }],
  fasting: [{ time: '04:30', text: 'Подъём, сухур' }],
  physical: [{ time: '04:30', text: 'Подъём (по возможности)' }]
}
```

Каждое из четырёх полей — массив объектов `{ time, text }`: время и текст строки.
Значения примеров показывают форму данных, не полный список дня. Хранится в
`youplanner.schedule`. Формат: `{ weekday: [...], weekend: [...], fasting: [...],
physical: [...] }`. Каждый пункт: `{ time: 'HH:MM', text: 'Название' }`. При
отсутствии ключа `loadSchedule()` возвращает копию `DEFAULT_SCHEDULE`.
Синхронизируется через Firebase и включается в бэкапы (BACKUP_VERSION 11).

### `youplanner.prayer` — координаты, мазхаб и метод (2026-09-30, §11q)

```js
{ lat: 43.38639, lng: 45.82889, madhhab: 'shafi', method: 'dum-chr' }
```

- `lat`, `lng` — числа, широта −90…90 и долгота −180…180. Без координат времена
  намазов не считаются, и вкладка показывает приветственный экран.
- `madhhab` — `'shafi'` (тень ×1, по умолчанию) или `'hanafi'` (тень ×2).
  Влияет только на время Асра.
- `method` — `'dum-chr'` (по умолчанию) или `'astro'`. Влияет только на Зухр:
  у ДУМ ЧР он закреплён на 12:30, у астрономического берётся истинный полдень.
  Ключ без этого поля — состояние до этой задачи: читается как `'dum-chr'`.
- Ключа нет — это и есть «первый запуск». Битое значение (не объект, не числа,
  координаты вне диапазона, мазхаб или метод вне списка) читается как отсутствие
  ключа, а не роняет расчёт: `loadPrayer()` возвращает `null`, а мазхаб и метод
  вне списка приводятся к `'shafi'` и `'dum-chr'`.
- Запись — только через `savePrayer()`, он же ставит отложенную отправку.

Три точки обмена и копии; задачи из них сняты 2026-10-14:

- **`syncToCloud`** — `prayer: loadPrayer() || {}` в теле `PUT`.
- **`applyCloudData`** — пятый раздел рядом с `habits` / `records` / `qaza` /
  остальных действующих разделов. Условие то же: объект и
  `hasData(data.prayer) || !hasData(local.prayer)`.
  Пустой `prayer` с сервера не затирает заданные координаты.
- **`buildBackup` / `parseBackup` / `applyBackup`** — пятый раздел файла.
  Тогда `BACKUP_VERSION = 3`; версия 4 добавлена уровнями выполнения (§11r),
  версия 5 — разделом `fast` (§11x). При импорте необязателен.

### `youplanner.qaza.fast` — счётчик каза-постов (2026-10-05, §11x)

```js
{
  version: 1,
  remaining: 15,                                       // целое ≥ 0
  history: [
    { date: '2026-10-05', count: 15, source: 'set' },  // первый запуск
    { date: '2026-10-06', count: 1,  source: 'done' }, // «Возместить 1 день»
    { date: '2026-10-07', count: 3,  source: 'add' }   // «Добавить уразу»
  ]
}
```

- `version` — 1.
- `remaining` — целое ≥ 0. **Ноль здесь значимое значение**, а не пустое:
  `remaining: 0` — это существующий счётчик, и экран у него обычный.
- `history` — **растущий массив событий**, а не стек: он не чистится по датам
  и не откатывается. Это единственное назначение поля — **задел под будущий
  раздел «Статистика»**; интерфейс уразы историю не читает, только пишет.
  Размер ограничен архивацией (js/data/archive.js): детально хранится
  последний год (12 календарных месяцев), более старые события уходят
  в месячные своды `youplanner.archive`. Записи не отбрасываются по датам,
  в отличие от `history` каза (§5).
- `history[].source` — `'set'` (первый запуск и «Изменить счётчик»),
  `'done'` («Возместить 1 день»), `'add'` («Добавить уразу»).
- `history[].count` — сколько записано этим событием: у `'done'` всегда 1,
  у `'set'` и `'add'` — введённое число.
- `history[].date` — календарный день `'YYYY-MM-DD'` (`toISODate(new Date())`),
  **без правила дня каза до Фаджра**: возмещение поста — запись о действии,
  а не намаз, привязанный к границе дня очереди (§5, §11x).

**Признак первого запуска — только отсутствие ключа.** `loadFast()` возвращает
`null`, если ключа нет, JSON битый, значение не объект, `remaining` не конечное
число или отрицательное, `history` не массив; `history` с битыми элементами —
объект с очищенным массивом. Значение `0` первым запуском
не считается. Дефолта у раздела нет: начальное число задаёт человек, и только
через форму первого запуска. В отличие от `loadQaza()`, `loadFast()` при чтении
ничего не пишет.

**`validFastHistory(history)`** — чистка истории, новый помощник захода 3
статистики (§11y). Возвращает пустой массив, если на входе не массив; иначе
оставляет только элементы-объекты, у которых `date` — строка вида
`YYYY-MM-DD` (`/^\d{4}-\d{2}-\d{2}$/`), `count` — конечное число `≥ 0`,
а `source` — одно из `'set'` / `'done'` / `'add'`. Битые элементы
отбрасываются молча, порядок валидных сохраняется. Применяется ровно в трёх
точках, и ни в одной из них битая запись раздел не роняет:

- **`loadFast`** — `history` возвращается очищенной. Пустой после чистки
  массив — всё равно объект, а не `null`: счётчик важнее истории, и одна
  испорченная строка не должна превращать его в незаведённый.
- **`applyCloudData`** (ветка `fast`) — раздел применяется, а история из
  снимка чистится перед записью. Условие применения то же, что было.
- **`parseBackup`** — после проверок «`fast` объект, `remaining` число,
  `history` массив» история заменяется очищенной. Отказ разбора — как был:
  битая запись внутри валидного раздела копию не отклоняет.

Три точки, как у каза и молитв (задачи сняты):

- **`syncToCloud`** — `fast: loadFast() || null` в теле `PUT`. Ноль счётчиком
  быть не перестаёт: объект с `remaining: 0` остаётся объектом и уезжает как
  есть, `null` уходит только когда ключа нет вовсе.
- **`applyCloudData`** — шестой раздел рядом с `habits` / `records` / `qaza` /
  `prayer`. Условие общее: объект и `hasData(data.fast) ||
  !hasData(local.fast)`. Проверка `hasData` на объекте уразы даёт `true`
  и с нулевым остатком: ключей в нём три. Поэтому ноль с сервера применяется,
  а не принимается за пустой раздел, — иначе возмещённые дни вернулись бы.
  `null` (или отсутствие раздела) с сервера счётчик на устройстве не затирает:
  это уровень защиты 1 (§2a). История из снимка перед записью чистится
  `validFastHistory`, но раздел из-за неё не отклоняется (§11y).
- **`buildBackup` / `parseBackup` / `applyBackup`** — шестой раздел файла, тогда
  `BACKUP_VERSION = 5`. Раздел **необязателен**: отсутствие — текущий счётчик
  сохраняется. Записывается он только при заведённом счётчике — устройство
  без него раздела не пишет вовсе, а не пишет `null`: правило разбора
  «`fast` не объект — отказ» отвергло бы собственную копию. Если раздел есть,
  но `fast` не объект, `remaining` не число или `history` не массив — импорт
  отклоняется целиком, текущий счётчик остаётся нетронутым. Очищенная
  `validFastHistory` история — не отказ: битая запись внутри раздела просто
  не доходит до хранилища (§11y).

### `youplanner.qaza.log` — растущий журнал выполнений каза (2026-10-07)

```js
{
  version: 1,
  since: '2026-10-07',
  entries: [
    { date: '2026-10-07', namaz: 'maghrib', source: 'done' },
    { date: '2026-10-07', namaz: 'asr',     source: 'manual' }
  ]
}
```

- `version` — 1.
- `since` — дата первой записи, `'YYYY-MM-DD'`. До неё статистика каза читает
  `h6`, с неё и позже — журнал (§11y). Меняется один раз: при заведении.
- `entries` — **растущий массив событий**, а не стек: он не чистится по датам
  и не обрезается, в отличие от `history` самого каза (§5, §6.4). Ограничения
  размера нет: три записи в день — около 60 КБ в год, что приемлемо.
- `entries[].source` — `'done'` (обычное выполнение, §6.3) либо `'manual'`
  (ручное добавление пропуска, §6.6).
- `entries[].date` — день каза `'YYYY-MM-DD'` (`kazaDayFor`): до Фаджра это ещё
  вчерашний день, и это тот же ключ, под которым выполнение записано в `h6`.
  Поля `count` у записи нет — одна запись, один намаз.

**Признак отсутствия журнала — только отсутствие ключа.** `loadQazaLog()`
возвращает `null`, если ключа нет, JSON битый, значение не объект, `since`
не дата `'YYYY-MM-DD'` или `entries` не массив; `entries` с битыми элементами —
объект с очищенным массивом. Как `loadFast()`, при чтении ничего не пишет:
пустое хранилище здесь значит «журнала ещё нет», а не «пора завести».

**`validQazaLogDate(value)`** — дата журнала: строка под
`/^\d{4}-\d{2}-\d{2}$/`. **`validQazaLogEntries(entries)`** — чистка записей,
правило то же, что у истории уразы (§5, `validFastHistory`): элемент годится,
если это объект с датой `'YYYY-MM-DD'`, известным намазом из `NAMAZ_ORDER`
и известным источником; битые отбрасываются молча, порядок валидных
сохраняется. Применяется в трёх точках, и ни в одной из них битая запись
раздел не роняет: `loadQazaLog`, `applyCloudData` (ветка `qazaLog`)
и `parseBackup`.

**Точки записи.** Журнал пишут два действия очереди: `markQazaDone` (§6.3)
и `addMissedQaza` (§6.6) — по записи на каждое, с источником `'done'`
и `'manual'` соответственно. Первый вызов заводит журнал: `since` равен дате
этой записи, поэтому за дни до неё статистика остаётся на `h6`.

**Отдельной отмены у журнала нет.** `undoQazaDone` (§6.4) снимает последнюю
подходящую запись — это **отступление от исходного плана захода** (пометка
и причина в §6.4).

Дальше три точки, как у каза и молитв (задачи сняты):

- **`syncToCloud`** — `qazaLog: loadQazaLog() || null` в теле `PUT`. Журнала
  нет — уходит `null`. Пустой журнал (`entries: []`) счётчиком быть не
  перестаёт: ключей в нём три, объект остаётся объектом и уезжает как есть.
- **`applyCloudData`** — седьмой раздел рядом с `habits` / `records` / `qaza` /
  `prayer` / `fast`. Условие общее: объект, `since` — дата и
  `hasData(data.qazaLog) || !hasData(local.qazaLog)`. Пустой журнал с сервера
  применяется и затирает локальный — ноль здесь значим, как `remaining: 0`
  у уразы: иначе возмещённые дни вернулись бы. `null` (или отсутствие раздела)
  журнал на устройстве не затирает: это уровень защиты 1 (§2a). Битый `since`
  раздел не пропускает — записанный, он читался бы как «журнала нет», и
  история пропала бы вовсе. Записи из снимка чистятся, раздел из-за них
  не отклоняется.
- **`buildBackup` / `parseBackup` / `applyBackup`** — седьмой раздел файла,
  тогда `BACKUP_VERSION = 6` (§11.2). Раздел **необязателен**: записывается
  только при заведённом журнале, а не пишется `null` — правило разбора
  «`qazaLog` не объект — отказ» отвергло бы собственную копию. Файл без
  раздела текущий журнал сохраняет: импорт старых копий его не стирает.

### `youplanner.sleep` — режим сна (2026-10-08, §11ab)

```js
{
  version: 4,
  bed: '23:30',     // 'HH:MM'
  fall: 20,         // целое 0…120
  wake: '07:00',    // 'HH:MM'
  actualWake: '07:00', // время, которое идёт в историю
  sleepMin: 430,    // минут от засыпания до actualWake
  realWake: null,   // 'HH:MM' или null; null — «встал по плану», факт равен actualWake
  realSleepMin: null, // целое 0…1439 или null; парное к realWake
  excluded: false,  // boolean; true — день исключён из статистики
  history: [        // растущий массив, запись на день
    { date: '2026-10-07', bed: '23:00', fall: 15,
      wake: '06:30', actualWake: '06:30', sleepMin: 435,
      realWake: null, realSleepMin: null, excluded: false }
  ]
}
```

- `bed` — время отхода, `'HH:MM'` в 24-часовом виде. Другого формата здесь
  быть не может: поле на экране — `type="time"`, браузер отдаёт ровно такой.
- `fall` — сколько минут человек засыпал, целое 0…120. **Ноль здесь значимое
  значение**, а не пустое: «лёг и сразу заснул» — обычный случай. Потолок
  задан смыслом поля: больше двух часов — это уже не засыпание.
- `wake` — желаемое время подъёма, `'HH:MM'`.
- Поля `bed`, `fall` и `wake` — три опоры расчёта, и все три обязательны:
  без любого из них запись неполна, и расчёт не строится (§11ab).
- `actualWake` и `sleepMin` — время, которое уходит в историю, и длительность
  сна. Пара появилась в версии 2 (§11ab). Снятая галочка «встану
  по рекомендации» даёт цель, отмеченная — ближайший конец цикла.
- **Галочка — отметка устройства, а не данных.** Отдельного поля у неё нет:
  в ключе `youplanner.sleep` она не лежит и на сервер не уходит. При открытии
  экрана галочка восстанавливается сравнением `actualWake !== wake`: «встаю
  по рекомендации» — это ровно случай, когда времена разошлись. Совпадение
  (будильник встал точно на конец цикла) читается как «галочки не было»,
  но разницы там нет — оба режима дают одно и то же время (§11ab). До версии 2
  поля `actualWake` в записи не было вовсе, и его роль играло само поле `wake`:
  версия 1 читается как «встаю по цели».
- `history` — **растущий массив записей по дням, как у уразы** (§5) и журнала
  каза (§5), а не стек: он не чистится по датам и растёт без предела.
  Запись одна на день и перезаписывается при сохранении формы; день ищется
  проходом по полю `date`, отдельного ключа с датой нет. Поля записи — те же,
  что у ключа, плюс `date`: запись объекта `{ date, bed, fall, wake,
  actualWake, sleepMin }`, например `{ date: '2026-10-07', bed: '23:00',
  fall: 15, wake: '06:30', actualWake: '06:30', sleepMin: 435 }` (§11ab).
- `date` — день сохранения формы, `'YYYY-MM-DD'` по локальным компонентам
  (`toISODate`): раздел заполняют перед сном, и другой даты у записи нет.
  Заполнение после полуночи уходит на следующие сутки — принято сознательно.
- История появилась в версии 3. **Запись версий 1–2 истории не знает, и это
  её возраст, а не порча:** читается она как читалась, а `history`
  подставляется пустым массивом. Вида «истории нет, потому что её ещё
  не завели» и «истории нет, потому что стёрли» не различаются — как
  у счётчика уразы, где пустой раздел значит «не заведено».

**Признак первого запуска — только отсутствие ключа.** `loadSleep()`
возвращает `null`, если ключа нет, JSON битый, значение не объект (в том
числе массив), `bed` или `wake` не время суток, `fall` не целое 0…120,
пара `actualWake`/`sleepMin` есть, но битая. История в это число не входит:
она **чистится при чтении**, а не отклоняет запись, — как история уразы
(§5, §11y). Битый элемент отбрасывается, если это не объект, `date`
не `'YYYY-MM-DD'`, `bed` или `wake` не время суток, `fall` не целое 0…120,
`actualWake` не время суток либо `sleepMin` не целое 0…1439 или не сходится
с `sleepDurationMinutes(bed, fall, actualWake)`. Сходимость проверяется
не для порядка: битая пара роняет запись и при чтении ключа, и в истории
ей не место. История не массивом — теряется только она: три опоры расчёта
важнее дневника, как счётчик уразы важнее её истории.
Времени суток мало соответствовать форме «две цифры : две цифры»: `'25:00'`
и `'99:99'` под неё подходят, но временем не являются, поэтому проверка идёт
через `sleepTimeMinutes()`, единственный разбор времени в разделе (§11ab).
Дефолта у раздела нет: начальные значения задаёт человек, и только полями
экрана. Как `loadFast()` и `loadQazaLog()`, `loadSleep()` при чтении ничего
не пишет: незаполненный раздел и есть отсутствие ключа.

**`saveSleep(sleep)` пишет только полный набор, а историю ведёт сам.**
Проверки ядра те же, что при чтении: неполная или битая запись не пишется
вовсе, а не подменяется дефолтом, — иначе поле на экране разошлось бы
с хранилищем. Прежняя история берётся **из хранилища**, а не из аргумента:
вызывающему о ней знать нечего, а передача её снаружи означала бы, что любой
вызов без неё стирает дневник. Читается она тем же `loadSleep()`: в дневник
копится только то, что прошло проверку. Дата записи — день сохранения формы.
Отложенная отправка ставится здесь же: запись входит в снимок узла и в файл
копии восьмым разделом.

Три точки, как у каза, молитв, уразы и журнала (задачи сняты):

- **`syncToCloud`** — `sleep: loadSleep() || null` в теле `PUT`. Пустого
  объекта здесь быть не может: `loadSleep()` возвращает либо полную запись,
  либо `null`. Записи нет — наверх уходит `null`.
- **`applyCloudData`** — восьмой раздел рядом с `habits` / `records` /
  `qaza` / `prayer` / `fast` / `qazaLog`. Условие общее: объект,
  не массив и `hasData(data.sleep) || !hasData(local.sleep)`. `null` (или
  отсутствие раздела) с сервера запись на устройстве не затирает: это
  уровень защиты 1 (§2a). История едет вместе с разделом, а не отдельно
  от него.
- **`buildBackup` / `parseBackup` / `applyBackup`** — восьмой раздел файла,
  тогда `BACKUP_VERSION = 8` (§11.2). Раздел **необязателен** и записывается
  только при заведённой записи — устройство без неё раздела не пишет вовсе,
  а не пишет `null`: правило разбора «`sleep` не объект — отказ» отвергло бы
  собственную копию. Если раздел есть, но `sleep` не объект, `bed` или `wake`
  не время суток либо `fall` не целое 0…120 — импорт отклоняется целиком,
  текущая запись остаётся нетронутой. Время в файле проверяется тем же
  `sleepTimeMinutes()`: своя регулярка вида «две цифры : две цифры» пропускала
  бы `'25:00'`, файл разбирался бы, а следующий `loadSleep()` возвращал `null`,
  и заведённая запись пропадала бы (§11ab).
- **История в файле** необязательна, как и у уразы: файл версии 7 её не знает
  и разбирается как разбирался. История есть, но не массив — отказ целиком:
  запись легла бы в ключ, а следующий `loadSleep()` отбросил бы историю,
  и она бы молча пропала. Битые элементы внутри массива разбор, наоборот,
  не роняют — их отбрасывает `validSleepHistory` (§11ab).

### Уровни выполнения у Корана и Спорта (§11r, 2026-10-01)

Две привычки — Коран (`h8`) и Спорт (`h7`) — получают необязательное время
и два уровня выполнения. Новых ключей localStorage не заводится: `time` едет
в разделе `habits`, `level` — в `records`.

```js
{ id: 'h8', name: 'Коран', type: 'number', unit: 'стр.', goal: 5, time: '10:30' }
{ "2026-10-01": { "h8": { value: 4, level: 'on-time' } } }
```

- `time` — `'HH:MM'` или `null`. Поля нет вовсе у остальных привычек.
- `level` — `'on-time' | 'late' | 'two-min' | null`.
- У **всех** остальных привычек запись остаётся скаляром, как была: объектную
  запись получают только привычки с уровнями.
- Коды Спорта: `'yes' | 'no' | 'two-min' | 'rest'`. Старые значения читаются
  на лету, без перезаписи в localStorage: `'да' → 'yes'`, `'нет' → 'no'`,
  `'частично' → 'two-min'` (уровень `'two-min'`), `'отдых' → 'rest'`.
- `BACKUP_VERSION` поднят с 3 до 4, с §11x — до 5. Старые файлы читаются как раньше.
- С §11s привычек с уровнями три: к Корану и Спорту добавился Пресс (`h12`) —
  те же четыре кода Спорта и своё время. Разбор — §11s.

Подробности — §11r.

### `youplanner.habits` — список привычек

```js
[{ id: 'h7', name: 'Спорт', type: 'choice', unit: '', goal: null, time: null }]
```

- Ключа нет, строка пустая, JSON битый или это не массив — `loadHabits`
  отдаёт `[]` и **ничего не пишет**. Отсутствие ключа и пустой список здесь
  одно и то же состояние: «привычек нет».
- `DEFAULT_HABITS` в хранилище из `loadHabits` не пишутся. Их засевает
  `settleHabitsAfterSync` после первой сверки и только при подтверждённо
  пустом сервере (§11t, §13).
- Ключ `time` есть только у привычек с уровнями (`h7`, `h8`, `h12`),
  `addHabit` ставит его сразу и пустым (§11s).

### Прочие ключи localStorage

- `youplanner.sync.ts` — метка времени последней синхронизации (Unix ms).
- `youplanner.mainView` — `'day' | 'week'`, режим вкладки «Главное» на мобильном.
- `youplanner.stats.period` — период раздела «Статистика» (§11y): объект
  с пятью полями — `hub`, `qaza`, `habits`, `fast`, `sleep`.
  Каждое поле —
  `'week' | 'month' | 'year' | 'all'`. **Отметка устройства**, как
  `youplanner.mainView`: в синхронизацию и в файл резервной копии не входит,
  новых разделов в Firebase и в файле копии не появляется. Ключа нет или
  значение поля вне списка — «Месяц» для этого поля. Строка из списка — след
  прежней версии, где период был один: читается как значение всех пяти полей,
  а объект кладётся в ключ при первой правке периода.
- `youplanner.migrations` — какие разовые правки устройство уже прошло (§11s):
  `{ "press": true, "drop-tasks": true }`. В синхронизацию и в файл копии не входит — это отметка
  устройства, а не данные человека.

### 6.2 План на сегодня

Вычисляется на лету, нигде не сохраняется.

```js
// До 3 индексов: идём по кругу от cursor, пропуская remaining === 0.
function getQazaPlan(qaza)
```

- Начинается всегда с `cursor`.
- Если ненулевых остатков меньше трёх — возвращается столько, сколько есть.
- Если все остатки нулевые — возвращается пустой массив.

Пример: `cursor = 0`, остатки `305/306/306/305/305` → план `[Фаджр, Зухр, Аср]`.
Пример с пропуском: `cursor = 0`, `remaining.zuhr = 0` → план `[Фаджр, Аср, Магриб]`.

### 6.3 «Выполнено»

Доступно **только у первого пункта плана**, то есть у намаза под курсором. Благодаря этому
очередь не может быть перепрыгнута и список не «перескакивает» под рукой.

Порядок действий:

1. Если `remaining[cursor] === 0` — ничего не делать (защита от двойного клика).
2. `remaining[cursor] -= 1`.
3. `history.push({ namaz: NAMAZ_ORDER[cursor], date: сегодня })`.
4. `appendQazaLog(NAMAZ_ORDER[cursor], сегодня, 'done')` — запись в растущий
   журнал выполнений (§5). Порядок шагов не меняет, но добавляет вторую запись
   о том же событии: стек — для отмены, журнал — для статистики.
5. `setRecord(сегодня, 'h6', history.length)` — счётчик каза за сегодня.
6. `cursor = nextQazaIndex(qaza, cursor)`.
7. `saveQaza(qaza)`, перерисовать вкладку и ячейку `h6` в таблице.

### 6.4 «Отменить»

Откатывает **последнюю запись сегодня** — любого типа, потому что обычные выполнения
и ручные добавления лежат в одном стеке. Если сегодня записей не было — кнопка неактивна.

1. Если `history` пуст или последняя запись не за сегодня — ничего не делать.
2. `const last = history.pop()`.
3. Снятая со стека запись снимается и с журнала: `dropLastQazaLog(last.namaz,
   last.date, last.source)` — снимает последнюю подходящую запись журнала (§5).
   Делается это в обеих ветках, до действия по остатку.
4. Если `last.source === 'manual'` — `remaining[last.namaz] -= 1` (добавление его
   увеличивало). Курсор и `h6` ручная запись не трогала, значит и откат не трогает.
5. Иначе (`'done'`) — `remaining[last.namaz] += 1`, `cursor = NAMAZ_ORDER.indexOf(last.namaz)`,
   `setRecord(сегодня, 'h6', qazaDoneCount(qaza, сегодня))`. При нуле записывается `0`,
   а не удаление: в проекте `0` — значимое значение и входит в базу прогресса.
6. Курсор не должен указывать на намаз с остатком 0 — при необходимости сдвигается
   через `nextQazaIndex`.
7. `saveQaza(qaza)`, перерисовать.

Отмена возможна многократно, пока в стеке есть сегодняшние записи. Верхняя запись
определяет тип отката: снять ручное добавление и снять выполнение — разные операции.

**Отступление от исходного плана захода.** Изначально `undoQazaDone` не должен был
трогать журнал, но без снятия журнал расходится со стеком: отменённый намаз остаётся
в статистике выполненным. Поведение принято сознательно.

Оговорка к шагу 3: журнал «растущий» в том смысле, что он не чистится по датам
и не обрезается, — а не в том, что из него нельзя ничего убрать. Снятие ищет
запись с конца, тем же порядком, каким записи добавлялись, и снимает одну.
Журнала нет или записи в нём нет (она старше `since`) — шаг ничего не делает:
отменять тогда нечего, и старой истории он не касается.

### 6.5 Выбор стартового намаза

Курсор не угадывается при инициализации — его задаёт пользователь во вкладке,
в блоке «Откуда продолжаем?».

- Блок содержит пять вариантов (`Фаджр`, `Зухр`, `Аср`, `Магриб`, `Иша`) в виде нативных
  радиокнопок в `role="radiogroup"`. Нативные радио выбраны ради семантики «одно из пяти»
  и навигации стрелками без ручного кода.
- Текущий вариант выделен рамкой `--accent` и словом «сейчас», а не только цветом.
- `change` на группе → `cursor = индекс`, `saveQaza`, перерисовка вкладки.
- Если выбран намаз с остатком 0, курсор доводится до ближайшего ненулевого через
  `nextQazaIndex`. Инвариант «курсор указывает на намаз с остатком > 0» сохраняется,
  и надпись «Начать с: …» не расходится с первым пунктом плана.
- При полностью исчерпанной очереди блок скрывается: выбирать не из чего.

**Разовая миграция.** Состояние с `version: 1` содержало стартовый курсор на Фаджре,
который в начальных данных уже выполнен. При загрузке такого состояния курсор
переставляется на `QAZA_DEFAULT_CURSOR` (Магриб), но **только если журнал выполнений пуст**.
Если выполнения есть, курсор осмысленный и не перезаписывается. Загруженное состояние
всегда помечается текущей `version`.

### 6.6 Ручное добавление пропущенного намаза

Случай: «я вспомнил, что не сделал Зухр». Намаз не выполнен, а обнаружен — поэтому
запись увеличивает долг, но не засчитывается как работа за день.

Блок «Добавить пропущенный намаз»: пять вариантов пилюлями (те же нативные радио,
что и в §6.5) плюс кнопка «Добавить». Вариант не выбран по умолчанию — какой именно
намаз человек забыл, программа не угадывает. Пока выбор пуст, кнопка неактивна.

1. `remaining[key] += 1`.
2. `history.push({ namaz: key, date: сегодня, source: 'manual' })`.
3. `appendQazaLog(key, сегодня, 'manual')` — запись в растущий журнал выполнений
   (§5). Источник у неё свой, `'manual'`: в счёт выполнений статистика такие записи
   не берёт, но день выполнения из журнала не выпадает (§11y).
4. `setRecord` **не вызывается**: счётчик дня от ручных записей не меняется.
5. `cursor` не переставляется — очередь продолжается с того намаза, на котором стояла.
   Исключение — исчерпанная очередь: если `remaining[cursor] === 0`, курсор доводится
   до ближайшего ненулевого через `nextQazaIndex`, иначе инвариант §6.1 сломался бы
   и план разошёлся бы с надписью «Начать с: …».
6. `saveQaza(qaza)`, перерисовать.

После добавления выбор сбрасывается: повторное нажатие не должно записать тот же намаз
второй раз. Ошибочно выбранный намаз откатывается кнопкой «Отменить последнее» (§6.4),
при этом курсор остаётся на месте: ручное добавление его не двигало.

  `.stats-menu-toggle` раскрывает категории. Стрелка пунктом не является:

- `#stats-hub-toggle` — кнопка стрелки. Несёт `aria-label` («Показать

- `.stats-menu-item` — пункт панели, `<button>` с `data-stats-view` =
  `stats` | `stats-fast` | `stats-qaza` | `stats-sleep` | `stats-habits`.

  внутри `#stats-hub-sub`. Отдельный пункт — «Цикл сна»
  с атрибутом `data-sleep-view`: он стоит на верхнем уровне, после блока
  категорий, и экран берётся отдельной веткой обработчика. У остальных

  в него — из панели гамбургера, а она принадлежит главной. Подсвечена
  поэтому «Настройки» — как у статистики, которая живёт там же (§11ab).
- Классы на `body` гасят шапку действий и половины недели: `view-qaza`,

  одно и то же, но имя читается по экрану.
- Статистика открывается строкой из Настроек, а не кнопкой в шапке: гамбургера
  в проекте нет, и раздел живёт вложенным экраном Настроек (§11y). Выход даёт

- Идентификатор отображаемого вида отдельным флагом не хранится — источник правды
  это атрибут `hidden` на самих элементах, чтобы не появилось второе состояние,
  которое может разойтись с DOM.

## 8. Строка `h6` в главной таблице

- Константа `QAZA_HABIT_ID = 'h6'` — по спеке трекера дефолтные привычки имеют
  стабильные id `h1`…`h11`, `h6` документирован как «Каза».

  `<span class="cell-qaza">`: число, а если записи нет — прочерк `—`.
- Делегированные обработчики `#habits-table` не меняются: внутри такой ячейки нет
  `.cell-check`, `.cell-x`, `.cell-select`, `.cell-number`, поэтому события не срабатывают.
- В модалке у `h6` убирается кнопка «Удалить», а селект типа всегда заблокирован.
  Причина: удаление или смена типа сломала бы синхронизацию, причём необратимо.
  Правка имени и единицы остаётся доступной.

**Оформление вкладки.** Мягкая тень карточки, скругления 10–14px,
пилюли радиусом 999px, `tabular-nums` у остатков, заголовок 19px. Лёгкий 3D: у контейнеров
`.qaza-rows` и `.qaza-plan` задан `perspective: 900px`, при наведении строка поднимается
`translateZ(14px) rotateX(1.2deg)` и получает тень `--shadow`, пилюли — `translateZ(8px)`.
Анимируются только `transform` и `opacity` — свойства, не вызывающие перерисовку.

Два ограничителя, продиктованные доступностью:

- Подъём описан внутри `@media (hover: hover)`: на тач-устройствах hover «залипает»
  после касания и карточка осталась бы поднятой.
- `@media (prefers-reduced-motion: reduce)` снимает и анимацию появления, и переходы,
  и трансформации: движение здесь украшение, а не смысл.

  как таковой, а не одного экрана.

  модалки (§11.4в): панель начинается от края экрана и на телефоне
  с вырезом подпись уехала бы под него.
- Выезд — `transform: translateX(-100%)` → `translateX(0)` за .25s
  `ease-out`. Едет только `transform`.
- **Закрытая панель не ловит фокус.** У закрытого состояния
  `visibility: hidden`, у `.is-open` — `visible`, а в переходе
  `visibility 0s linear .25s`: замок снимается после того, как панель
  доехала, и ставится сразу при закрытии. Без этого пункты оставались бы
  в обходе Tab, уехав за край экрана.
- `#stats-menu.is-open` — открытое состояние: `translateX(0)`,
  `visibility: visible`, переход `visibility 0s`.
- `@media (prefers-reduced-motion: reduce)` снимает переходы у панели.
  Блок стоит сразу за её правилами, а не в общем списке выше по файлу:
  `#stats-menu.is-open` сильнее одиночного `#stats-menu`, и запрет,
  объявленный раньше самих правил, был бы перебит порядком.
- `#stats-menu-backdrop` — `position: fixed`, `inset: 0`, `z-index: 55`.
  Выше таб-бара (50) намеренно: панель перекрывает нижнюю навигацию,
  и тап уходит в подложку, а не в кнопки разделов. Своего `display`
  у подложки нет нигде — иначе он перебил бы атрибут `hidden`, которым
  она и гасится. Поэтому в список правила `[hidden]` (§9) её вносить
  не понадобилось.
- `.stats-menu-title` — `--text-muted`, 13px, отступ `0 20px`.
- `.stats-menu-item` — во всю ширину панели, `min-height: 44px`,

- `.stats-menu-toggle` — кнопка стрелки: не меньше 44×44 (`width: 44px`,
  `min-height: 44px`), разделители слева и снизу `--border`, фон

  стрелка читалась кнопкой, а не голой галочкой; разделитель снизу — тот же,
  что у пункта, и строка остаётся одной линией списка. Кольцо

- `.stats-menu-toggle-icon` — сама иконка: `display: block` и переход

- `@media (prefers-reduced-motion: reduce)` снимает переход у иконки. Блок
  стоит сразу за её правилом, а не в общем запрете движения выше по файлу:

## 10. Функции

### Слой данных

#### Контракт сохранения (save-check, 2026-10-17)

- **Boolean-контракт `save*`.** `saveHabits`, `saveRecords`, `saveQaza`,
  `saveQazaLog`, `savePrayer`, `saveFast`, `saveSleep` и `saveStatsPeriod`
  возвращают boolean результата записи (`safeSetItem` при ошибке сам
  показывает тост «Не удалось сохранить: хранилище переполнено»).
  `appendQazaLog` и `dropLastQazaLog` тоже возвращают boolean; у
  `dropLastQazaLog` отсутствие журнала или подходящей записи — успешный
  no-op (`true`), а не ошибка. `setRecord` и `writeHabitEntry` возвращают
  boolean; `setRecord` до мутации делает снимок records, при `false`
  откатывает его и ставит `scheduleSync()` только при успехе. Проверка
  у вызывающих — всегда `if (!save…(…)) …`: ранняя валидация отдельных
  `save*` может вернуть `undefined`, и оно трактуется как провал.
- **Обязательный паттерн обработчиков.** Каждый UI-обработчик, чьё
  действие пишется в хранилище, проверяет результат и при `false`
  прерывается до перерисовки, закрытия попапа/формы и подтверждающих
  тостов: таблица привычек и карточки дня, попап уровня, каза
  («Выполнено», «Отменить», «Добавить», стартовый намаз), ураза, молитвы,
  сон и сегменты периодов статистики. Свой тост об ошибке сохранения
  обработчики не добавляют — его уже показал `safeSetItem`.
- **Составные операции: снимок и откат.** `markQazaDone`, `undoQazaDone`
  и `addMissedQaza` до любых мутаций делают глубокий снимок qaza
  (`JSON.parse(JSON.stringify(qaza))`) и запоминают прежнюю запись дня
  h6; при `false` от любого из своих сохранений (журнал каза, запись дня,
  `saveQaza`) восстанавливают qaza из снимка, откатывают уже успевшую
  записаться запись дня и запись журнала (в `undoQazaDone` — только если
  запись в журнале реально была, `logHadEntry`). `markFastDone`,
  `addFast` и `setFast` делают снимок fast и при `false` от `saveFast`
  восстанавливают объект in-place. `removeHabit` при провале `saveRecords`
  возвращает список привычек на диске к снимку через `saveHabits`
  (best-effort).
- **Изменение контрактов (breaking).** `markQazaDone`, `undoQazaDone`,
  `addMissedQaza`, `markFastDone`, `addFast` и `setFast` возвращают
  boolean, а не объект состояния, как раньше. Вызывающих, которым нужен
  сам объект, не предусмотрено: новые вызывающие обязаны проверять
  boolean и при `false` не перерисовывать UI.
- **CRUD привычек.** `addHabit` и `updateHabit` возвращают созданный /
  изменённый объект при успехе и `null` при провале `saveHabits`.
  `removeHabit` возвращает boolean: `true` только если сохранены и
  привычки, и записи; `scheduleSync()` — только при полном успехе.
- **`saveNormalized`.** Возвращает результат обёрнутой `write()`-функции
  (boolean от `save*`). Сейчас вызывающие (`migratePressHabit`, `loadQaza`,
  `settleHabitsAfterSync`) результат не проверяют — это фоновые пути
  чтения/миграции, где провал записи не блокирует работу приложения.
- **Молитвы.** `applyPrayerCoords` возвращает boolean от `savePrayer`
  и не перерисовывает ничего сама: `afterPrayerChange()` вызывают
  обработчики (`onPrayerGeo`, `onPrayerRefresh`, `onPrayerManualSave`)
  только при успехе. В частности, `onPrayerRefresh` при провале не
  показывает тост «Координаты обновлены».

### Валидация разделов из облака (applyCloudData)

Перед применением каждого раздела с сервера идёт проверка `validCloud<Раздел>`.
Раздел, не прошедший проверку, не применяется, локальное остаётся
нетронутым. Помощники и то, что каждый проверяет:

- `validCloudHabits` — массив; каждый элемент — объект, строковый непустой
  `id`, строковый `name`, `type` из `{boolean, number, choice}`;
- `validCloudRecords` — объект; ключи `'YYYY-MM-DD'`, значения — объекты;
- `validCloudQaza` — объект; `version === QAZA_VERSION`, `cursor` целое 0…4,
  `remaining` — объект с пятью ключами из `NAMAZ_ORDER`, все значения — целые
  ≥ 0, `history` массив;
- `validCloudPrayer` — объект; `lat` число [-89.8, 89.8], `lng` число
  [-180, 180], `madhhab` из `PRAYER_MADHHABS`, `method` из `PRAYER_METHODS`;
- `validCloudFast` — объект; `remaining` целое ≥ 0 (строка и дробное
  отклоняются), `history` массив;
- `validCloudQazaLog` — объект; `since` `'YYYY-MM-DD'`, `entries` массив;
- `validCloudSleep` — как `loadSleep`: `bed`/`wake` — время суток, `fall` целое
  0…120; `actualWake`/`sleepMin` — оба отсутствуют либо сходятся, так же
  `realWake`/`realSleepMin`; `excluded` — boolean, `history` — массив.

`fastInitMode` — переменная уровня модуля: `'add'` или `'edit'`, когда форма
открыта кнопкой обычного экрана, иначе `null`. Первый запуск в неё не пишется:
он выводится из `loadFast() === null`, иначе «ключ стёрли» и «форму ещё
не закрыли» стали бы одним состоянием. При входе на экран (`switchAppView`)
переменная сбрасывается — наполовину заполненная форма уход с экрана
не переживает. Режим первого запуска в коде помечен литералом `'start'`.

`sleepReturnView` — переменная уровня модуля: куда вернёт `#sleep-back`.
У экрана два входа — строка в Настройках на ПК и пункт гамбургера на
телефоне, — и «Назад» обязан вернуть туда, откуда вошли, а не в жёстко
заданный экран (§11ab). Значение снимается один раз, на входе в раздел:
иначе переход между экранами переписывал бы его.

В итоге сна крупным идёт **первый** из `recommended`. Будильник ровно на
конце цикла даёт один вариант — подсвечена одна строка списка; будильник
между двумя циклами даёт два — подсвечены обе строки, а крупным показан
более ранний: решает человек, а не расчёт. Пояснение под будильником
называет число циклов и длительность сна, а при двух вариантах — ещё
и оба времени.

Имена экспорта и импорта начинаются с `export`/`import`/`applyBackup`/`buildBackup`/
`parseBackup` и ни с чем существующим не пересекаются.

`qazaAddPick` — намаз, выбранный в блоке добавления. Хранится отдельной переменной
уровня модуля, а не в `qazaState`: это подготовка к нажатию, а не часть состояния очереди,
и в localStorage она не попадает.

`restoreQazaRadioFocus` нужен потому, что обе группы радио перерисовываются целиком
(`innerHTML`): вместе со старыми узлами уходит и фокус, из-за чего обход стрелками
обрывался на первом же нажатии. Функция возвращает фокус на выбранный вариант; при
мышином клике кольцо `:focus-visible` не появляется, так что вид не меняется.

Ни одно имя не пересекается с существующими: имена каза начинаются с
`qaza` / `QAZA_` / `NAMAZ_`, расписания — с `schedule` / `SCHEDULE_`.

Обработчики навешиваются один раз в `bindEvents()`. Разметка вкладки каза
статична и не перерисовывается целиком, поэтому делегирование там не требуется.

### Ураза: счётчик каза-постов (§11x, 2026-10-05)

Очереди у раздела нет — §6 описывает каза-намазы. Здесь счётчик: одна
величина `remaining` и растущая история событий. Дневной цели, плана
на сегодня и отдельной отмены у него тоже нет. Константы и сигнатуры функций —
выше, в «Слое данных» и «Слое интерфейса»; здесь правила, по которым они
работают.

**Первый запуск.** `loadFast() === null` — единственный признак. Экран
показывает форму с вопросом «Сколько дней нужно возместить?», поле и
«Сохранить»; «Отмены» нет — отменять нечего, обычного экрана ещё не было.
Сохранение заводит ключ через `setFast()`: `remaining` = введённое число,
в историю уходит `{ count: введённое, source: 'set' }`.

**Обычный экран.** Есть при любом заведённом счётчике, включая `remaining: 0`.

1. Строка «Ураза: осталось N дней» — `fastRemainingLabel(n)` со склонением:
   1 и 21 — «день», 2–4 и 22–24 — «дня», 0, 5–20 и 11–14 — «дней».
2. «Возместить 1 день» — `markFastDone()`: при `remaining > 0` уменьшает
   на 1 и пишет в историю `{ count: 1, source: 'done' }`. При `remaining === 0`
   кнопка **погашена**, и обработчик проверяет остаток сам: погашенная кнопка —
   подсказка, а не защита. Счётчик не может уйти в минус ни нажатием,
   ни правкой хранилища — `saveFast` ещё раз приводит значение к ≥ 0.
3. «Добавить уразу» — `addFast(fast, count)`: `remaining += count`,
   в историю `{ count, source: 'add' }`.
4. «Изменить счётчик» — `setFast(fast, count)`: `remaining = count`
   (**перезапись, не прибавка**), в историю `{ count, source: 'set' }`.

Три действия ведут в одну форму `#fast-init`: у неё меняются заголовок
(«Сколько дней добавить?» / «Сколько дней осталось?» / вопрос первого запуска)
и видимость «Отмены» — она есть только у формы, открытой кнопкой.

**Валидация ввода.** `parseFastInput(text, mode)` — только целое число.
Пустое, дробное, отрицательное, нечисловое и больше `FAST_MAX_INPUT`
отклоняются: поле остаётся открытым, под ним появляется сообщение,
в `remaining` и историю ничего не пишется. Режимы: `'counter'` (первый запуск
и «Изменить счётчик») — целое ≥ 0; `'add'` («Добавить уразу») — целое > 0,
ноль не принимается: прибавлять нечего.

**История пишется всегда и не читается.** Отдельной отмены у раздела нет:
возмещённый пост — факт. Ошибочный ввод исправляется вручную через «Изменить
счётчик», а новый счётчик пишется новой записью истории — старые остаются
на месте. Именно поэтому история растущая, а не стек.

### Отмеченные «не баги» (2026-10-06)

Разобраны и правок не требуют:

- **Ветка `manual` в `undoQazaDone`.** Отсутствие явного `else` — стиль,
  а не дефект: при ручной записи функция и так ничего не делает, и это
  функционально совпадает со спекой (§6.4).

## 11r. Уровни выполнения у Корана и Спорта (2026-10-01, восемнадцатая итерация)

Две привычки — Коран (`h8`) и Спорт (`h7`) — получают необязательное время
и два уровня выполнения. Остальные девять привычек не затронуты.
Уровень задаётся попапом с двумя пунктами; у Спорта попапа нет, потому что
там «2 минуты» уже стоят пунктом в самом списке ответов.

### Что было в данных

Спорт — привычка типа `choice`, хранилась **строкой**: `'да' | 'нет' | 'частично' | 'отдых'`
(`CHOICE_OPTIONS`, вес в `calcProgress` — `да 1, частично 0.5, нет 0, отдых 0`).
Не `true/false`. «Отдых» — четвёртый вариант списка, о котором задача молчала;
по решению автора он остаётся, но получает код `rest` и запланированным пропуском:
уровня не несёт, в прогресс не входит, серию не рвёт.

### Решения по развилкам

Зафиксированы с автором задачи до написания кода.

| Вопрос | Решение |
|--------|---------|
| Код «отдыха» | `'rest'` — все четыре значения английские, как `'yes'` и `'two-min'` |
| Коран: «2 минуты» без числа | `value: 0`, `level: 'two-min'` |
| Коран: «Полная версия» без числа | Пункт погашен: пока поле пустое, выполнять нечего |
| Отметка в 00:15 при времени 23:30 | Уезжает во вчерашнюю колонку, сегодняшняя перерисовывается пустой |
| Спорт: уровень | Задаётся только списком. Пункт «2 минуты» ставит `level: 'two-min'`, второй способ через попап не заводится |
| Кому попап | Только Корану: у него числа и уровня в одном поле нет |
| Поле времени в модалке | Нативный `input type="time"` |
| Прогресс Корана | По сумме `value`, а не по числу отметок |

### Схема записи

Схема, поля `time` и `level`, чтение старого формата, `BACKUP_VERSION` — в §5,
раздел «Уровни выполнения у Корана и Спорта»; про ключ `time` у привычки
из формы — §11s.

**`level: null` до сервера не доезжает.** Firebase Realtime Database не хранит
`null` — узел со значением `null` считается удалённым (та же причина, по которой
не хранятся пустые объекты). Запись `{ value: 2, level: null }` уходит наверх
как есть, а возвращается `{ value: 2 }` — без поля. Это не потеря данных:
отсутствующий `level` и `null` значат одно и то же, и `normalizeEntry` читает
`raw.level || null`. Проверено записью в тестовый узел: `{"value":2,"level":null}`
возвращается как `{"value":2}`.

### Уровень и цвет

Уровень выводится из времени отметки: `'on-time'` — попадание в окно ±60 минут
от назначенного, `'late'` — вне окна, `null` — время у привычки не задано.

**Цветные рамки полей убраны** по решению владельца: поля отметки нейтральные
(серая заливка `--surface-muted`, без цветных обводок), и уровень цветом больше
не передаётся. Ранее граница поля красилась (`--success` — вовремя, `--danger`
— поздно, `--two-min: #38bdf8` — «2 минуты»); классы `is-on-time` / `is-late` /
`is-two-min` JS по-прежнему ставит, но CSS их не стилизует — оставлены как хук
данных и для тестов. Уровень виден в попапе «Как выполнено?» и по точке
`.cell-level-btn.is-set` на кнопке уровня.

Спорт уровнем отвечает только на «да»: «нет» и «отдых» выполнением не являются
и уровня не несут. «2 минуты» в списке — само себе уровень.

### Граница дня обычных привычек

Если назначенное время привычки на **вчера** попадает в окно ±60 минут от «сейчас»,
отметка уезжает во вчерашний день. Время 23:30 и отметка в 00:15 — это вчера;
в 00:45 — уже сегодня. Считается расстояние по часовой стрелке через полночь,
поэтому правило само срабатывает только в первый час после неё.

Правило смотрит только на **сегодняшнюю** колонку: день, выбранный руками,
человек выбрал осознанно. Сегодняшняя клетка при этом перерисовывается пустой —
отметка встаёт в свою колонку, а не остаётся в чужой.

### Правило дня каза

`kazaDayBoundary()` возвращает начало дня каза в минутах от полуночи UTC+3:
Фаджр из `prayerTimes()` по текущим координатам, а при их отсутствии или
неудачном расчёте — 05:00 (300). `kazaDayFor(now)` по этой границе выбирает день:
до неё — вчерашний, после — сегодняшний.

Следствия:

- `markQazaDone`, `addMissedQaza`, `undoQazaDone` и фильтр истории в `loadQaza`
  работают с днём каза, а не с календарным. Отмена снимает вчерашнюю запись
  там же, где та легла, и переживает перезагрузку.
- Счётчик `h6` уходит во вчерашний день.
- При переносе во вчера показывается тост `showToast('Каза зачтена во вчерашний день')`.
  Днём тоста нет.
- Часы сверяются по UTC+3 — тому же поясу, в котором считает `prayerTimes()`,
  а ключ дня берётся общим `toISODate`, как у остальных записей.

### Разметка

Элементы, классы и атрибут `data-level-sheet-close` — в §7, раздел «Уровни
выполнения». Здесь только то, чего там нет: попап открывается у одного Корана —
у Спорта «2 минуты» стоят пунктом в самом списке, и второй способ задать тот же
уровень не заводится. Кнопка вызова попапа несёт `data-habit-id` и `data-date`.
В `switchAppView` попап закрывается — единообразно с панелью статистики (§11z).
Программный переход (из консоли, теста или будущего кода) без этого оставил бы
попап висеть поверх нового экрана. Тап по вкладке таб-бара по-прежнему попадает
в подложку (`z-index: 120` выше 50): попап гасится, вид не меняется.

### Функции

Константы и сигнатуры — в §10, раздел «Уровни выполнения».
`onTableChange` при правке значения сохраняет выбранные «2 минуты» — но только
у Корана: у Спорта уровень выводится из самого ответа, и «отдых» после «2 минут»
не должен сохранить уровень `two-min`.

### Критерии готовности

1. `time` сохраняется и читается в модалке привычки; у привычек без уровней
   поля времени нет; пустое поле даёт `null`, а не пустую строку.
2. Классы уровня ставятся правильно: `is-on-time` — вовремя, `is-late` —
   поздно, `is-two-min` — «2 минуты». Сами поля нейтральные: цветные рамки
   убраны, заливка и текст не меняются.
3. Уровень «2 минуты» ставится всегда, в том числе при `time: null`.
4. Окно ±60 минут: ровно 60 — вовремя, 61 — поздно, в обе стороны.
   Битое время и `null` уровня не дают.
5. Отметка после полуночи в пределах часа относится ко вчера; 00:45 — уже сегодня;
   чужой день руками не переписывается.
6. Каза до Фаджра относится ко вчера. Без координат граница 05:00;
   с координатами — Фаджр из `prayerTimes()`.
7. Тост «Каза зачтена во вчерашний день» показывается; днём его нет.
8. Отмена снимает вчерашнюю запись, остаток возвращается, журнал опустеет.
9. Старые записи читаются корректно: число Корана как `value`, «частично» —
   как «2 минуты» с уровнем `two-min`, «да»/«нет»/«отдых» — в новые коды.
10. Спорт переведён на новую схему: четыре пункта без «частично»,
    «2 минуты» в списке ставит уровень `two-min`, «отдых» уровня не несёт.
11. Кнопка попапа есть у Корана и её нет у Спорта — ни в таблице, ни в карточке дня.
12. Таблицы, Книга и Каза не задеты: их записи остаются скалярами,
    кнопки уровня у них нет, прогресс считается как раньше.
13. В недельной таблице на телефоне поле числа Корана и кнопка попапа стоят
    в одной строке (одинаковый отступ сверху), строка Корана не выше строки
    Спорта, оба элемента не вылезают из колонки, а двузначное число в поле
    видно целиком. Без правил, которые это держат, строка снова распухает —
    проверяется там же, снятием правил у страницы.

Проверки живут в `.scratch/habits-edit/check.js`: 228 проверок (на дату записи;
текущее число — в §11x), из них 158 новых.

**Проверка на живом iPhone.** Разговорчивость тоста автор смотрит на живом
iPhone: headless-браузер яркость не передаёт. Читаемость цветной границы
на солнце больше не проверяется — рамки убраны.

**Правка соседних наборов.** В `.scratch/day-week/check.js` две проверки ждали
скаляр у Спорта и Корана — теперь они ждут объект `{ value, level }`, как требует
эта итерация. В `export-import`, `prayer` и `settings-pc` обновлены версия файла
копии (3 → 4) и дата сборки в строке версии.

В `.scratch/prayer/check.js` переписаны три проверки на iPhone SE про счётчик
до начала намаза. Прежние ждали счётчик в раскрытом списке всегда, а он там
бывает не всегда: после Иши следующий намаз — завтрашний Фаджр, и в раскрытых
шести строках его нет, потому что там времена сегодняшнего дня. Теперь счётчик
ищется в свёрнутой паре (следующий и после следующего — её `view.shown` и есть),
а раскрытый список сверяется с днём следующего намаза: сегодня — ровно одна
строка со счётчиком, завтра — ни одной, и вместо него о дне говорит подсказка
«завтра» в круге. Проверено в обеих ветках на замороженных часах (12:00 и 19:36).

**Заглушка сети — теперь проверяется, а не предполагается.** Во всех восьми
наборах `foreignCalls` возвращал `window.__calls || []`, и отсутствие заглушки
выглядело как «в сеть не ходили»: проверка «боевой адрес не использован»
проходила вхолостую. Теперь при неопределённом `__calls` возвращается метка
`'ЗАГЛУШКА НЕ УСТАНОВЛЕНА'`, которая не начинается с тестового пути и роняет
проверку. Разом проверено, что заглушка ставится на каждой странице каждого
набора, что ни одна из них не откатывается к настоящему `fetch`, что в самом
приложении нет транспорта кроме `fetch` (ни `XMLHttpRequest`, ни `WebSocket`,
ни `EventSource`) и что все наборы открывают `file://`, где service worker
не регистрируется. Боевой узел трогается только на чтение.

## 11s. Время новой привычки, «Пресс» и миграция (2026-10-02, девятнадцатая итерация)

Три правки: у привычки из формы появляется ключ `time`, заводится третья
привычка с уровнями «Пресс», и она доезжает до устройства со сложившимся
списком разовой миграцией.

### Решения по развилкам

Зафиксированы с автором задачи до написания кода.

| Вопрос | Решение |
|--------|---------|
| id и место «Пресс» | `h12`, в конце `DEFAULT_HABITS` |
| Форма «Новая привычка» | Не меняется. Тип «Выбор» у неё общий, коды и уровни привязаны к id привычки |
| Как «Пресс» попадает на iPhone | Разовой миграцией при загрузке |
| Защита миграции | Флаг в новом ключе `youplanner.migrations`: правка проходится один раз на устройстве |

### Время у новой привычки

`addHabit` ставит `time: null` при создании. До этого ключа у привычки
из формы не было вовсе, и получалось два формата одного состояния: у одной
привычки ключ есть и пуст, у другой его нет. Читающий код оба понимает
одинаково (`habitLevelByTime` и `habitMarkDate` проверяют `null` и `undefined`
вместе), но состояние всё равно одно, поэтому ключ теперь ставится сразу.

Привычек без уровней это не касается: у `h1`–`h6` и `h9`–`h11` поля `time`
нет вовсе, и в форму они попадают по-прежнему без него — ключ добавляет
только `addHabit`, а не `defaultHabit`.

### «Пресс» (`h12`)

```js
{ id: 'h12', name: 'Пресс', type: 'choice', unit: '', goal: null, time: null }
```

Такая же, как Спорт: тип `choice`, список ответов «да / нет / 2 минуты / отдых»,
своё поле времени, уровни по общим правилам (`on-time` / `late` / `two-min`,
при `time: null` уровня нет). Цветных рамок у полей нет — как и везде,
после их удаления. Иконок у вариантов нет: ни у «отдых» и «нет», ни у
остальных — список остаётся текстовым, как у Спорта.

Кода правок немного, потому что «Пресс» — второй экземпляр уже описанной
схемы, а не новая:

- `PRESS_HABIT_ID = 'h12'` рядом с `SPORT_HABIT_ID` и `QURAN_HABIT_ID`;
- `isChoiceLevelHabit(habitId)` — «Спорт или Пресс»: привычка типа `choice`
  со своим списком кодов. Заменяет прежние проверки `habitId === SPORT_HABIT_ID`
  в `normalizeEntry`, `defaultLevel` и `choiceOptionsMarkup`;
- `isLevelHabit` = `isChoiceLevelHabit(habitId) || habitId === QURAN_HABIT_ID`;
- `hasLevelPopup` не тронут — попап остаётся только у Корана: у Спорта
  и Пресса «2 минуты» стоят пунктом в самом списке ответов.

`CHOICE_OPTIONS`, веса `calcProgress`, поле времени в модалке и в списке
«Привычки» (`isLevelHabit`) подхватывают «Пресс» сами: и то, и другое уже
написано через общие проверки. `BACKUP_VERSION` не меняется — формат записи
и `habits` не изменились.

### Миграция `h12`

Устройство, где список привычек давно лежит в `localStorage`, из `DEFAULT_HABITS`
ничего не получит: дефолты пишутся только на подтверждённо пустом сервере
(§11t). Поэтому `h12` туда доводит разовая миграция.

```js
// youplanner.migrations
{ "press": true }
```

`migratePressHabit()` зовётся из `settleHabitsAfterSync` — то есть после
первой сверки, а не при чтении. Если `h12` в списке нет, привычка добавляется
в конец копией из дефолтов и список сохраняется через `saveNormalized`.
Флаг ставится **до** проверки списка: миграция считается пройденной и тогда,
когда добавлять было нечего.

На пустом списке миграция молчит и флаг не ставит. Иначе она завела бы «Пресс»
на устройстве, которое ещё не знает своих привычек, — то есть вернула бы
удалённую привычку ровно тем механизмом, ради которого заведён флаг.

Флаг — не украшение, а условие задачи. Без него «нет `h12` — добавить» означало
бы, что удалённый «Пресс» возвращается при каждой загрузке: ровно тот механизм,
из-за которого в первых версиях возвращались удалённые привычки (разбор — §11t).
С флагом правка проходится один раз на устройстве, и удаление «Пресса»
остаётся удалением.

Побочное следствие, осознанное: устройство, которое миграцию уже прошло,
а `h12` с сервера не получило (например, «Пресс» удалён на другом устройстве),
второй раз его не заведёт. Это и есть цена однократности.

Запись идёт через `saveNormalized`, поэтому миграция не взводит `syncPending`
и не мешает применить серверный снимок — она читается как приведение данных
в порядок, а не как правка человека (§11o — журнал). Наверх «Пресс» уезжает обычным
порядком: следующим `PUT`-ом после первой правки.

Сигнатуры — в §10, раздел «Привычки и первая сверка». `STORAGE_KEYS` получил
`migrations: 'youplanner.migrations'`. `loadHabits()` миграцию не зовёт: её
место — `settleHabitsAfterSync` (§11t). Разбор дефолтов свёрнут в `defaultHabit`.

### Разметка и стили

Ничего не добавилось. «Пресс» рисуется теми же `.cell-select`, `.day-card`,
полем времени `.habit-edit-time` и цветами `levelClass`, что Спорт: новых
классов, id и переменных палитры итерация не завела.

### Критерии готовности

1. `addHabit` ставит `time: null` — и в возвращаемой привычке, и в сохранённой;
   привычка, заведённая формой «Новая привычка», приходит с этим ключом.
2. Привычка без ключа `time` и привычка с `time: null` читаются одинаково:
   `habitLevelByTime`, `habitMarkDate` и `defaultLevel` дают тот же ответ.
3. «Пресс» есть в `DEFAULT_HABITS` под id `h12`, последним в списке, типом
   `choice` и явным `time: null`; дублей нет.
4. У «Пресса» четыре ответа Спорта и пустая опция; иконок в разметке нет.
5. Классы уровня у «Пресса»: `on-time`, `late`, `two-min`, обычный — по уровню
   записи; цветные рамки не красятся, поля нейтральные.
6. «2 минуты» пишутся объектом `{ value: 'two-min', level: 'two-min' }`,
   «отдых» уровня не несёт и прогресса не даёт, «да» — 1, «2 минуты» — 0.5.
7. Поле времени есть у «Пресса» в модалке и сохраняется как у Спорта;
   кнопки попапа у него нет ни в таблице, ни в карточке дня.
8. Миграция: на списке без `h12` привычка добавляется в конец с дефолтными
   настройками, флаг `press` появляется в `youplanner.migrations`.
9. Удалённый «Пресс» больше не возвращается; существующий не дублируется
   и не затирается; на чистой установке — двенадцать привычек и флаг сразу.

Проверки: `.scratch/habits-edit/check.js` вырос с 228 до 272; счёт привычек
обновлён с 11 на 12 в `habits-edit`, `day-week`, `export-import`, `settings-pc`
и `sync`, в `day-week` селект типа `choice` теперь ищется по id.

**Проверка на живом iPhone.** Как выглядит «Пресс» в таблице и в карточке дня
на живом iPhone — headless-браузер показывает разметку, но не читаемость
на солнце.

## 11v. Перерисовка после отклонённого снимка (2026-10-03, аудит)
> Возвращено инлайн при сжатии 2026-11-13: целевой раздел АКТИВНОЙ ссылки.

**Что было.** `syncFromCloud` отвергает серверный снимок, если тот старше
локальной метки времени или спорит с правкой, которой сервер ещё не видел
(`cloudSnapshotWins`). У этой ветки есть один выход для привычек: если своих
привычек у устройства нет вовсе, серверный список всё же забирается в
`localStorage` — иначе пустой список уехал бы наверх и стёр серверный. Запись
в хранилище была, а перерисовки после неё не было: `appState.habits` оставался
прежним, и таблица, карточки дня и пометка «Привычки не загружены» показывали
старое состояние. Ветку применённого снимка это не задевало: там данные
приводит `applyCloudData`, и экран она перерисовывает сама.

**Что стало.** После того как отклонённый снимок отдал серверные привычки
в `localStorage`, экран перерисовывается тем же путём, что и при применённом
снимке: `appState.habits` перечитывается через `loadHabits`, затем идут
`renderMainView`, `renderQazaView`, `renderTasksView`, `renderPrayerView` —
тот же набор, что и в `applyCloudData`. Сверх этого не добавлено ничего;
поведение ветки применённого снимка и остальных вызовов `syncFromCloud`
(`init`, кнопка «Обновить с сервера») не менялось.

**Где правилось.** `index.html`, функция `syncFromCloud`, ветка
`!cloudSnapshotWins`. Пометка `#habits-note` снимается тем же вызовом: список
стал непустым, а `cloudReachable` уже взведён ответом сервера.

**Проверки.** Набор `.scratch/sync/check.js`: пустое хранилище и снимок, который
проигрывает по времени; серверные привычки легли в `localStorage`; таблица
показывает тот же список; пометка снята; дефолты наверх не ушли; консоль без
ошибок.

## 13. Известные ограничения

- Расписание редактируется через Настройки («Редактировать расписание»).
  Пустой массив для типа дня — валидное состояние (пользователь удалил все
  пункты); `loadSchedule` вернёт его как есть. Битый JSON или отсутствие
  ключа читаются как `DEFAULT_SCHEDULE`. Выбранный тип дня в просмотре
  по-прежнему не сохраняется между запусками.
- **Пустое хранилище без подтверждённой сверки не засеивает дефолты.**
  Отсутствие ключа `youplanner.habits`, пустая строка, битый JSON и не-массив
  читаются `loadHabits` одинаково: пустой список. `DEFAULT_HABITS` пишутся
  только в `settleHabitsAfterSync`, и только если сервер ответил и подтвердил,
  что он пуст. Пока ответа нет, таблица пустая и об этом говорит пометка
  `#habits-note`: пустая таблица — это «не загрузили», а не «привычек нет».
  Обратная сторона: недоступный сервер на чистом устройстве оставляет
  приложение без привычек до первой удачной сверки. Пустой массив `[]`
  дефолтами не заменяется и после неё — это осознанное «привычек нет».
- **Узкая щель с `habits: []`.** Пока сверка ни разу не дошла до сервера,
  `syncBody` не отправляет пустой список как есть, а подставляет привычки
  из предыдущего узла. Но если предыдущий узел прочитать не удалось — чтение
  упало, а `PUT` при этом прошёл — и своих привычек у устройства нет, наверх
  уходит `habits: []`. Решение оставить как есть, не закрывать.
  Что при этом происходит:
  - `PUT` кладёт узел целиком, поэтому в узле на сервере привычек не станет;
  - устройства своих привычек не теряют: `applyCloudData` пустой раздел
    не применяет — это уровень защиты 1 (§2a), — а из локального хранилища
    привычки никуда не деваются;
  - список вернётся со следующей отправки с устройства, где он есть: правка
    человека или «Отправить на сервер» в Настройках.
  Если же узел прочитался и он пуст, `[]` уходит по делу — привычек
  на сервере и не было.
- **Облачный раздел применяется только целиком.** `applyCloudData` проверяет
  каждый раздел снимка своим `validCloud*`: частичное применение невозможно —
  раздел либо валиден целиком, либо не применяется, локальные данные остаются
  нетронутыми. Это ограничение защищает данные от порчи.
- Правим артефакт напрямую: `index.html` + `styles/` + `js/` — источник
  правды; сборка не восстанавливается.
- Если привычку `h6` удалить в обход модалки (правкой `localStorage`), синхронизация
  отключится: вкладка продолжит считать очередь, но строки в таблице не будет.
  `loadQaza` и `markQazaDone` обязаны это переносить без ошибок.
- Записи `h6`, введённые вручную до этой задачи, остаются в `youplanner.records`
  и продолжают влиять на круг; вкладка о них не знает и не переписывает их.
  После первого выполнения вкладка перезапишет значение за сегодняшний день.
- У того, кто пользовался удалённой тёмной темой, в `localStorage` остался ключ
  `youplanner.theme` со значением `dark`. Код его не читает и на палитру он не
  влияет. Удалять ключ кодом не стали: пришлось бы вернуть в файл строку
  `'youplanner.theme'`, то есть снова сослаться на тему. Ключ безвреден и уйдёт
  вместе с остальными при очистке хранилища.
- Общий тост молитв и каза исчезает сам через 3,5 с и повторить себя не умеет: не успевший
  прочитать увидит сообщение только при следующей попытке. Истории
  сообщений в приложении нет.
- Одновременная правка с двух устройств: правило «кто позже, тот прав»,
  правки одного могут потеряться. Это ограничение всего проекта, и раздел
  «Ураза» подпадает под него наравне с остальными (§11x): счётчик ходит
  одним разделом `fast` целиком, слияния по событиям истории нет, поэтому
  возмещённый день, записанный на одном устройстве, разойдётся с другим.
  Пустой раздел с сервера (`null`) заведённый счётчик не затирает — это
  уровень защиты 1 (§2a), — но обратное верно: обнулив счётчик на одном
  устройстве, на другом его не обнулить.
- История уразы растёт без ограничения и не чистится по датам: это её
  назначение, а не недосмотр (§5, §11x). Запись снимается только вместе
  с очисткой хранилища или заменой ключа импортом. При 365 событиях в год
  это около 20 КБ в год — размером решено не управлять, но запись о том,
  что предела нет, здесь оставлена. Отдельной отмены у раздела тоже нет:
  ошибочный ввод исправляется кнопкой «Изменить счётчик», а исправление
  ложится в историю новой записью, старые остаются на месте.
- `validFastHistory` проверяет форму даты, а не её существование: `2026-13-45`
  чистку пройдёт — регулярное выражение смотрит на вид строки, а не на
  календарь. Запись такого вида появляется только из испорченного хранилища,
  и вреда от неё не больше одной строки в цифре «История копится с»:
  в график такой день не попадёт (§5, §11y).
- Восстановление из отдельного корня `FIREBASE_BACKUPS_URL` — вручную через
  Firebase Console. Старый вложенный путь `youplanner-a7x9k2/backups` не
  используется.
- Обновление PWA требует закрытия и открытия приложения.
- Времена намазов считаются по формулам, а не берутся из справочника. Сверены
  с расписанием ДУМ ЧР для Петропавловской (43.38639, 45.82889) на весь сентябрь
  2026: расхождение не больше одной минуты по всем шести временам и всем
  тридцати дням (§11q). Сверен только этот месяц: на другие месяцы и другие
  координаты эталона не было, поэтому там совпадение не проверено. С таблицами
  других источников расхождения могут быть больше: эталон у каждой мечети свой,
  и совпадение с одним не означает совпадения с остальными. Геолокация
  округляется до пяти знаков — около метра, — и на времена это не влияет.
- Постоянных правок в минутах в расчёте нет и быть не должно. Всё, что
  уточняется под источник, живёт в углах метода (Фаджр 16°, Иша 15°), в тени
  Асра и в закреплённом Зухре. Правка вида «прибавить десять минут к Фаджру»
  прячет расхождение вместо того, чтобы его показать, — на этом уже один раз
  ошиблись, подгоняя времена под описание другого источника (§11q).
- Зухр у метода ДУМ ЧР — фиксированное время **12:30** на весь год, а не истинный
  солнечный полдень: так его публикует ДУМ ЧР. Полдень для Петропавловской
  ложится между 11:40 и 12:11, поэтому Зухр метода из расчёта не выводится вовсе и
  от координат не зависит. Кому нужно астрономическое значение — переключатель
  «Астрономический» в Настройках.
- Шафиитская тень для Асра — ровно ×1, ханафитская ×2. Промежуточных значений
  у мазхаба нет, и шафиитский Аср под чужой источник не подтягивается.
- Часовой пояс расчёта — константа UTC+3 (§11q). Для координат за пределами
  этого пояса времена будут показаны по московскому времени, а не по местному.
  Осознанное решение: задача поставлена для ДУМ ЧР.
- Высокие широты: за полярным кругом Фаджр и Иша могут не наступать, и тогда
  их время пустое. Экран это переносит, но «разумного» значения не подставляет.
- Safe-area на iPhone проверяется только глазами: Playwright отдаёт 0px
  для `env(safe-area-inset-*)`. Правила с `env()` в тестах нормальны,
  на телефоне крестики и панели уезжают под Dynamic Island.
  Коснулось `#tab-bar` и `.modal-header`.
- PWA-ассеты лежат в папке проекта рядом с `index.html`: `manifest.json`,
  `sw.js`, `icon-180.png`, `icon-512.png`, `icon.svg`. На рабочем столе
  оставлены их копии. Все ссылки в разметке относительные, поэтому
  на GitHub Pages файлы должны лежать в той же папке, что и `index.html`.
  `icon.svg` не используется ни разметкой, ни манифестом: манифест ссылается
  на `icon-180.png` и `icon-512.png`.
- Регистрация service worker по `file://` не проходит: браузер не заводит
  service worker на file-схеме. Регистрация обёрнута в `.catch(function () {})`
  и молчит, страница работает как обычно. Офлайн даёт только GitHub Pages
  по https.
- **Гонка в автобэкапе `FIREBASE_BACKUPS_URL.json`** (аудит 2026-10-06,
  решено не чинить). Два устройства или две вкладки читают список копий
  одновременно, каждая делает `unshift` и пишет свой список — один снимок может потеряться.
  Транзакций REST не даёт, а цена закрытия выше пользы: страдает только
  глубина резервной копии, данные человека при этом целы.
- **Контраст активных пилюль метода расчёта и мазхаба — 5.03:1**, запас 0.53
  к порогу. Если палитра будет меняться, это первое место, где порог поедет.
- **Правило 18:00 в статистике сна и дневной сон.** Средние отбой и подъём
  в разделе «Статистика → Сон» считаются по одной шкале «вечер → ночь →
  утро»: времена до 18:00 сдвигаются на сутки, чтобы отбой в 23:30 и отбой
  в 00:30 не разъехались на 23 часа в среднем. Плата за это — дневной сон
  не учитывается: запись с отбоем в 15:00 сдвинется на 15:00 следующих
  суток и утянет среднее вверх. Для трекера ночного сна это принято;
  отдельного признака «это дневной сон» у записи нет, и раздел его
  не различает.
- **`sleepAverageMinutes` не доверяет входу.** Функция оставляет
  в массиве только конечные числа и лишь потом считает среднее:
  `null`, `undefined` и строки до арифметики не доходят. Сейчас это
  подстраховка, а не лечение наблюдаемой ошибки: `validSleepHistory`
  отбрасывает записи с пустым `bed` или `actualWake`, и до функции
  такие значения не добираются. Фильтр стоит затем, чтобы связка
  «очистка → среднее» держалась на функции, а не на памяти о том,
  кто её зовёт.
