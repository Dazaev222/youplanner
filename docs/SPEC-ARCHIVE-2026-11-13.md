### 11.2 Критерии экспорта/импорта

1. Экспорт скачивает `youplanner-backup-YYYY-MM-DD.json`.
2. Содержимое файла совпадает с `localStorage` по `habits`, `records`, `qaza`,
   `prayer`, `fast`, `qazaLog`, `sleep`; раздел tasks снят, `version` в файле — 10.
   Разделы `fast`, `qazaLog` и `sleep` необязательны и попадают в файл только
   при заведённом счётчике, журнале или записи о сне соответственно:
   устройство без них ключа в файле не заводит.
3. Импорт валидного файла заменяет данные, `scheduleSync` вызван.
4. Битый JSON → `alert`, данные не изменены.
5. Отсутствие `records` → `alert`, данные не изменены.
6. Cancel в `confirm` → данные не изменены.
7. Повторный импорт того же файла работает.
8. Снято 2026-10-14: импорт раздела `tasks` с заменой списка задач.
9. Снято 2026-10-14: импорт без `tasks` с сохранением локальных задач.
10. Снято 2026-10-14: проверка типа раздела `tasks` при импорте.
    Файл со старым разделом `tasks` отвергается целиком: `alert`, данные не изменены.
11. Импорт файла с разделом `prayer` заменяет координаты, мазхаб и метод
    расчёта целиком: раздел пишется в ключ `youplanner.prayer` как есть,
    слияния по полям нет. Пустой `prayer` в файле координаты стирает —
    раздел заменяется без оговорок, подтверждение уже спрошено (§11q).
12. Импорт файла без раздела `prayer` координаты не трогает: остаются те,
    что были.
13. `prayer` в файле не объект (в том числе массив) → `alert`, данные
    не изменены.
14. Запись с уровнем уезжает в файл как есть: у Корана и Спорта в `records`
    лежит объект `{ value, level }`, и в скачанном файле он тот же объект,
    а не развёрнутый в два поля или в скаляр (§11r).
15. Импорт файла с объектной записью применяется: поле отметки показывает
    `value`, класс уровня ставится по `level` (цветной рамки больше нет —
    класс не видно глазом, читается только тестами).
16. Скалярная запись в файле читается как `{ value, level: null }`: старое
    число страниц Корана не роняет разбор и попадает в поле как число,
    а класс уровня не ставится. Файл версии 3 и ниже принимается наравне
    с текущей версией 8 — разбор версию не проверяет.
17. Импорт файла с разделом `fast` заменяет счётчик уразы целиком: раздел
    пишется в ключ `youplanner.qaza.fast` как есть, слияния по полям нет.
    Файл без раздела `fast` счётчик сохраняет: остаётся тот, что был.
    `fast` в файле не объект (в том числе массив), `remaining` не число
    или `history` не массив → провал разбора без `confirm`, данные целы
    (§11x).
18. Импорт файла с разделом `qazaLog` заменяет журнал выполнений каза целиком:
    раздел пишется в ключ `youplanner.qaza.log` как есть, слияния по полям нет.
    Файл без раздела `qazaLog` журнал сохраняет: остаётся тот, что был,
    — импорт старых копий историю не стирает. `qazaLog` в файле не объект
    (в том числе массив), `since` не дата `'YYYY-MM-DD'` или `entries`
    не массив → провал разбора без `confirm`, данные целы. Битая запись внутри
    `entries` провалом не считается: она отбрасывается молча, порядок валидных
    сохраняется, разбор не отклоняется (§5).
19. Раздел `sleep` необязателен. Импорт файла с разделом заменяет запись
    целиком. Файл без раздела запись сохраняет. `sleep` не объект, `bed` или
    `wake` не `'HH:MM'`, `fall` не целое 0…120 — отказ разбора. `version`
    в файле — 10. Пара `actualWake`/`sleepMin` есть только у файла версии 2
    и моложе: файл без неё — старая копия, и разбирается как разбирался,
    а `loadSleep()` подставит недостающее целью. Пара есть, но битая
    (`actualWake` не время суток, `sleepMin` не целое 0…1439) — отказ
    разбора. Пара `realWake`/`realSleepMin` и флаг `excluded` — версия 4.
    Файл без них разбирается как раньше: значения подставляются null, null,
    false. Файл с ними проверяется по тем же правилам, что `loadSleep`:
    `realWake` — null или время суток, `realSleepMin` — null или целое
    0…1439, смешанные состояния — отказ разбора. История необязательна,
    как и у уразы: файл версии 7 её не знает и разбирается как разбирался.
    История есть, но не массив — отказ целиком: запись легла бы в ключ,
    а следующий `loadSleep()` отбросил бы историю, и она бы молча пропала.
    Битые элементы внутри массива разбор не роняют — их отбрасывает
    `validSleepHistory`.

14. Удаление спрашивает `confirm('Удалить задачу?')`; отказ не меняет данные,
    согласие удаляет задачу из `localStorage` и из списка.
15. Возврат к форме создания возвращает заголовок «Новая задача», пустое поле
    и меню без строки «Удалить».
16. Escape при открытом меню закрывает верхнюю шторку за раз: сначала меню
    действий, потом меню приоритета, и только затем форму.
17. Тап по подложке формы закрывает её без сохранения: введённый текст
    задачу не создаёт.

### 11.4в Критерии пикера даты (§11n — журнал) — снято 2026-10-14

*Снято: пикер задач удалён вместе с разделом «Задачи» (§11ac). Критерии ниже — история.*

Пункты 3, 13 и 23–30 переписаны вместе с отказом от сдвига на год: прошедший
день больше не уводит дату вперёд, а запрещает сохранение.

1. Поля времени `#task-sheet-time` в форме больше нет; в `.sheet-toolbar`
   три элемента, галочка `#task-sheet-save-inline` — последняя.
2. Кнопка даты `#task-sheet-date` активна и при создании, и при правке;
   тап по ней открывает `#task-date-sheet`.
3. Подпись на кнопке — «Сегодня», «Завтра» или «дд.мм»; у новой задачи это
   выбранный день вкладки, у правки — день самой задачи, а если он уже прошёл,
   то сегодняшний (критерий 26).
4. В пикере три чипа, сетка из 42 ячеек, строка «Срок исполнения»
   и кнопка «Очистить»; подпись месяца — как у календаря вкладки; текущий
   день помечен `is-today`, выбранный — `is-selected`.
5. У дней с задачами в сетке пикера стоят те же точки статуса, что
   в календаре вкладки (`getDayMarker`).
6. Чип «Завтра» записывает `formDate` на завтрашний день, закрывает пикер
   и меняет подпись кнопки на «Завтра».
7. Задача, сохранённая после чипа «Завтра», попадает в `youplanner.tasks`
   с завтрашней датой и не появляется в сегодняшнем дне.
8. Чип «След. понедельник» даёт ближайший понедельник после сегодняшнего
   (если сегодня понедельник — следующий, через неделю).
9. Тап по ячейке сетки выбирает её день (`data-date`), закрывает пикер
   и меняет подпись кнопки.
10. Листание месяцев `#date-cal-prev` / `#date-cal-next` меняет подпись
    месяца и не сбрасывает `formDate`: выбранный день остаётся прежним.
11. Тап по строке «Срок исполнения» открывает поверх пикера шторку колеса
    `#task-time-sheet`; пикер даты остаётся открытым под ней. Панель колеса
    стоит по центру экрана (`.time-sheet-panel`) и снизу не выезжает, подложка
    у шторки своя и затемняет всё окно. Колесо часов
    идёт 00–23, колесо минут — 00–55 с шагом 5. Прокрутка нативная, со снапом:
    выбранной считается строка, вставшая в середину окна, — она крупнее
    и темнее соседних, у краёв окна затухания. При пустом `formTime` оба
    колеса стоят на «00».
12. «Готово» в шапке колеса пишет выбранные часы и минуты в `formTime`,
    закрывает только колесо и возвращает в открытый пикер, а подпись срока
    становится «Сегодня, 14:30». «✕», тап по подложке и Escape закрывают
    колесо, время не записывая. Время задаётся в форме только колесом: после
    закрытия пикера кнопка даты по-прежнему показывает день, а сохранение
    пишет это время в задачу.
13. «Очистить» при создании возвращает сегодняшний день и `formTime = null`;
    «Очистить» при правке возвращает день задачи, а если он уже прошёл —
    сегодняшний (критерий 29); `formTime` при этом тоже сбрасывается, а пикер
    не закрывается.
14. Задача без времени сохраняется с приоритетом `low`, со временем — `high`.
15. Смена даты в правке переносит задачу: в `youplanner.tasks` меняется
    `date`, на прежнем дне задачи не остаётся.
16. Лимит десяти в правке считается без учёта самой задачи: перенос на день
    с девятью невыполненными проходит, с десятью — блокируется `alert`
    «На этот день уже 10 невыполненных задач», данные не меняются.
17. Создание с датой на переполненном дне даёт тот же `alert`; задача
    не создаётся, форма остаётся открытой с введённым текстом.
18. Перенос уже выполненной задачи спрашивает
    `confirm('Задача выполнена. Снять отметку и перенести её на другой день?')`:
    согласие меняет `date` и ставит `done: false`, отказ не меняет ничего —
    ни дату, ни отметку.
19. Смена даты зажигает галочку сохранения, возврат прежней даты её гасит.
20. Закрытие формы сбрасывает `formDate` и `formTime`: следующее открытие
    на создание даёт день вкладки и пустое время.
21. Escape снимает шторки по слоям: открытое колесо времени — первым, затем
    пикер; форма под ними остаётся. «✕» и тап по подложке делают то же самое
    в своей шторке.
22. Панель пикера не выходит за экран: на iPhone SE (320×568) она ограничена
    по высоте и прокручивается, чипы видны сверху, «Очистить» достаётся
    прокруткой; горизонтального перелива нет.
23. Прошедшие дни в сетке пикера помечены `is-past` и приглушены цветом
    `--text-muted`; сегодняшний и будущие дни этой пометки не получают.
    Пометка — единственная подсказка о прошлом дне: выбрать его она не мешает.
24. Прошедший день выбирается как любой другой: тап по нему пишет его
    в `formDate`, закрывает пикер и меняет подпись кнопки даты. Сдвига даты
    на год в приложении нет вовсе — функции `rollToFuture` и её вызовов
    не существует.
25. Сохранить прошедшую дату нельзя. Если `formDate` меньше сегодняшнего дня
    (человек выбрал его в пикере руками), сохранение показывает тост
    «Упс... дата уже прошла, выберите будущую дату» и не делает больше ничего:
    ни при создании, ни при правке задача не пишется, форма остаётся открытой
    с выбранной датой, `formDate` не сбрасывается, `confirm` и `alert`
    не спрашиваются. Тост лежит выше пикера и не перехватывает клики,
    отступ снизу растёт вместе с `--keyboard-offset` (подсказку видно
    и при поднятой клавиатуре), а через 3,5 с тост исчезает сам.
26. При открытии формы правки дата задачи, лежавшая в прошлом, подменяется
    сегодняшней: `formDate` сразу берётся `сегодня`, кнопка даты показывает
    «Сегодня», и о подмене говорит тост «Упс... ваша задача была в прошлом.
    Дата изменена на сегодня». Снимок `originalFormState` берётся уже от
    подменённого дня, поэтому галочка сохранения остаётся серой до первой
    правки — при открытии ничего не спрашивается.
27. День вкладки в прошлом форму не открывает: кнопка «＋» на нём погашена,
    и программный клик по ней `#task-sheet` не раскрывает. В прошлое задача
    не встаёт с этой стороны тоже.
28. Сохранение правки с подменённой датой переносом не считается: второй
    `confirm` не спрашивается, отметка «выполнено» сохраняется, ручной
    приоритет и время не трогаются. Лимит десяти на сегодня при этом
    проверяется — как у обычного переноса: если сегодня уже 10 невыполненных,
    сохранение даёт `alert` «На этот день уже 10 невыполненных задач»
    и не меняет ни дату, ни отметку, форма остаётся открытой.
29. «Очистить» в правке задачи с датой в прошлом возвращает сегодняшний день,
    а не прошлый.
30. После создания задачи из прошлого дня вкладки, правки старой задачи
    и «Очистить» в хранилище не остаётся задач с `date < сегодня` — кроме
    случая, когда выправление заблокировано лимитом десяти (критерий 28):
    тогда задача остаётся на прежнем прошлом дне.

## 11q. Вкладка «Молитвы» (2026-09-30, семнадцатая итерация)

Новая вкладка: времена пяти намазов и восхода для заданных
координат, приветственный экран первого запуска, экран настроек с мазхабом
и координатами. Вкладка живёт внутри «Каза-намазов» — отдельной вкладки
в таб-баре у неё нет, «Каза» остаётся подсвеченной. Без уведомлений, звуков
и напоминаний: экран говорит, когда намаз, и молчит в остальное время.

Точки в `index.html`:

- **Шапка `#qaza-view`** — добавлена кнопка `#prayer-btn` первой слева, заголовок
  ушёл вправо. Порядок в разметке: кнопка, заголовок, «← Назад».
- **Разметка** — `#prayer-view` (приветственный экран и экран времён) и
  `#prayer-settings-view`; строка `#settings-prayer` в `#settings-list` между
  «Редактировать привычки» и «Экспорт данных».
- **Расчёт** — `prayerTimes()` и его окружение: юлианский день, склонение Солнца
  и уравнение времени, часовой угол для высоты. Считается вручную, без библиотек.
- **Метод расчёта** — пятый аргумент `prayerTimes()` (`'dum-chr'` / `'astro'`),
  поле `method` в ключе, группа `#prayer-method` в настройках молитв и её
  `renderPrayerMethod()` / `markPrayerMethod()` / `onPrayerMethodChange()`.
- **Данные** — `loadPrayer()` / `savePrayer()` на ключе `youplanner.prayer`.
- **Синхронизация** — раздел `prayer` в `syncToCloud` и `applyCloudData`
  с тем же условием `hasData`, что у остальных.
- **Копия** — пятый раздел `prayer` в `buildBackup` / `parseBackup` /
  `applyBackup`, `BACKUP_VERSION` поднят с 2 до 3.
- **Переключение видов** — `'prayer'` и `'prayer-settings'` в `switchAppView`,
  подсветка вкладок через `tabView`.
- **Обновление** — `prayerTick()` раз в минуту плюс смена суток.

**Расчёт.** Метод ДУМ ЧР: Фаджр — 16° под горизонтом, Иша — 15°, восход и закат —
0,833° (рефракция и радиус диска). Часовой пояс задан числом `PRAYER_TZ = 3`,
летнего времени нет. Аср — по тени: `arccot(тень + tan|φ − δ|)`, где тень равна
1 у шафиитского мазхаба и 2 у ханафитского. Два прогона: первый берёт
приблизительные времена, второй уточняет по ним положение Солнца.
Никаких постоянных правок в минутах в расчёте нет: углы и тень дают времена
как есть.

Зухр из этого расчёта — истинный солнечный полдень, и он у метода ДУМ ЧР
не используется: ДУМ ЧР закрепляет Зухр на 12:30 круглый год. Поэтому у
расчёта два метода, и отличаются они **только Зухром**:

| Метод | Зухр | Ключ |
|---|---|---|
| ДУМ ЧР (по умолчанию) | 12:30 фиксированно, круглый год | `dum-chr` |
| Астрономический | истинный солнечный полдень | `astro` |

Проверка на 43.38639, 45.82889 (Петропавловская) для 30.09.2026:

| Время | ДУМ ЧР | Астрономический |
|---|---|---|
| Фаджр | 04:29 | 04:29 |
| Восход | 05:53 | 05:53 |
| Зухр | 12:30 | 11:47 |
| Аср (шафиитский) | 15:04 | 15:04 |
| Аср (ханафитский) | 15:52 | 15:52 |
| Магриб | 17:40 | 17:40 |
| Иша | 18:58 | 18:58 |

Сезонный разброс для тех же координат: 21.12 восход 07:26 и закат 16:23,
21.06 восход 04:16 и закат 19:41 — то есть расчёт живой, а не подогнанный
под одну дату.

**Сверка с эталоном.** Расчёт сверен с расписанием ДУМ ЧР для Петропавловской
(43.38639, 45.82889) на весь сентябрь 2026 — тридцать дней по шесть времён,
180 значений. Расхождение не больше **одной минуты** по всем временам и всем
дням; у Зухра ноль по определению. Таблица эталона целиком лежит
в `.scratch\prayer\check.js` (`ETALON_DUM`), там же допуск — одна минута.

Оговорка о границах проверки: сверен **только сентябрь 2026** — единственный
месяц, на который был эталон. Другие месяцы и другие координаты против
расписания ДУМ ЧР не сверялись, и совпадение в сентябре не доказывает
совпадения в них. Сезонные проверки набора (июнь против декабря) доказывают
лишь то, что расчёт живой, а не подогнанный: с эталоном они ничего
не сравнивают.

Сходимость не случайна и объясняет, почему правок в минутах больше нет:
эталон ДУМ ЧР и есть чистый астрономический расчёт с углами 16° / 15° и тенью
×1. Прежняя калибровка под расписание «1Муслим» (шафиитская тень 1,21, Фаджр
+10 мин, Восход −3, Магриб +4, Иша = Магриб + 89) уводила времена от ДУМ ЧР
на 10–17 минут — то есть чинила расхождение с чужим источником, а не с этим.
Поправки сняты (§13).

— **Пояс — константа, а не пояс устройства.** Времена намазов на телефоне
  в другом часовом поясе должны остаться временами того места, где человек
  живёт, а не того, где он сейчас оказался. Отсюда `PRAYER_TZ` и то, что и
  «сегодня», и «сейчас», и полночь считаются по UTC+3 через `prayerDateISO()`
  и `prayerMinutes()`, а не через методы `Date`, которые читают пояс машины.

— **Координат нет — это и есть первый запуск.** Отдельного флага «показывали
  ли приветствие» не заводится: состояние выводится из ключа `youplanner.prayer`.
  Два состояния не могут разойтись, а повторный вход на вкладку после сброса
  координат снова показывает приветствие — что и требуется.

— **Свёрнутый список показывает не «текущий и следующий», а «следующий
  и после следующего»**, как в приложениях, к которым привык автор задачи.
  Окно намаза — исключение: когда намаз идёт, первым показывается он, вторым —
  следующий. Отсюда `PRAYER_WINDOWS`: у Фаджра окно до восхода, у Зухра до Асра
  и так далее. Восход окна не имеет — это не намаз, а граница утреннего,
  и текущим он не становится никогда.

— **Иша не тянется через полночь.** Формально её время продолжается до Фаджра,
  но её продолжение после 00:00 принадлежит уже другому дню, а строка «Иша 18:58»
  в час ночи читалась бы как время в будущем. Поэтому окно Иши — `[isha, 1440)`,
  а между полуночью и Фаджром текущего намаза нет, и список показывает
  «Фаджр и Восход».

— **Следующее событие может быть завтрашним.** После Иши наступает завтрашний
  Фаджр, и круг обязан его показать. Завтрашние времена считаются тем же
  `prayerTimes()` на завтрашнюю дату, а их минуты идут со сдвигом на сутки —
  так счётчик и кольцо считаются вычитанием, без отдельной ветки. Подсказка
  «завтра» в круге отличает этот случай от обычного: без неё «Фаджр 04:26»
  в 23:00 читался бы как прошедший.

— **Недостижимое время — `null`, а не выдуманное число.** За полярным кругом

## 11t. Старые привычки возвращаются при обновлении (2026-10-02, разбор)

Симптом: автор заливает новый `index.html` на GitHub Pages, обновляет PWA
на iPhone — возвращаются привычки, удалённые в первых версиях.

### Что проверено

- Залитая версия совпадает с локальной: `dazaev222.github.io/youplanner/index.html`
  байт в байт равна локальному `index.html`.
- Узел `habits` боевого сервера: пять привычек (`h6`, `h7`, `h8` с `time: 21:20`,
  `h10`, `h11`). Удалённых `h1`–`h5` и `h9` там нет, `updatedAt` — сегодняшний.
- В `records` следа удалённых привычек тоже нет.
- `/backups` — `null`: история снимков пуста. Код её только пишет и никогда
  не читает, восстанавливать из неё нечего.
- Других узлов в базе нет.
- В коде `DEFAULT_HABITS` читается ровно в одном месте — `loadHabits()`, и только
  когда ключа нет, JSON битый или это не массив. Подмешивания дефолтов
  к существующему списку нет нигде. Стирать `localStorage` приложение не умеет:
  ни `removeItem`, ни `clear` в файле не вызываются.

### Источник

**`DEFAULT_HABITS` в коде, а сервер только переносчик.** В дефолтах лежат
все шесть удалённых привычек — на момент разбора в списке было одиннадцать,
с §11s двенадцать.

Механизм, воспроизведённый на снимке боевого сервера (число дефолтов
в таблице — как на момент разбора; с §11s их на один больше):

| Сценарий | Привычки у страницы | `PUT` наверх |
|---|---|---|
| Хранилище пусто, сверка успела, правок нет | пять серверных | нет |
| Сверка идёт 2.5 с, человек успел тапнуть | одиннадцать дефолтов | **одиннадцать дефолтов** |
| Первая сверка упала, человек тапнул | одиннадцать дефолтов | **одиннадцать дефолтов** |

При пустом хранилище `loadHabits()` пишет дефолты. Дальше `cloudSnapshotWins`
серверный снимок не пускает — либо потому что первая сверка ещё идёт и тап
взвёл `syncPending`, либо потому что сверка упала. Правка человека ставит
отложенный `PUT`, а `syncToCloud` кладёт узел целиком: на сервер уезжают
дефолты, и их забирают все устройства. Первый сценарий объясняет,
почему симптом плавающий: при живом сервере всё чинится само.

Чего разбор не объясняет — почему `youplanner.habits` оказался пуст именно
в тот раз. Это единственный вход в сценарий; проверять надо на устройстве,
где привычки пропали (у `file://` своё хранилище, и оно стартует пустым).

### Решение (2026-10-02)

Дефолты перестали быть значением по умолчанию для пустого хранилища.
`loadHabits` отдаёт `[]` и не пишет ничего; запись перенесена в
`settleHabitsAfterSync`, который зовётся по итогу сверки — из `init` и из
ручной кнопки «Обновить с сервера» в Настройках. Без второго вызова
приложение, стартовавшее без сети, после ручной сверки осталось бы с пустой
таблицей и без пометки: `cloudReachable` уже взведён, а данных нет.

| Итог сверки | Что делает приложение |
|---|---|
| Сервер не ответил (бросок или отказ) | Ничего не пишет. Таблица пустая, `#habits-note` говорит «не загружены». Следующая сверка подтянет серверное |
| Сервер ответил, узел пуст | Пишет `DEFAULT_HABITS` через `saveNormalized` и отправляет их одним `PUT` |
| Сервер ответил, привычки есть | Применяет серверный список; дефолты не нужны |

`saveNormalized` здесь не украшение: запись идёт до `cloudReady = true`,
поэтому `scheduleSync` не взводит `syncPending` (правки человека нет) и не
ставит таймер, а отправку забирает сам `init` — узел пуст, PUT и так уходит.
Миграция `h12` переехала туда же, за сверку: до ответа сервера список ещё
может приехать с сервера.

Отдельно закрыт обратный ход той же ошибки. Пустое хранилище — это «не знаем»,
и PUT, кладущий узел целиком, стёр бы серверные привычки, которых устройство
просто не видело. Поэтому при отвергнутом снимке `syncFromCloud` забирает
серверные привычки, если своих нет вовсе (правка, которой сервер не видел,
привычек не касалась — править было нечего), а `syncBody` подставляет
серверный список в тело `PUT`, пока сверка ни разу не дошла до сервера.
Не проверено — §13.

Воспроизведение живёт в `.scratch/habits-edit/diag-defaults.js`
(`NODE_PATH="<кэш npx>/node_modules" node diag-defaults.js`). Наборы проверок
его не касаются: он ничего не проверяет, а печатает три сценария — что лежит
у страницы и что уходит наверх. После правки он показывает то, что нужно:
в первом сценарии применён серверный список и наверх не ушло ничего, во втором
наверх ушёл серверный список, а не дефолты, в третьем на странице пусто.

## 11v. Перерисовка после отклонённого снимка (2026-10-03, аудит)

**Что было.** `syncFromCloud` отвергает серверный снимок, если тот старше
локальной метки времени или спорит с правкой, которой сервер ещё не видел
(`cloudSnapshotWins`). У этой ветки есть один выход для привычек: если своих
привычек у устройства нет вовсе, серверный список всё же забирается в
`localStorage` — иначе пустой список уехал бы наверх и стёр серверный. Запись
в хранилище была, а перерисовки после неё не было: `appState.habits` оставался
прежним, и таблица, карточки дня и пометка «Привычки не загружены» показывали
старое состояние. Ветку применённого снимка это не задевало: там данные
приводит `applyCloudData`, и экран она перерисовывает сама.

**Что стало.** После того как отклонённый снимок отдал серверные привычки
в `localStorage`, экран перерисовывается тем же путём, что и при применённом
снимке: `appState.habits` перечитывается через `loadHabits`, затем идут
`renderMainView`, `renderQazaView`, `renderTasksView`, `renderPrayerView` —
тот же набор, что и в `applyCloudData`. Сверх этого не добавлено ничего;
поведение ветки применённого снимка и остальных вызовов `syncFromCloud`
(`init`, кнопка «Обновить с сервера») не менялось.

**Где правилось.** `index.html`, функция `syncFromCloud`, ветка
`!cloudSnapshotWins`. Пометка `#habits-note` снимается тем же вызовом: список
стал непустым, а `cloudReachable` уже взведён ответом сервера.

**Проверки.** Набор `.scratch/sync/check.js`: пустое хранилище и снимок, который
проигрывает по времени; серверные привычки легли в `localStorage`; таблица
показывает тот же список; пометка снята; дефолты наверх не ушли; консоль без
ошибок.

## 11w. Приоритет в снимке галочки сохранения (2026-10-03, аудит)

**Что было.** Галочка сохранения в панели формы (`#task-sheet-save-inline`)
сравнивала с состоянием на момент открытия только текст, время и дату;
приоритет в сравнение не входил. Смена одного приоритета через меню правкой
не считалась: галочка оставалась серой, и сохранить такую правку можно было
лишь строкой «Сохранить» в меню «⋯». Ограничение было записано в §13.

**Что стало.** Снимок `originalFormState` несёт ещё пару
`{ priority, manualPriority }`, и галочка сравнивает её наравне с текстом,
временем и датой: смена приоритета галочку зажигает, возврат к прежнему —
гасит. Выбор приоритета, который был в форме при открытии, ручным выбором
не считается: пара возвращается к снимку, поэтому «потыкал и вернул» галочку
не зажигает, а меню, открытое и закрытое без выбора, не меняет ничего
(§11.4б, 11). Правку текста ручной выбор по-прежнему не сбрасывает (§5).
`saveTaskFromSheet` не менялся: он и раньше сохранял приоритет правильно —
дело было только в активности галочки.

**Где правилось.** `index.html`: `openTaskSheet` (снимок берётся с формы уже
после выбора приоритета), `updateTaskSaveInline` (пара в сравнении),
`onPriorityPick` (возврат к прежнему приоритету обнуляет ручной выбор и
пересчитывает галочку).

**Проверки.** Набор `.scratch/tasks/check.js`: неизменённая задача — галочка
серая; меню, закрытое без выбора, её не зажигает; `low → high` — активна;
`high → low` — снова серая; сохранение галочкой пишет `priority: 'high'`,
`manualPriority: true` и красит флаг строки в `is-high`; правка текста у задачи
с ручным приоритетом его сохраняет.

**Документация.** Описание снимка в §5 (`youplanner.tasks`) приведено
в согласие с кодом: `{ text, time, date, priority, manualPriority }`, у новой
задачи — дефолтная пара после `openTaskSheet`. Расхождения между §5 и этой
записью нет.

## 11x. Раздел «Ураза» (2026-10-05, двадцатая итерация)

Учёт каза-постов отдельным счётчиком. Отмены у раздела нет, но история
пишется: следующим заходом появится раздел «Статистика» — новый экран
приложения, который соберёт данные по всем разделам, включая уразу, —
и будет читать эту историю.

### Решения по развилкам

Зафиксированы с автором задачи до написания кода.

| Вопрос | Решение |
|--------|---------|
| Отдельная отмена | Нет. Ошибки ввода исправляются вручную через «Изменить счётчик» |
| `history` и интерфейс | Пишется всегда, читает её только будущий раздел «Статистика»; UI в историю не смотрит |
| Форма `history` | Растущий массив, не стек. По датам не чистится, размер ограничен архивацией (js/data/archive.js): детально — последний год, старше — месячные своды |
| Дневная цель | Нет. Плана на сегодня тоже нет |
| Начальное значение | Только через первый запуск. Дефолта нет |
| `remaining: 0` | Обычное состояние: «Возместить» гаснет, «Добавить» и «Изменить» работают |
| «Изменить счётчик» | Перезапись, а не добавление |
| Ключ | `youplanner.qaza.fast` — новый |
| Связь с каза-намазами | Счётчики независимы: у уразы свой ключ, своя история, своя форма |
| Одновременная правка с двух устройств | Общее ограничение проекта («кто позже, тот прав»), §13 |

Три уточнения, которых в задании не было и которые выбраны по ходу:

1. **`buildBackup` не пишет раздел `fast`, если счётчика нет** — а не пишет
   `fast: null`. `null` сломал бы правило разбора «`fast` не объект — отказ»
   и собственная копия устройства без счётчика не импортировалась бы.
2. **Дата записи истории — календарный день** (`toISODate(new Date())`),
   без правила «день каза до Фаджра»: возмещение поста — запись о действии,
   а не намаз, привязанный к границе дня очереди.
3. **Образец набора проверок — `.scratch/prayer/check.js`**. Каталога
   `.scratch/qaza` в проекте нет: проверки вкладки каза живут в наборе prayer,
   вместе с ней и появившиеся (§11q).

### Что было и что стало

Было: счётчик каза-постов в приложении отсутствовал — был только счётчик
каза-намазов (`youplanner.qaza`) со своей очередью и отменой.

Стало: раздел «Ураза» открывается кнопкой `#fast-btn` из шапки вкладки каза.
Первый запуск показывает форму ввода, дальше — обычный экран со строкой
«Ураза: осталось N дней» и тремя кнопками. Каждый действие пишет событие
в историю, но ни одно её не читает.

Хранилище:

```js
{
  version: 1,
  remaining: 15,
  history: [
    { date: '2026-10-05', count: 15, source: 'set' },
    { date: '2026-10-06', count: 1,  source: 'done' },
    { date: '2026-10-07', count: 3,  source: 'add' }

}
```

`remaining` не может уйти в минус: `markFastDone` не работает при нуле,
а `saveFast` ещё раз приводит значение к `Math.max(0, Math.floor(…))`.

### Валидация

`parseFastInput(text, mode)` принимает только целое. Отклоняются пустое,
дробное (`1.5`, `1,5`), отрицательное, нечисловое (`abc`, `12шт`),
больше `FAST_MAX_INPUT = 100000`, а в режиме `'add'` — ещё и ноль.
При отказе форма остаётся открытой, под полем появляется сообщение,
в `remaining` и историю не пишется ничего. Поле — `type="text"` с
`inputmode="numeric"`: цифровая клавиатура на телефоне без браузерной
валидации, которая молча съедала бы часть случаев.

### Период

Пять независимых периодов: хаб, каза, привычки, ураза, сон. У каждого
экрана свой выбор. Хаб: `#stats-period`. Каза: `#stats-qaza-period`.
Привычки: `#stats-habits-period` и `#stats-habit-period` (одна категория,
два экрана). Ураза: `#stats-fast-period`. Сон: `#stats-sleep-period`.
Выбор хранится в `youplanner.stats.period` как объект.

Дни считаются существующими `toISODate`, `addDays` и `getWeekStart`,
по сегодня включительно:

| Период | Откуда |
|--------|--------|
| Неделя | понедельник текущей недели (`getWeekStart`) |
| Месяц | 1-е число текущего месяца |
| Год | 1 января текущего года |
| Всё время | сегодня − 364 дня, то есть ровно 365 дней включая сегодня |

«Всё время» — окно, а не «от первой записи»: одна старая запись растянула бы
график на годы пустых дней.

### Почему каза считаются по `h6` и по журналу, а не по `history`

`qaza.history` живёт только за сегодня — `loadQaza()` отбрасывает из неё
записи других дней, потому что стек нужен лишь для отмены (§5). За период он
не годится и теперь. Источников два, и границу между ними задаёт `since`
журнала `youplanner.qaza.log` (§5, выше):

- **до `since`** — поле `h6` в `youplanner.records` (§5, §8), единственный
  свидетель тех дней: журнал тогда не вёлся, и задним числом его не собрать;
- **с `since` и позже** — записи журнала со `source: 'done'`.

Журнала нет вовсе — работает только `h6`, по всем датам периода: пока журнал
не заведён, раздел считает ровно как раньше. Ручное добавление пропуска
(`source: 'manual'`) в счёт выполнений не входит ни в одном из источников:
в `h6` оно не попадает, а из журнала отбирается по `source` — намаз не выполнен,
а вспомнен, и в статистику выполнения он не входит, как и в прогресс-круг.

Зачем журнал вообще: окно «Всё время» — 365 дней, а `h6` пишет только вкладка
очереди и только о текущем дне. Журнал же не чистится по датам и хранит день
выполнения так, как он был записан тогда, — но и он заводится не задним числом,
поэтому первая его запись и служит границей `since`.

### Что показывает категория «Каза-намазы»

- **Выполнено за период** — по дням до `since` сумма `h6`, с `since` и позже —
  записи журнала со `source: 'done'` (§5). Журнала нет — `h6` по всем датам,
  как раньше.
- **Средний темп** — выполнено, делённое на число дней периода.
- **Текущая серия** — сколько дней подряд по сегодня включительно есть хотя бы
  один каза. Считается назад от сегодня и периода не касается: серия —
  свойство сегодняшнего дня, а не выбранного окна. Источник у неё один —
  поле `h6`: журнал в серию не смотрит (§11, п. 37).
- **Общий остаток** — `qazaTotalRemaining(qazaState)`.
- **График по дням** — столбики, высота = сколько каза за день. День без каза
  столбика не даёт; все нули — график пуст.

### Что показывает категория «Привычки»

Список — та же цифра, что и в хабе, но по каждой привычке отдельно:
`calcProgress(habit, dates)`, округлённый, со знаком «%». Привычек нет —
список пуст, а цифра хаба остаётся «—». Записей нет — «0%»: пустой день
у `calcProgress` и так ноль, поэтому отдельной ветки у списка нет.

Карточка — по одной привычке:

- **Средний процент за период** — тот же `calcProgress(habit, dates)`.
- **Текущая серия** — сколько дней подряд по сегодня включительно есть
  отметка. Как у каза, считается назад от сегодня и периода не касается.
- **Лучшая серия за период** — самый длинный ряд подряд идущих отмеченных
  дней внутри выбранного окна.
- **Всего отметок за период** — число дней периода с отметкой.
- **График по дням** — столбики, высота = `calcProgress` за один день.
- **Сетка-календарь** — клетка на каждый день периода: колонка неделя,
  строка день недели. Закрашен день с весом больше нуля, пуст — с нулевым.

**Отметка — это вес больше нуля.** Критерий один для всех типов привычек
и для всех трёх мест сразу: серий, счётчика отметок и сетки. Считается через
`calcProgress(habit, [день]) > 0`, чтобы вес дня читался ровно так же, как
прогресс в кругах таблицы: у boolean это `true`, у choice — «да» и «частично»
(вес 1 и 0,5), у числовых — непустое поле. У записи с нулевым весом —
`false`, «нет», «Отдых», ноль страниц — день не закрашен и серию не держит:
в прогресс-кругах «Отдых» серию не рвёт, но в статистике привычек критерий
один и задан весом, а не типом записи.

### Что показывала категория «Задачи» — снято 2026-10-14

*История: категория и `renderStatsTasksView()` удалены вместе с разделом «Задачи».*

Источник — `loadTasks()`, список читается из хранилища, как в хабе. У задачи
два разных дня, и путать их нельзя: `createdAt` — когда задача заведена,
`date` — на какой день она поставлена.

- **Создано за период** — задачи, у которых день `createdAt` попал в период.
- **Выполнено за период** — задачи с `done === true`, у которых в период попал
  день срока `date`. Задача, созданная в прошлом месяце и закрытая сегодня,
  в «создано» не появится, а в «выполнено» — да.
- **Просрочено за период** — задачи, созданные в периоде, со сроком раньше
  сегодняшнего дня и без отметки. Правило задано периодом создания, а не срока:
  иначе список просроченного не отвечал бы на вопрос «что я за этот месяц
  не сделал».
- **Приоритеты** — «N высоких / M обычных» среди задач, созданных в периоде.
  Обычная — всё, что не «высокий»: у задачи два приоритета, `high` и `low`.
- **График по дням** — столбики, высота = сколько задач выполнено в этот день
  срока. День без отметок столбика не даёт; все нули — график пуст.

### Что показывает категория «Ураза»

Источник — `loadFast()` и его растущая история событий, которая копилась
с §11x ровно под этот экран.

- **Остаток** — `fast.remaining`.
- **Возмещено за период** — сумма `count` у событий с `source === 'done'`
  и датой внутри периода.
- **Добавлено за период** — то же у событий с `source === 'add'`.
- **История копится с** — минимальная дата по всей истории, а не по периоду:
  начало истории не должно меняться от выбранного окна. История пуста — «—».
- **График по дням** — столбики, высота = сколько постов возмещено в этот
  день. События `'add'` и `'set'` в график не входят: он про возмещение.

**Два пустых состояния, и они разные.** Счётчика нет вовсе (`loadFast()`
вернул `null`) — вместо цифр и графика строка «Счётчик не заведён»: показать
ноль было бы ложью, ноль здесь значимое значение (§5). Счётчик есть, но
в истории меньше пяти событий за всё время — цифры показаны, а вместо графика
одна строка «История копится с <дата>. Данных пока мало для графика»: три
столбика на всю ширину карточки читались бы как «данных достаточно».
Порог задан константой `FAST_HISTORY_MIN = 5`.

## 11z. Панель навигации статистики: гамбургер (2026-10-05, двадцать четвёртая итерация)

Итог после снятия `stats-tasks` 2026-10-14: шесть пунктов панели — общая
статистика, четыре категории (каза, сон, ураза, привычки) и «Цикл сна».
Маршрута `stats-tasks` больше нет. Описания ниже сохраняют историю внедрения;
исторические таблицы §11z не переписаны.

Вход в раздел переехал в шапку главной — но только на телефоне. На ПК
панели нет вовсе, и там вход остался прежним, строкой в Настройках.

### Решения по развилкам

- **Панель на классе, а не на атрибуте `hidden`.** Задание описывало
  `#stats-menu` и как обёртку `.sheet` с `hidden`, и как выезжающую панель
  с `transform`. Совместить нельзя: переход через `display: none`
  не играется, и «выезд» существовал бы только в правилах. Выбран класс
  `is-open`: панель — сам `#stats-menu`, подложка — отдельный сиблинг
  с `hidden`. Плата — расхождение с буквой задания, поэтому раздел §7
  описывает разметку по факту.
- **Строка в Настройках гасится, а не удаляется.** На ПК это единственный
  вход в раздел: удалив строку, мы оставили бы шесть экранов статистики
  недостижимыми на большой вёрстке. На телефоне строка погашена
  медиа-запросом, и вход там ровно один — гамбургер. Побочная выгода:
  разметка `#settings-list` не изменилась, и порядок строк, который держит
  набор `export-import`, остался тем же.
- **Возврат «Назад» запоминается, а не задаётся.** «Всегда на главную»
  сломало бы ПК, где вход остался в Настройках; «всегда в Настройки» —
  телефон. Вход запоминается в `statsReturnView` на первом входе в раздел.

### Что было и что стало

### В2 (критичная). Снимок уразы без числа больше не затирает счётчик

`applyCloudData` применял раздел `fast` по `hasData(data.fast)` — то есть
по одному наличию ключей. Снимок вида `{remaining: "15"}` или `{junk: 1}`
эту проверку проходил: объект есть, ключи есть, числа нет. В счётчик
писалась строка или `undefined`, `undefined` исчезал при `JSON.stringify`,
и следующий `loadFast()` возвращал `null` — единственный признак первого
запуска (§11x). Экран уразы показывал форму первого запуска: остаток
и история терялись.

Исправлено добавлением в условие применения проверки
`Number.isFinite(data.fast.remaining) && data.fast.remaining >= 0`. Раздел,
её не прошедший, не применяется вовсе — локальный счётчик остаётся
нетронутым (уровень защиты 1, §2a). Условие
`hasData(data.fast) || !hasData(local.fast)` не менялось: ноль счётчиком
быть не перестаёт, а `null` с сервера по-прежнему не затирает заведённый
счётчик на этом устройстве. `loadFast`, `saveFast` и `parseBackup` не
тронуты — там проверки уже были, `hasData` тоже. Проверка одна,
в наборе `sync`.

### В1 (средняя). Окно ±60 минут считается через полночь

`habitLevelByTime` считала окно линейно: `Math.abs(minutes - plan)`.
`habitMarkDate` то же окно считает через полночь. При `time = '23:30'`
и отметке в 00:15 вторая уже кладёт отметку во вчера (расстояние «через
полночь» — 45 минут), а первая возвращала `'late'`: `|15 − 1410| = 1395`.
Две функции одного правила расходились в оценке одного окна.

Исправлено: расстояние считается по меньшей из двух дуг — прямой и через
полночь:

```js
const forward = Math.abs(minutes - plan);
const around = 1440 - forward;
const distance = Math.min(forward, around);
```

При `time = '23:30'` отметка в 00:15 — «вовремя», в 00:45 — «поздно»;
00:30 (ровно 60 минут через полночь) — ещё «вовремя», 00:31 — «поздно».
`habitMarkDate` не менялась: она работает правильно. Проверок шесть,
в наборе `habits-edit`.

### Что было и что стало

Было: раздела не было. Приложение показывало времена намазов, очередь каза
и счётчик уразы, но о сне не знало ничего.

Стало: с главной (телефон) или из Настроек (ПК) открывается экран
`#sleep-view` — карточка того же образца, что каза и ураза. В нём три поля:
время отхода, минуты засыпания и желаемое время подъёма. Итог считается
на каждой правке поля и сразу же пишется в хранилище.

### Формат ключа

```js
{ version: 3, bed: '23:30', fall: 20, wake: '07:00',
  actualWake: '07:00', sleepMin: 430, history: [] }
```

Поля и правила чтения — §5. Коротко: `bed` и `wake` — `'HH:MM'` 24-часового
вида, `fall` — целое 0…120, где ноль значимое значение, а не пустое; пара
`actualWake`/`sleepMin` — время, которое ушло в историю, и длительность сна;
`history` — растущий массив записей по дням. Битый ключ читается как `null`,
а `null` и есть первый запуск.

### История

Запись дня — шесть тех же полей плюс `date`. Дневник ведёт `saveSleep`,
и **прежнюю историю он берёт из хранилища, а не из аргумента**: вызывающему
о ней знать нечего, а передача её снаружи означала бы, что любой вызов
без неё стирает дневник. Читает он её тем же `loadSleep()` — в дневник
копится только прошедшее проверку.

День ищется проходом по полю `date` и перезаписывается на месте:
`saveSleep` вызывается на каждую правку поля, и без этого одна правка формы
оставляла бы в дневнике десяток записей об одном дне. Отдельного ключа
с датой нет намеренно — его пришлось бы гасить при импорте копии, и он
разошёлся бы с содержимым истории.

Дата — день сохранения формы (`toISODate(new Date())`, локальными
компонентами): раздел заполняют перед сном, и другой даты у записи нет.
Заполнение в 01:30 уходит на следующие сутки — принято сознательно.

Чтение истории **чистит, а не отклоняет** (образец — `validFastHistory`):
битый элемент отбрасывается молча, а не роняет запись. Три опоры расчёта
важнее дневника — то же правило, что у уразы, где счётчик важнее истории.
Проверка каждого поля — в §5. `sleepMin` сверяется с `sleepDurationMinutes`:
битая пара роняет запись и при чтении ключа, и в истории ей не место.

Растёт массив без предела и по датам не чистится: он нужен целиком экрану
статистики сна. Десять лет — около 3650 записей и 300 КБ.

**Режим подъёма — галочка, и она не хранится.** На экране под тремя полями
стоит четвёртый элемент: `#sleep-follow-rec`, «Встану по рекомендации,
а не в своё время». Снята — в историю уходит время из поля подъёма (`wake`),
отмечена — ближайший конец цикла. Отдельного поля у галочки нет: в ключе
`youplanner.sleep` она не лежит и в синхронизацию не ходит, при открытии
экрана восстанавливается сравнением `actualWake !== wake` (§5). Это та же
логика, что у периода статистики: отметка устройства, а не данные человека.

**Крупный будильник и время для истории могут не совпадать.** Крупным идёт
первый элемент `recommended` — более ранний из двух концов цикла. В историю же
идёт то, что даёт галочка: своё время (снята) или ближайший конец цикла
(отмечена). Будильник 07:00 при отходе 23:30 и засыпании 20 минут даёт
`recommended = [05:50, 07:20]`, крупным показан 05:50; снятая галочка запишет
в историю 07:00, отмеченная — 07:20. Так и задумано: крупная цифра —
рекомендация, история хранит то, что человек выбрал. На экране это видно
двумя строками — `.sleep-actual` («В историю: 07:00 (по цели)»)
и `.sleep-duration` («Сон: 7 ч 10 мин»).

**Фактический подъём и исключение из статистики.** Галочка `#sleep-on-plan`
(«встал по плану») стоит под галочкой рекомендации. Отмечена — фактический
подъём равен плану, `realWake = null`, в историю идёт `actualWake`. Снята —
поле `#sleep-real-wake` обязательно: пока оно пустое, запись в хранилище
не идёт (`ready = false`). Заполненное поле даёт `realWake` и `realSleepMin`,
которые в истории заменяют `actualWake` и `sleepMin` в статистике. Галочка
`#sleep-excluded` («исключить день из статистики») при отметке исключает
запись из средних, графика и счётчика в разделе «Статистика → Сон».

### Расчёт

`sleepAnchors(bed, fall, wake)` ставит три момента на одну шкалу в минутах
от полуночи. Если будильник раньше отхода, к нему прибавляются сутки:
сравнивается он именно с отходом, а не с засыпанием, — «встать раньше, чем
лёг» и «встать раньше, чем заснул» разные вещи, и первое и есть смена суток.

`sleepCycleTimes` отсчитывает от засыпания (`bed + fall`) концы циклов через
каждые 90 минут и ищет среди них соседей будильника:

- будильник ровно на конце цикла — вариант один;
- между двумя циклами — вариантов два: тот, что раньше, и тот, что позже;
- раньше первого или позже последнего — соседа с одной стороны нет,
  и остаётся один, ближайший.

Пример из задачи: лёг 23:30, засыпал 20 минут, встать в 07:00. Засыпание
23:50, концы циклов 01:20, 02:50, 04:20, 05:50, 07:20, 08:50; 07:00 попадает
между 05:50 (четыре цикла) и 07:20 (пять) — рекомендуются оба.

### Поведение при двух вариантах

Крупным идёт первый элемент `recommended` — более ранний. Подсвечены в списке
оба: решает человек, а не расчёт. Пояснение под будильником называет число
циклов и длительность сна, а при двух вариантах — ещё и оба времени:
«4 цикла, 6 ч · встать раньше — 05:50, встать позже — 07:20». При точном
попадании второй половины фразы нет вовсе.

### Строка в Настройках

`#settings-sleep` стоит в `#settings-list` между «Молитвы» и «Экспорт данных».
На ПК это единственный вход в раздел. На телефоне она погашена медиа-запросом
— как `#settings-stats` (§9), — но из разметки не удалена: порядок строк
списка держит набор `export-import`.

### Синхронизация и копия

Раздел восьмой в теле `PUT` и восьмой в `applyCloudData` — после `fast`.
Условие применения общее: объект, не массив и `hasData(data.sleep) ||
!hasData(local.sleep)`. Пустой раздел с сервера не затирает заведённую
запись: это след неполного снимка, а не удаление (уровень защиты 1, §2a).

История едет вместе с разделом `sleep`, а не отдельно от него: у снимка
с одной датой записи быть не может, и отсутствие поля — признак неполноты,
а не истории без записей.

В файле копии раздел **необязателен** и пишется только при заведённой записи:
`null` сломал бы правило разбора «`sleep` не объект — отказ», и собственная
копия устройства без записи не импортировалась бы. `BACKUP_VERSION` поднят
с 6 до 7 в заходе 1 и с 7 до 8 в заходе 2 (§11.2). Время в файле проверяется
тем же `sleepTimeMinutes()`, что и ключ: своя регулярка вида «две цифры :
две цифры» пропускала бы `'25:00'`, файл разбирался бы, а следующий
`loadSleep()` возвращал `null` — и раздел показывал бы первый запуск
при живой записи. История в файле не массивом — отказ целиком: запись легла
бы в ключ, а следующий `loadSleep()` отбросил бы историю, и она бы молча
пропала. Битые элементы внутри массива разбор, наоборот, не роняют — их
отбрасывает `validSleepHistory`.

### Проверки

Набор `.scratch/sleep/check.js` — 122 проверки. Чистый расчёт (времена
и длительности циклов, точное попадание, попадание между двумя циклами,
засыпание ровно в полночь, будильник через полночь, будильник позже
последнего цикла, битые поля), хранилище с двух сторон — чтение засеянного
ключа без единого клика и запись правкой поля, синхронизация (тело `PUT`,
снимок с сервера, пустой раздел с сервера), копия (сборка, разбор, замена,
отказы) и сам экран на телефоне и на ПК: три поля из хранилища, крупный
будильник, пояснение, список циклов, полоска с засечками, пустое поле
и возврат «Назад» на обоих входах.

Числа набор считает сам: ожидания записаны в нём литералами, снятыми
с примера из задачи, а не вычитаны из DOM приложения. Сверяется результат
функций, а не то, что оказалось нарисовано. Единственное число, которое
набор берёт у машины, — сегодняшняя дата: пересказанная своими словами,
она сделала бы сравнение вечным.

**История проверяется отдельным блоком «И».** Чтение засеянной истории,
чистка по каждому полю, запись при правке формы, перезапись записи того же
дня, запись прошлого дня рядом с сегодняшней, отсутствие ключа, сохранение
без истории и передача её через хранилище. Отдельно проверяется, что
`saveSleep` берёт прежнюю историю из ключа, а не из аргумента: иначе вызов
без неё стирал бы дневник, и три существующие фикстуры набора это показывают.

**Сравнения хранилища идут через обёртку `core()`** — ядро записи без
`version` и `history`. Иначе повышение версии схемы краснило бы разом шесть
пунктов хранилища, и связка «мутант ↔ проверка» поехала бы: у пункта правки
поля своя забота — его поля, а не возраст ключа.

**Проверка отправки гасит очередь перед замером.** `saveSleep` ставит
отложенную отправку, но до него её ставит и импорт копии; без явного гашения
очереди мутант «нет `scheduleSync`» не отличился бы — чужой `PUT` сошёл бы
за отправку от `saveSleep`. Подробнее — §11z.

(прекэш SW, офлайн работает; CDN не используется). Пути строятся от
`document.baseURI` лениво — относительный спецификатор динамического import
резолвится от URL модуля, а import.meta несовместим с классическим скриптом
тестовой песочницы. Воркер same-origin, без blob-обёртки. Текст живёт
в переменной модуля (перезагрузка страницы сбрасывает), прикрепляется
к системному промпту каждого запроса, в историю не пишется. Лимиты:
200 страниц (`PDF_MAX_PAGES`), 50 000 символов (`PDF_MAX_CHARS`), обрезка
помечена «…[текст обрезан]». Пустой по тексту файл и не-PDF отвергаются
с тостом. Отправка на время разбора заблокирована (кнопка, Enter, чипы),
текст в поле не теряется; диагностика — `console.log '[assistant] PDF …'`.

**Каркас экрана.** Экран-колонка: при `body.view-assistant` каркас `#app`
сам становится flex-колонкой на `100dvh`, лента `#assistant-chat` —
единственный скроллируемый слой (`overscroll-behavior: contain`), шапка
и док закреплены. На телефоне глобальная шапка скрыта, запас дока —
`calc(84px + env(safe-area-inset-bottom))` над таб-баром, своя шапка
учитывает `safe-area-inset-top`. Парное `#assistant-view[hidden]{display:none}`
обязательно: `display:flex` контейнера иначе перебивает атрибут hidden.
Никаких констант вида `calc(100vh - Npx)`: высота мобильной шапки
переменная, константа уже уводила док под таб-бар (коммиты 83088bf → 68343b8).

**Дизайн.** Пузыри: пользователь — акцент `var(--accent)`, белый текст,
радиусы 16/16/4/16; ассистент — белая карточка `var(--surface-card)`,
мягкая тень, 16/16/16/4; серии односторонних реплик сжаты через `:has()`
(деградация — равные 10px). Композер — серая капсула `var(--surface-alt)`
с фокус-подсветкой всей капсулы, призрачная скрепка, круглая кнопка
отправки на акценте. Чипы — пилюли `var(--accent-soft)`. Тексты пузырей —
только `textContent` (XSS).

**Таймауты и ошибки.** 60 с (`REQUEST_TIMEOUT_MS`, ручной AbortController
при отсутствии `AbortSignal.timeout`). Ошибки 401/403/429/5xx/сети —
готовый текст в пузыре `is-error`, «Печатает…» гасится в `finally`,
401/403 поднимает модалку ключа. Повторяющиеся ошибочные тосты —
`showErrorToast` (дедупликация по тексту, продление таймера).

**Тесты (на момент захода).** `npm test` 34/34 (ассистент в песочнице не исполняется —
модуль UI). E2E Playwright в `.scratch/pdf-test/` (47 + 14 проверок):
гонка PDF, 401/429/500/обрыв, офлайн-разбор, поворот, быстрые переключения
вкладок, очистка localStorage, геометрия дока/таб-бара. Гамбургер
статистики — круглая Liquid Glass-кнопка 44×44 (blur 20px, saturate 180%,
внутренний блик), §11z.

## 11ae. Фон приложения (2026-10-25)

Пользовательское фото как фон всего приложения. Решения по ответам
владельца: на всё приложение, но модалки и экран Ассистента остаются
на плотном `var(--bg)`; источник — только фото с устройства; оригинал
не хранится (сжатие под экран, ≤ 800 КБ); настройка локальная, как
API-ключ — в Firebase и файлы копий не входит; затемнение — ползунок
с авто-базой по яркости фото; карточки плотно-белые; обрезка `cover`
без ручной позиции.

**Слои.** `#app-bg-layer` (фото, `background-size: cover; center`) и
`#app-bg-scrim` (`rgba(254,254,254, var(--bg-scrim-opacity, .8))`) —
`position: fixed; inset: 0; z-index: -1`, включаются классом
`body.has-app-bg`; без фото оба скрыты, чтобы скрим не серил обычный
фон. `background-attachment: fixed` не используется (лаги iOS Safari).

**Данные.** `js/core/db.js` — узкая обёртка IndexedDB (база `youplanner`,
store `prefs`, get/put/delete; без IDB тихо отрабатывает пустотой —
песочница тестов). `js/data/background.js`: `compressBgImage` —
`createImageBitmap(file, {imageOrientation:'from-image'})` → canvas
до длинной стороны экрана в физических пикселях (потолок 2048,
без апскейла) → WebP 0.8, при неподдержке/переборе — JPEG 0.7/0.55,
потолок 800 КБ; `autoDimForBitmap` — средняя luma по canvas 16×16,
скрим 55 + (1−luma)·40, кламп 55–95%. Blob — IDB-ключ
`app-background-image`; затемнение — `youplanner.app_bg` `{dim}`
в localStorage. Ключи в STORAGE_KEYS не входят сознательно.

**Применение.** app.js: `restoreAppBackground()` при init (Blob →
objectURL → `--app-bg-image`, `--bg-scrim-opacity`, класс body),
панель в Настройках (статус с размером, миниатюра, «Загрузить фото»,
«Сбросить фон» с confirm, ползунок 0–100: живая правка на input,
сохранение на change). Замена фона отзывает прежний objectURL.
Сброс чистит IDB и prefs.

**Тесты (на момент захода).** `npm test` 34/34; Playwright `.scratch/pdf-test/background.test.js`
17/17: слои до/после, Blob в IDB ≤ 800 КБ, авто-скрим темнее для тёмного
фото и светлее для светлого, восстановление после reload, живой ползунок,
полный сброс. Vision-аудит тёмного и светлого фото: контраст текста
оценён как ≥7:1 на карточках, ≥10:1 на скриме.
