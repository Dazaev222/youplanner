## 1. Критические баги (P0/P1)

### P0. Правила `auth != null` не привязаны к владельцу: любой аноним читает и затирает данные
`database.rules.json:1-6` (прочитано лично):
```json
{ "rules": { ".read": "auth != null", ".write": "auth != null" } }
```
Атака без взаимодействия с жертвой: Web API Key публичен (`js/data/firebase-auth.js:22`,
репо публичен — проба (c)), Anonymous-вход включён → один POST
`identitytoolkit…accounts:signUp` даёт чужому человеку свой idToken, и `auth != null`
для него истинно. `GET <узел>.json` — весь снимок: привычки, журнал сна и
**координаты молитвы lat/lng** (`js/sync/core.js:117-123` — домашняя геолокация);
`PUT` — затирание/отравление, которое `applyCloudData` честно применит в localStorage.
Косвенный вред без злого умысла: два незнакомых пользователя приложения делят один
узел и затирают друг друга — мультиарендность в архитектуре отсутствует.

**Как чинить (важно: предложенный субагентом переход на per-uid пути
`users/$uid` сломал бы мультидевайс — у каждого устройства СВОЯ анонимная
учётка, а путь данных зашит один).** Отсюда два честных варианта:

- **Рекомендуемый (0 строк кода):** захардкодить uid владельца в правилах —
  ```json
  { "rules": { ".read": "auth != null && auth.uid === 'OWNER_UID'",
               ".write": "auth != null && auth.uid === 'OWNER_UID'" } }
  ```
  где OWNER_UID — `sub` из idToken основного устройства. Все устройства должны
  делить одну анонимную учётку: один раз скопировать `youplanner.fb.refresh`
  из localStorage основного устройства во второе. Новое «само-онбординг»
  устройство перестанет работать — для личного приложения это приемлемо.
- **Стоп-кран (0 строк всего):** `{"rules": {".read": false, ".write": false}}`
  — синк честно деградирует в офлайн-режим (`js/sync/sync.js:50-54`),
  приложение продолжает работать локально.
- Долгосрочно (по желанию): App Check против автоматизации.

### P1-1. Удаление привычки не переживает второе устройство (доказано PoC)
`js/data/habits.js:234-251` (pruneResolvedTombstones) + `js/sync/sync.js:610` +
`js/sync/merge.js:81-117`. Prune стирает надгробие, когда «привычка есть в
локальном списке», но на устройстве B она «есть» именно потому, что B ещё не
видел удаление. Последовательность: B правит записи → A удаляет привычку и
PUT → B синхронится, merge приносит надгробие, но habit ещё в списке → prune
стирает надгробие → B PUT-ит привычку обратно → A воскресает привычку
(PoC на реальных модулях: «hX resurrected on A? true»). **Фикс:** не делать
prune после merge-пути (только после цельного applyCloudData), либо не стирать
чужие надгробия, пока их ts < последнего принятого sectionTs.habits.

### P1-2. Гонка PUT не закрыта: окно между контрольным GET и PUT
`js/sync/sync.js:427-451`. A GET(свежо) → B PUT → A PUT — данные B стёрты с
сервера. Коллекции (records/habits/sleep.history/qazaLog) самовосстанавливаются
аддитивным merge, но **цельные разделы — нет**: `cloudWins` по sectionTs
(`merge.js:364-375`) кладёт старую серверную копию qaza/prayer/fast/schedule
поверх локальной правки B. **Фикс:** conditional PUT через `If-Match`/ETag
(RTDB REST отдаёт ETag, 412 на промах) с повторным merge; после него
контрольный GET не нужен.

### P1-3. LWW по часам отправителя: разошедшиеся часы стабильно съедают правки
`js/sync/sync.js:514-524` (все sectionTs = `Date.now()` отправителя) +
`merge.js:361-363`. Устройство с часами +10 мин пишет «будущее»: правка
счётчика каза/уразы/расписания с другого устройства, сделанная позже по
реальному времени, проигрывает и перетирается. **Фикс (без смены
архитектуры):** счётчик каза уже дублируется аддитивным журналом qazaLog —
выводить remaining из него и убрать этот раздел из LWW; для остальных
цельных разделов — миграция значений в конверты `{v, ts}` (лениво, при записи).

### P1-4. CSP отсутствует, при этом в localStorage лежат оба секрета
`index.html` — мета Content-Security-Policy нет (GitHub Pages заголовки не
отдаёт → CSP нулевой); `youplanner.fb.refresh` (`firebase-auth.js:27,110`) и
`youplanner.api_key` (`assistant-view.js:57,770`) — одна будущая XSS крадёт
оба секрета одним `localStorage.getItem`. Текущие XSS-стоки чисты (см. «чисто»),
это defense-in-depth с высокой ценой пропуска. **Фикс:** мета CSP
(`default-src 'self'; connect-src 'self' https://*.firebaseio.com
https://identitytoolkit.googleapis.com https://securetoken.googleapis.com
https://api.neuraldeep.ru; …`).

## 2. Архитектурные дыры (хрупкость)

1. **Конфликт значений решается порядком PUT, а не временем правки**
   (`merge.js:160-171`: расхождение поля → всегда серверная сторона, без ts).
   Офлайн-правка позже по времени перетирается онлайн-правкой раньше.
   Фикс: конверт `{v, ts}` для значений дня (см. P1-3).
2. **Импорт бэкапа без лимита размера и без валидации ключей records**
   (`js/app.js:87-93` — readAsText всего файла; `backup.js:71` — JSON.parse
   гигабайта; `:83-84` — records проверен только «объект»): крафтовый файл
   кладёт `"__proto__"` в localStorage, дальше `Object.assign` в merge.js
   (`:137,159`) через `[[Set]]` — примитив порчи прототипа. Фикс: лимит
   `file.size` до чтения (5 МБ), records через `validCloudRecords`.
3. **Матрица Эйзенхауэра не попадает ни в синк (осознанно), ни в файловую
   копию (не осознанно)** — `buildBackup`/`applyBackup` раздел
   `youplanner.matrix.tasks` не знают: экспорт и переезд на телефон теряют
   все задачи молча (`js/data/matrix.js:9-12`, `backup.js:26-65,190-279`).
   Фикс: добавить раздел в бэкап (локальный без синка — это уже умеет архив).
4. **refresh/idToken в URL** (`?auth=`, `sync.js:55-65`) — виден в логах
   Firebase/прокси (TTL 1 ч смягчает). Фикс: `Authorization: Bearer` — RTDB
   REST поддерживает.
5. **dump-localstorage.html в корне публичного сайта** (`:76-80`): печатает
   ВСЕ ключи localStorage, не отличая секреты от данных. Не утечка наружу
   (печатает локальное), но приучает копировать ключи в «поддержку». Фикс:
   убрать из деплоя или дампить только data-ключи.
6. **Мелочи:** `flushPendingSync` без `keepalive` (`sync.js:723-728`) — хвостовая
   правка доезжает только восстановлением pending на следующем открытии;
   `sw.js:79-88` кладёт в кэш успешные .js/.css без проверки same-origin
   (сейчас кросс-доменных скриптов нет); README и `firebase-rules.e2e.mjs`
   называют backups «отдельным инстансом» — по коду (`core.js:22,27`) это
   соседний ПУТЬ того же инстанса, публикация правил одна на оба узла
   (владелец зря ищет второй инстанс в консоли).
7. **Осознанно принятое, зафиксировать:** полный снимок данных трекера уходит
   на api.neuraldeep.ru в каждый запрос ассистента — внести в README «Безопасность».

## 3. Оптимизация и читаемость

1. **Стоимость обмена: полное дерево × 5 запросов на одну отметку.**
   `sync.js:396-463` — GET данных + GET списка бэкапов + PUT списка + контрольный
   GET + PUT дерева; бэкап-узел переписывается целиком (до 10 снимков) на каждую
   отправку (`:638-669`). При дереве 150-300 КБ это 3-7 МБ трафика и 5 round-trip
   на одну галочку. Фикс: бэкап-снимок раз в N минут/правок; поключевой PUT;
   контрольный GET убрать после ETag (P1-2).
2. **`bindEvents` — 741 строка, ~120 слушателей всех экранов подряд**
   (`js/app.js:203-943`): главный тормоз читаемости и источник конфликтов
   слияния. Фикс: `bindXxxView()` рядом с каждой вьюхой + реестр
   «контейнер → обработчики».
3. **`applyCloudData` — 186 строк из десяти однотипных блоков** (`sync.js:129-233`):
   новый раздел = копипаста; расхождение с `mergeSectionKey` не ловится.
   Фикс: таблица дескрипторов `{key, valid, needsPendingGate}` + один цикл —
   заодно устранит дубль между applyCloudData и applyMergedFromCloud.
4. **Дубли:** склонение дней ×3 (`matrix-view.js:119`, `assistant-view.js:147`,
   `fast.js:143`); окно через полночь двумя формулами (`records.js:204-208,222-226`);
   гард таймаута ×3 (`sync.js:28-43`, `firebase-auth.js:63-78`,
   `assistant-media.js:69` — можно поднять в core). Фикс: одно правило — одно место.
5. **Контракт boolean нарушен в трёх `save*`:** `prayer.js:210-211`, `fast.js:65`,
   `sleep.js:393-401` на невалидном вводе `return;` → undefined вместо false.
   Живые вызовы проверяют фальшивость, но контракт надо держать буквально.
6. **Магические числа:** геометрия капли таб-бара `app.js:1399-1412`, 1440 минут
   в сутках без имени (`records.js:206-208,226`), потолок progressCache 1000
   (`records.js:395`), 700px дублирует медиа-запрос CSS (`ui/state.js:13`),
   86400000 (`matrix-view.js:131`). Остальные (SYNC_*, SLEEP_*, ARCHIVE_*) —
   образцовый порядок.
7. **Мёртвый гейт `tasks` в backup.js:87** — файлы v10 уже отвергаются версией;
   гейт срабатывает только на рукотворных v11 с tasks. Снять вместе с пометкой
   в `storage.js:10-12`, когда матрица получит бэкап (дыра 3).

**Доки vs код (docs/ARCHITECTURE.md от 2026-10-31):** `js/core/db.js` и
`js/core/debounce.js` не существуют — слиты в `core/storage.js:50-129` и
`core/dom.js:133-164`; `sync/state.js`+`validators.js` слиты в `sync/core.js`;
`assistant-vision.js`/`assistant-api.js` слиты в `assistant-media.js`;
«19 стилей» — фактически 22; кэш «v29» — фактически v39; «153/153 в 20 файлах» —
фактически 351 тест в 35 файлах. Док помечен как снимок, но примеры читаются
как живая структура — обновить.

**Проверено и чисто (важное):** XSS-стоков нет — в четырёх файлах ассистента
innerHTML не используется вовсе (реплики через textContent; DOMPurify не нужен);
`tests/xss.test.mjs` закрепляет экранирование; модель в payload валидируется
белым списком (`assistant-view.js:165-175`); ключ нейросети только в Bearer на
api.neuraldeep.ru, в URL/Firebase не утекает; records-кэш: все прямые записи
инвалидируют кэш, нарушителей нет; sw.js — 70/70 ASSETS совпадают с диском,
Firebase мимо кэша, не-GET не кэшируется; трёхфазные apply с откатом
(QuotaExceeded не оставляет смесь); рост хранилища ограничен (архив 12 месяцев,
tombstones ≤500, история ассистента ≤50); router без утечек state; таймеры и
обзерверы снимаются; single-flight сериализует обмены; миграция drop-tasks
безопасна для свежего устройства.
