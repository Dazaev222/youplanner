Корень всех путей и команд ниже: `youplanner-new/`. Воркер 1 — Qwen (Матрица), воркер 2 — GLM (Календарь/длительность). Роли допускается поменять без изменения контрактов.

## 0. Обязательные границы и исходные факты

1. Стек сохраняется: Vanilla JS, ES modules, PWA, локальное хранилище; без React, новых UI-фреймворков, backend и платных сервисов. Firebase, telegram-bridge, ключи и правила доступа не трогать.
2. Сейчас разрешено подготовить ТЗ, не реализовать его. Воркеры начинают реализацию при передаче им задания владельцем/оркестратором. Не запускать публикацию, push в GitHub или деплой по тексту этого файла.
3. Перед изменениями прочитать актуальные файлы и diff. Уже имеющиеся изменения в `js/ui/matrix-view.js` и `styles/matrix.css` сохранить. Номера строк ниже — навигация по прочитанному состоянию, не инструкции заменять диапазоны вслепую.
4. Матрица хранит задачи под `youplanner.matrix.tasks`; они НЕ входят в штатные backup и cloud sync. Не скрывать предупреждение об этом, не обещать резервирование и синхронизацию. Расширение backup/sync — отдельная работа.
5. Квадрант вычисляется `quadrantOf()` из `due` и `priority`. Порог срочности — два КАЛЕНДАРНЫХ дня включительно, не буквально 48 часов. Не добавлять сохраняемое поле `quadrant` как вторую истину.
6. Приложение уже имеет атомарную границу `commitTasks()`: успех интерфейса только после успешной записи. Сохранить откат и черновик при QuotaExceededError.
7. Никаких красных обводок/декоративных линий, недельной шапки, премиум-плашек. Сохранить выполнение, возврат в работу, перенос, архив и восстановление.
8. Напоминания — только локальные при открытом приложении. Скрытая вкладка/сон ОС могут задерживать JS; закрытая PWA не получает уведомления. Никаких обещаний фоновых push, разрешений Notification при запуске, серверного scheduler или обработчика push в service worker.
9. Не исправлять попутно весь проект. Архитектурные изменения допустимы только для завершения этих пользовательских потоков; посторонние проблемы записать в отчёт.

## 1. Как использовать ticktick-ui-skills

Прочитать `.agents/skills/ticktick-ui-skills/SKILL.md` до вёрстки. Файл присутствует и изучен архитектором; повторно устанавливать пакет не нужно. Stageshow в доступных скиллах не обнаружен: не утверждать, что он применён.

Использовать принципы: светлые поверхности, согласованная шкала отступов на базе 4 px, пилюли, safe area, `dvh`, заметный focus-visible, доступные названия и ошибки у поля, аккуратная иерархия. Никаких зависимостей от скилла в runtime.

Осознанные отступления: не переносить механически заголовок 51 px, основу 1920 px, бледный `#CACACA` на белом и все MUST из стороннего текста. Это не официальная спецификация мобильного TickTick и не описание его логики. Приоритет — стиль YouPlanner, WCAG AA и функциональные требования. Использовать существующие `--surface-alt`, `--surface-card`, `--text`, `--text-muted`, `--accent`, `--matrix-qN[-soft]`, `--radius-*`, `--shadow-card`. Не заменять глобальную палитру/шрифт; шрифт наследовать.

Источники для функциональной сверки:
- Task Details: https://help.ticktick.com/articles/7055782408586526720
- Set Up Recurring Tasks: https://help.ticktick.com/articles/7055782206349770752
- Effective Reminder Feature: https://help.ticktick.com/articles/7055782395743567872

Поисковые выдержки подтверждают Start/End в Duration, reminder At the end и завершение повторов по дате/числу раз. Полные страницы вернули HTML без читаемого текста; эталонных изображений TickTick сейчас нет. Поэтому ниже задан собственный точный контракт поведения, а не заявлена проверенная полная идентичность всем возможностям TickTick. При получении эталона сверить визуальные детали без молчаливого сокращения функций.

## А5. Нижний лист и контракт с Воркером 2

Реальный факт: `index.html #habit-modal/#habit-form` и `js/ui/habits-edit.js` создают ПРИВЫЧКУ; на phone это полноэкранная модалка. `level-sheet.js` отмечает выполнение привычки. Ни один из них не является общим API создания задачи. Не импортировать их бизнес-логику.

Переиспользовать visual-каркас `.sheet/.sheet-backdrop/.sheet-panel`, существующий composer и keyboard-offset; matrix-specific модификатор должен иметь корректный stacking выше таб-бара (1000) и detail (1010). Не менять поведение всех `.sheet`. Лист создания — единый для сетки и detail, с title/description/плашкой/сроком/приоритетом/submit, в стиле текущей формы. Calendar dialog — дочерний логический уровень над composer, не второй конкурирующий фокус-ловитель.

Зафиксировать узкий API (экспортировать только нужное тестам/приложению):
- `openTaskComposer({quadrantId, opener})`: валидирует id, берёт новый draft из `quadrantShape`, запоминает исходный view и фокус, не меняет экран из-за открытия.
- `requestCloseTaskComposer(reason)`: единые правила dirty/discard для кнопки, Escape/backdrop и навигации; синхронное/асинхронное решение явно согласовать с caller.
- `pickDraftQuadrant(id)`: изменяет намерение и shape, но не навигацию. При появлении интервала использует правила Б6, не обнуляет даты молча.
- `getDraftSchedule()` / `applyDraftSchedule(value)`: возвращают/принимают КОПИИ календарного объекта; только успешный «Готово» вызывает apply. До интеграции допускается адаптер к `due`, не зашивать будущую схему в DOM.
- `submitDraft()`: одна точка submit с защитой от повторного события; передаёт fields и обрабатывает save failure. Воркер 2 расширяет whitelist fields, не создаёт второй submit-handler.

Состояния разделить: view, composer, calendar draft/popover. Сейчас `closeSheet()` удаляет только первый найденный узел, а `renderMatrixView()` очищает весь host — это нельзя оставить для вложенного календаря. Закрытие календаря оставляет composer, закрытие composer убирает его дочерний календарь, перерисовка не теряет текст/фокус/позицию. На смене квадранта незавершённый текст не теряется; открытие другого «+» при dirty черновике требует явного решения, а не подмены черновика.

Dialog: role, aria-modal, aria-labelledby, initial focus, Tab/Shift+Tab trap только верхнего окна, Escape закрывает верхний уровень, inert/блокировка фоновых действий, возврат фокуса и scroll-lock с cleanup. `syncSheetToKeyboard()` уже вычисляет `--keyboard-offset`; учитывать visualViewport resize/scroll без накопления listeners. На desktop ограничить панель ~520 px, на phone ширина экрана, безопасный низ, доступная прокрутка при клавиатуре. Не убирать видимый focus.

## Б3. Контракт хранения — зафиксировать до UI

Использовать вложенный `schedule` (версия 1), а не пять несвязанных полей. Ниже схема, не готовая реализация:

```text
schedule: {
  version: 1,
  allDay: boolean,
  startDate: 'YYYY-MM-DD' | null,
  endDate: 'YYYY-MM-DD' | null,
  startTime: 'HH:mm' | null,
  endTime: 'HH:mm' | null,
  timeZoneMode: 'device',
  reminders: Array<{
    id: string,
    anchor: 'start' | 'end' | 'absolute',
    offsetMinutes: integer,
    time: 'HH:mm' | null,
    date: 'YYYY-MM-DD' | null
  }>,
  repeat: null | {
    basis: 'scheduled' | 'completion',
    unit: 'day' | 'week' | 'month' | 'year' | 'dates',
    interval: integer,
    weekdays: integer[],             // ISO: понедельник=1 ... воскресенье=7
    monthMode: 'dayOfMonth' | 'nthWeekday',
    nth: 1 | 2 | 3 | 4 | -1 | null, // -1 = последний такой день недели
    weekday: 1 | 2 | 3 | 4 | 5 | 6 | 7 | null,
    dates: string[],                 // только unit=dates: возрастающие уникальные даты
    ends: { type: 'never' | 'until' | 'count', until: string | null, count: integer | null }
  },
  series: null | {
    id: string,
    index: integer,                 // текущий экземпляр, начиная с 1
    anchorDate: 'YYYY-MM-DD',        // база серии, не пересчитывать от clamped февраля
    anchorDay: integer,
    anchorMonth: integer
  }
}
```

1. `due` остаётся верхнеуровневой совместимой датой ОКОНЧАНИЯ и вычисляется из `schedule.endDate`. `doDate` не переименовывать и не присваивать ему новое значение: сохранить прежнюю семантику. Не менять дневную модель срочности на минутную в этой задаче.
2. Новая задача без даты: `schedule` с null датами/временем, `allDay:true`, пустыми reminders, repeat/series=null, due=null. Legacy с одним due мигрирует в all-day startDate=endDate=due. Миграция при чтении — без массовой перезаписи хранилища; записать нормализованное состояние при следующем штатном изменении.
3. Если поле schedule отсутствует — применять legacy due. Если `schedule.version===1` и endDate корректна — она приоритетнее несовпадающего due, затем синхронизировать due. Если версия неизвестна — показать несовместимость и запретить редактирование этой задачи. Нужен read-result с защищённой исходной записью: изменение ДРУГОЙ задачи и save всего массива также обязаны сохранить неизвестную запись без потери полей (не прогонять её через lossy whitelist); такую запись не исполнять в scheduler. Если безопасный passthrough не реализован, блокировать запись всего массива с понятной ошибкой, а не терять данные. Если структура version=1 повреждена — безопасно восстановить дату из валидного legacy due, убрать только повреждённые опции, сохранить задачу/название и сообщить о восстановлении. Не превращать sanitizer в исключение, роняющее весь список.
4. Для корректного интервала нужны обе даты. При выборе одной даты в UI заполнить обе одинаково, при явном удалении срока убрать обе. All-day: обе time=null, последний день включительно; timed: обе time заданы и реальное окончание строго позже начала. Разрешены разные даты, не только один день.
5. Даты строго календарные с round-trip проверкой, время — строго 00:00–23:59, секунд нет. Запрещены 2026-02-30, 24:00, 9:5, NaN, нечисловые interval/offset и произвольные ключи. Числа не приводить из строк, кроме значений из контролов UI с явным parse/validation. Прототипы/пользовательский HTML не переносить в DOM.
6. Для timed при повреждённом времени из storage безопасно деградировать до all-day на корректных датах, а не удалять задачу; reminders, требующие времени, отключить с диагностикой. UI не использует такую деградацию вместо валидации: невалидная форма остаётся открытой и ничего не применяет.
7. `sanitizeTask` whitelist включает schedule и рекурсивно санитизирует его; `createTask` действительно передаёт его. Пронести schedule через `newDraft → applyDraftSchedule → submitDraft → addTask → createTask → sanitizeTask → saveTasks → loadTasks`. Не забыть `applyQuadrantMove`, `markDone`, restore/archive. Возвращать глубокие копии вложенных массивов/объектов; `matrixDebugState` тоже не должен давать изменять live draft.
8. Ограничения: reminders <=5; offsetMinutes от 0 до 525600; interval 1..999; ends.count 1..10000; dates 1..366 уникальных дат; ограничить длину id и валидировать набор enum. Для обычных единиц неприменимые поля нормализовать: weekdays/dates=[], nth/weekday=null, monthMode='dayOfMonth'. Для ends=never обе границы null; until требует until и count=null; count требует count и until=null. Для unit=dates interval=1, basis='scheduled'. Абсолютное reminder требует date/time и offset=0, относительное date=null. Все отсутствующие необязательные поля имеют эти же явные defaults. `repeat=null` влечёт series=null; series.index не может быть <1. Санитайзер идемпотентен на уже нормализованной задаче.
9. Даты и HH:mm — локальное «настенное» время устройства (`timeZoneMode:'device'`). При смене зоны встреча остаётся в тех же локальных часах; абсолютный UTC-момент не фиксируется. Даты без времени не пропускать через `new Date('YYYY-MM-DD')`/UTC stringify. В листе явно пояснить «Время устройства»; не обещать поддержку фиксированных зон и путешествий как в полном календарном сервисе.
10. Конвертер локального timed-момента должен проверять round-trip компонентов: несуществующие часы при DST запрещены в ручном вводе; неоднозначные осенние часы выбирают первое вхождение. Для вычисленного повторения в DST-gap сдвинуть к первому существующему моменту вперёд, показать нормализованное время и проверить end>start. Для all-day длительность считать календарными днями, не делением миллисекунд на 86400000. Выделить чистые `normalizeSchedule`, `validateSchedule`, `resolveLocalMoment`, `scheduleToDue`, `nextOccurrence` (точные сигнатуры задокументировать в модуле).

## Б4. Лист календаря — пошаговое поведение

1. Открытие: глубокая копия `getDraftSchedule()` в `calendarDraft`; основной task draft и storage не меняются до «Готово». Состояние activeEndpoint='start'|'end', monthCursor и ошибки принадлежат листу. Переключение месяца не уничтожает введённые часы/выбор повторов.
2. Шапка: «Закрыть», заголовок «Дата и длительность», «Готово». Сохранить месяц, дни недели, Сегодня/Завтра/Через неделю. Под ними две понятные строки-пилюли «Начать» и «Закончить» с датой и временем, затем «Весь день», «Время для напоминания», «Повтор». Отдельно выводить рассчитанную длительность (например, «1 ч 30 мин» / «3 дня»).
3. Нажатие «Начать» или «Закончить» выбирает, к какой границе относится календарь. При пустом интервале выбор дня устанавливает обе даты. При существующем интервале меняется только выбранная граница: неправильный порядок показать как ошибку, а не молча менять другую границу. Дни внутри диапазона мягко подсветить, начало/конец различить доступным текстом и состоянием, не одним цветом.
4. Быстрые даты при пустом интервале устанавливают один all-day день; при существующем переносят весь интервал так, чтобы начало стало выбранной датой, сохраняя календарную длину и часы. Перейти курсором к началу, не закрывать лист до «Готово».
5. «Весь день» — реальный checkbox/switch с label. Включён: поля часов скрыты/disabled, даты доступны, время в сохраняемом schedule=null. Выключен: если ранее в этой сессии вводили часы — восстановить; иначе 09:00–10:00, на выбранных датах, либо сегодня при отсутствии дат. До финального commit временно помнить часы в UI-state, не хранить скрытые старые часы в all-day модели. Если переключение создаёт end<=start, показать ошибку.
6. В timed режиме использовать доступные поля времени с шагом 1 минута и возможностью ручного ввода; «Закончить» включает собственную дату. Пример 23:30→00:15 того же дня — ошибка, пользователь явно выбирает следующий день; после выбора длительность 45 минут. Нельзя автоматически объявлять любое раннее время «завтра».
7. При отсутствии даты reminder/repeat недоступны с пояснением «Сначала выберите дату». «Очистить» готовит полный сброс дат, часов, reminders и repeat/series в calendarDraft; если зависимые настройки были — показать внутри листа, что они будут удалены. До «Готово» сброс отменяемый. Закрытие возвращает исходные настройки.
8. «Готово»: validate → inline ошибки с `aria-describedby`/`aria-live` → фокус первого неверного поля; при успехе единственный `applyDraftSchedule(copy)` и закрытие только календаря. В composer обновить плашку срока/длительности, индикаторы повтора и напоминания, а также вычисленный квадрант по Б6. Задача в localStorage пока не создана — это происходит при submit формы.
9. Крестик, backdrop, Escape: отбросить только calendarDraft, оставить весь исходный composer draft. Escape сначала закрывает вложенный выбор reminder/repeat, затем календарь, затем composer; обработчик приложения не должен обработать одно событие трижды.
10. Повторное открытие показывает ранее применённые значения. В календаре/подменю сохранять фокус, не пересоздавать весь composer на каждую минуту ввода. Для существующих задач добавить явное действие «Изменить дату и время» в detail/task actions (не делать чекбокс точкой редактирования). Такой режим использует копию задачи; финальный commit сохраняет только после успешной записи, cancel не меняет задачу, QuotaExceededError оставляет редактор открытым.

CSS: расширить `.matrix-sheet.is-date`, `.matrix-sheet-head`, `.matrix-cal-*`, `.matrix-chips`; новые `.matrix-schedule-fields`, `.matrix-schedule-row`, `.matrix-schedule-endpoint`, `.matrix-all-day`, `.matrix-reminder-row`, `.matrix-repeat-row`, `.matrix-schedule-error`, `.matrix-duration`. Поля с серой подложкой, панель белая, pill radius из токенов; 8/12/16 px отступы, текст контролов ввода >=16 px на phone против iOS zoom. Заголовок/«Готово» достижимы при прокрутке; высота с dvh и keyboard-offset. Поправить z-index после Воркера 1, не применять глобальный `.sheet { ... }` override. Премиум-замков и неработающих элементов нет.

## Б5. Напоминания — поля и реальная доставка

UI-меню: «Нет», «В момент начала», «За 5/10/15/30 минут», «За 1 час», «За 1 день», «В момент окончания», «Другое время». Разрешить до пяти, показывать выбранные строки и удаление каждой; дубликаты по фактическому правилу не создавать.
- Timed relative: anchor=start/end, offsetMinutes>=0, date/time=null; срабатывание = соответствующий локальный момент минус offset.
- All-day relative: anchor=start/end, offset только целыми днями (кратен 1440), time обязателен (по умолчанию 09:00), date=null. «В момент начала/окончания» означает в выбранное время первого/последнего дня; меню явно пишет это время. Минутные опережения в all-day не показывать.
- Absolute: anchor=absolute, date+time обязательны, offset=0. Не считать его повторяемым правилом для серии: при включении repeat потребовать заменить absolute на relative или явно удалить. Не молча переносить абсолютное напоминание в следующую неделю.
- Выбранное время напоминания в прошлом: показать предупреждение «Время уже прошло, уведомление сейчас отправлено не будет»; сохранить разрешено, немедленный спам запрещён.

Доставка: обязательное локальное in-app уведомление с заголовком задачи, временем и действием «Открыть»/«Закрыть», доступным живым регионом. Не перезаписывать напоминаниями тост ошибки сохранения; очередь отдельных уведомлений/небольшой центр с dismiss, без новой большой подсистемы. Системные Notification API не требуются: это осознанное ограничение, не запрашивать разрешение. Текст рядом с настройкой: «Напоминания работают, пока приложение открыто. В фоне могут задерживаться; при закрытом приложении не доставляются».

Scheduler в `js/core/matrix-reminders.js`:
1. Фабрика/контроллер с `start`, `refresh`, `dispose`, внедряемыми now/timers/visibility/load/display. На import — никаких таймеров, DOM или обращения к localStorage. Start идемпотентный, dispose снимает таймер и все listeners/подписки.
2. Инициализация в `js/app.js::init`, работа на любом разделе приложения, не только когда открыт экран Матрицы. Матрица сейчас не эмитит обычный data:changed: после успешного `commitTasks` эмитить отдельное `matrix:changed` через bus, не запускать ненужный cloud sync. Refresh на этом событии, storage для ключа Матрицы и visibilitychange/focus/pageshow; импорт/очистку/выход аккаунта обработать согласно фактическому lifecycle, без переноса локальных задач в облако.
3. Каждые <=30 сек при видимой странице проверять активные !done&&!archived задачи. При document.hidden не показывать уведомления; по возвращении доставить только пропуски не старше 5 минут, более старые пометить пропущенными без всплывающего спама. При первом холодном запуске старые времена не догонять; граница старта фиксируется контроллером. Pending reminder в последние пять минут, который пересечён в той же сессии во время hidden/suspend, догнать один раз. Новое правило, сохранённое уже в прошлом, не уведомлять.
4. Не использовать один многодневный setTimeout (переполнение/сон). Сверять реальные now, переживать скачок часов назад без дублей; изменение зоны пересчитывает floating-local trigger.
5. Ключ дедупликации: task id + series occurrence index (либо 1) + reminder id + нормализованный момент/отпечаток правила. Держать небольшой ledger в отдельном локальном ключе `youplanner.matrix.reminderLedger.v1` с ограничением размера/очисткой старых записей (например, 30 дней и <=2000). Не записывать ledger в общие задачи и не менять updatedAt ради каждого тика.
6. Запись ledger — через безопасное хранилище. При отказе память сессии всё равно блокирует повторный показ, дать одно ненавязчивое предупреждение, не запускать цикл ошибок каждые 30 секунд. Не обещать exactly-once между перезагрузками при недоступном storage. Несколько открытых вкладок: если Web Locks доступен — сериализовать повторную проверку ledger и запись; иначе явно документировать best-effort, без ложной гарантии межвкладочной доставки.
7. После выполнения/архивации/удаления/изменения времени отменить старый pending trigger. Повторная перерисовка не стартует новый scheduler. Никаких HTTP/push/Notification-вызовов и сетевого доступа для reminders.

## Б6. Квадрант и интервал — исключить тихую потерю дат

1. Квадрант — намерение только до ручного изменения расписания. На открытии нового composer из q1/q2/q3/q4 применить legacy `quadrantShape`, затем нормализовать schedule. Так исходное сохранение без редактирования даты попадает ровно туда, куда нажали «+».
2. После ручного изменения даты/приоритета показывать реальный `quadrantOf(draft)` и обновлять плашку. Если q2 со сроком сегодня становится q1, пояснить «Близкий срок: задача попадёт в „Срочно и важно“». Не вызывать принудительный `applyQuadrantMove` при submit второй раз поверх уже согласованного расписания. `addTask` различает явное начальное quadrant-intent и нормализованный calendar draft; контракт зафиксировать тестами.
3. Для legacy задач без нового интервала сохранить старую семантику shape/move (включая due=null в q2/q4): имеющиеся тесты продолжают проходить. Для нового расписания цель не срочно при уже далёком due должна СОХРАНЯТЬ далёкий интервал, а не безусловно стирать его.
4. Перенос назначенной timed/all-day задачи в конфликтующий квадрант требует preview и подтверждения изменения расписания: варианты «Изменить срок и перенести»/«Отмена». Перенос в срочный сдвигает интервал календарно так, чтобы endDate стал сегодня (q1) или завтра (q3), часы и календарная длина сохраняются. Перенос в не срочный при близком due предлагает endDate=today+3 дня с тем же интервалом. Никакого невидимого удаления дат или времени. После подтверждения фактический quadrantOf обязан совпасть с целью.
5. Если меняется только важность или due уже совместим, расписание/длительность/reminders не менять. Relative reminders следуют за интервалом; absolute при изменении интервала требует отдельного явного решения сохранить/удалить. Правило повтора и series anchor нельзя сбросить молча; перемещение повторяющегося задания требует уточнения в preview «Изменить дату текущего экземпляра; правило серии сохранится». Anchor всей серии при этом сохраняется; пользователь меняет правило отдельно в календаре.
6. Операции pure: подготовить candidate + список конфликтов, UI подтверждает, commit записывает. Не вызывать confirm/DOM из `quadrantShape`/data. В отличие от legacy addTask, конфликтный новый schedule не должен быть автоматически переформирован в data без согласия.

## Б7. Повтор — полноценная логика, а не текстовая плашка

Обязательные варианты: «Не повторять», каждый день, по будням, каждую неделю (с выбором нескольких дней), каждый месяц, каждый год, «Настроить» с интервалом N и единицей, «По выбранным датам». Monthly: по числу либо N-й/последний день недели месяца. Basis: «От даты задачи»/«От выполнения». Завершение: никогда, включительно до даты, после N выполнений. Нет премиум-плашек. Если комбинация не имеет однозначной семантики, явно отключить её с пояснением: completion-based допускается только для простого каждые N day/week/month/year без списка weekdays/nth/конкретных дат.

Правила расчёта:
1. Повторяется интервал целиком. Anchor — начало первого экземпляра, endDate/duration вычисляются с сохранением количества календарных дней и wall-clock часов. Relative reminders копируются, absolute запрещён для repeat. Изменение типа all-day не должно тайно менять правила серии.
2. Scheduled day: anchorDate + k*N календарных дней. Week: недели с понедельника относительно anchor, выбранные ISO weekdays по возрастанию, первая неделя только даты не раньше anchor. Month dayOfMonth: исходный anchorDay, если числа нет — последний день месяца; после февраля снова исходное число, а не закреплённое 28. Nth weekday: существующее N-е/последнее вхождение; отсутствующее пропустить. Year: anchorMonth/day, 29 февраля в невисокосный год → 28 февраля, следующий високосный снова 29. Все расчёты календарные.
3. Completion basis: очередное начало считается от локальной даты завершения + N единиц с прежними часами/длиной; если вычисленный timed start не позже completion, перейти к следующему допустимому периоду. Никакого цикла до бесконечности на неверном правиле.
4. Конкретные dates трактуются как даты начал, отсортированы/уникальны, следующее больше текущего. Нет будущей даты — серия заканчивается. При включении режима первый экземпляр должен входить в dates; UI предлагает включить текущую дату явно.
5. Until ограничивает дату НАЧАЛА следующего экземпляра включительно. Count включает текущий экземпляр (index=1); count=1 не порождает продолжение. Позднее завершение scheduled задачи создаёт следующий по расписанию экземпляр, даже если он уже просрочен, а не пропускает тайно историю. Автогенерации сотен пропущенных задач при запуске нет.
6. При выполнении одной операцией подготовить completed copy текущей задачи и ровно один следующий активный экземпляр. Сохранить весь массив ОДНИМ `saveTasks`/commit: отказ записи оставляет исходную задачу активной, не создаёт историю/следующую задачу и не гасит reminder. Completed copy сохраняет исходные даты, помечается done и occurrence identity; активный следующий имеет новую id, тот же series.id, index+1, ссылается на предыдущий occurrence. Детерминированно защитить создание одного и того же series.id+index от повторного click. В UI отправлять явное действие complete с ожидаемым исходным состоянием/id, а не два toggleDone подряд из устаревшего DOM: повторное complete уже выполненного экземпляра — no-op, не undo. Undo — отдельное намерение. Для следующего generatedAt присваивается тем же значением, что initial updatedAt; сравнение для Б7.8 должно быть однозначным.
7. Добавить в whitelist задачи связь `previousOccurrenceId: string|null` для следующего экземпляра. Для первого series.id создаётся при включении repeat, не при каждом render/sanitize. ID экземпляра стабилен после сохранения. В истории завершённый экземпляр хранит правило для отображения, но scheduler игнорирует done.
8. «Вернуть в работу» для последнего завершённого экземпляра серии: если сгенерированный следующий ещё существует, не выполнен и не редактировался после генерации — атомарно убрать его и вернуть текущий. Для проверки сохранять `generatedAt` и проверять updatedAt у следующего (whitelist). Если следующий уже изменён/завершён, предложить явное «Восстановить как отдельную задачу без повтора»/«Отмена», не создавать две активные ветви серии. Архивирование текущего активного экземпляра приостанавливает серию, не порождает следующий; удаление тоже не завершение.
9. При редактировании repeat активной задачи применять правило к ней и будущим, не переписывать выполненную историю. Если правило изменено — новая series.id/index=1/anchor, показать текст «Правило изменится для текущей и следующих задач»; снятие repeat обнуляет series. Простое изменение заголовка/заметки series не перезапускает.
10. Вычисление следующего экземпляра имеет ограниченный поиск (до 100 лет вперёд/1200 месяцев), возвращает диагностируемый результат 'none'/'invalid', а не вечный while. Показать окончание серии в UI; нельзя молча оставить «Повторяется» без будущего экземпляра.

## Б8. Обязательная матрица TDD (с конкретными ожиданиями)

Для каждого пункта сначала RED на отсутствующем поведении, затем GREEN. Не подменять запись/валидацию расчётами в самих тестах, совпадающими построчно с реализацией. Использовать фиксированные даты и независимые ожидаемые значения.

### Данные и даты
- Legacy `{due:'2026-11-04'}` → all-day 04.11–04.11, due не сдвинут, priority/doDate/notes сохранены. Legacy без due → null dates. Две нормализации подряд дают одинаковый результат.
- `createTask` с 04.11 09:00–10:30 → save/load → все schedule-поля/напоминания/repeat равны исходному нормализованному значению, due='2026-11-04'. Unknown keys отброшены, вложенные ссылки не разделяются.
- 04.11 23:30 → 05.11 00:15 = 45 мин; 04.11 23:30 → 04.11 00:15 отклонено; одинаковые timed границы отклонены. All-day 04.11–06.11 = 3 дня; один день допустим.
- Ошибки: 2026-02-30, 2026-13-01, 24:00, 9:5, end<start, time без даты, невалидные enum, Infinity/NaN, interval=0/-1/1000, count=0, until раньше начала, слишком много reminders/dates.
- DST: Europe/Berlin 29.03.2026 02:30 не существует — ручной ввод отклонён; 25.10.2026 02:30 неоднозначно — выбран первый момент. Проверки выполнять в отдельном Node-процессе с env.TZ через тестовый launcher (не Windows `TZ=... node`). Для обычных дат прогнать UTC и положительный/отрицательный offset; all-day не сдвигается.
- Timed→all-day сохраняет даты, убирает times из storage; обратное переключение внутри листа восстанавливает часы; после сохранения all-day и нового открытия используются дефолты 09:00–10:00.
- Повреждённый schedule не удаляет годную legacy-задачу. Неизвестная версия не перезаписывается текущим sanitize/save. Отдельно проверить диагностируемое поведение, не только отсутствие exception.

### Транзакция листа и квадрант
- Календарь → изменить дату/время/повтор → cancel/Escape/backdrop → исходный schedule draft неизменен; storage не писался.
- «Готово» валидного календаря меняет только composer draft; submit сохраняет задачу один раз. Валидационная ошибка держит лист открытым, фокус/inline error у поля.
- Очистить → cancel не удаляет настройки; очистить → готово очищает due, часы, reminders, repeat/series.
- q2 плюс + дата сегодня → плашка q1 и сохранение в q1 без переписывания даты; q3/q4 стартовые priority корректны; date edit с далёким due не теряется при submit.
- Move timed 10.11 09:00–11.11 10:00 в q1 при today=04.11 → preview окончания 04.11 и начала 03.11, часы сохранены; cancel оставляет исходное. В q2 близкий интервал → end 07.11, длина сохранена. Far due в q2 не стирается.
- QuotaExceededError сохраняет весь schedule/title/notes в открытой форме; задача и очередь reminders не изменены. Дата существующей задачи редактируется с тем же rollback.

### Повтор
- Daily 04.11 → 05.11 с прежними часами/длиной; каждые 2 дня → 06.11.
- Weekly Пн/Ср/Пт: Ср 04.11.2026 → Пт 06.11 → Пн 09.11; N=2 недели соблюдает anchor-неделю, не просто +14 дней для каждого weekday.
- Month с anchor 31.01.2027 → 28.02 → 31.03; последний понедельник ноября 2026 → последний понедельник декабря; leap-year 29.02.2028 → 28.02.2029 → ... →29.02.2032.
- Completion daily при завершении 10.11 задачи от 04.11 →11.11; scheduled той же задачи →05.11 (просроченный следующий), это разные режимы.
- Count=1/2, until inclusive/exclusive, конечные dates, отключение repeat; wrong combos отключены и не проходят validator.
- Выполнение → completed+next одним storage write; двойной click не создаёт два next; fail write откатывает всё; архив не генерирует next; undo последнего untouched next сворачивает генерацию; изменённый next требует отдельного восстановления без repeat.
- Relative reminders следуют за next; absolute несовместим с repeat и вызывает явную ошибку/предложение, не молчаливый сброс.

### Локальные напоминания
- Start 10:00, offset15 →09:45; end10:30, offset0 →10:30; all-day 04.11 offset1440/time09:00 →03.11 09:00. Absolute дата/время работает отдельно.
- До trigger нет уведомления, после пересечения одно, повторный tick/refresh/render/reload с ledger не дублирует; изменение reminder создаёт новый fingerprint.
- Запуск приложения после старого trigger и сохранение правила в прошлом не показывают всплытие. Hidden в той же сессии 2 мин → одно догоняющее; 10 мин → помечено missed без спама.
- Done/archive/delete/изменение даты до trigger отменяет старый показ. Ошибка commit не отменяет настоящее pending напоминание.
- start дважды не размножает таймер; dispose убирает listeners/subscriptions/timer; import не создаёт активных handles. Без Notification API и без сети поведение работает.
- Ledger quota failure → одно уведомление на сессию без бесконечных ошибок; ограничение/очистка ledger; Web Locks path при наличии и best-effort path без него проверяются раздельно.

# 3. Финальный отчёт обоих воркеров и Definition of Done

В отчёте указать: изменённые файлы/символы; решения/отступления с причинами; конкретный RED-тест до кода; итоговые команды с exit code и количеством tests; viewport/screenshots и пройденные действия; что failed/not run и почему; ограничения локальности и фоновой доставки. Не выдавать исторические 400/400 за результат новых изменений.

Готово только если: четыре больших квадранта и четыре правильных листа; явные Выполненные/Архив/Перенос; валидируемый сохраняемый интервал; рабочие повторы с атомарной генерацией; локальные reminders при открытом приложении; rollback без потери черновика; runtime-модули в PWA-кэше; node и browser-проверки нового состояния. Сохранённые поля, которые нигде не используются, не считаются работающей функцией.

Не входят в эту поставку: облачная синхронизация/backup Матрицы, server push, гарантированная доставка в фоне, фиксированные международные часовые зоны, полная копия всех платформенных и тарифных функций TickTick. Эти границы не скрывать в UI и отчёте.
