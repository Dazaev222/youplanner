# Привязка YouPlanner к UID владельца — пошаговая инструкция

Дата: 2026-11-04. Реализация: `js/data/firebase-auth.js` (режим постоянного
аккаунта), `database.rules.json` (шаблон с пином), `_tools/set-owner-uid.mjs`
(сборка правил), Настройки → «Аккаунт владельца» (вход), `tests/e2e/
firebase-rules.e2e.mjs` (живая проверка). Тесты: `npm test` → 398/398.

## 0. Что изменилось и зачем

Правила вида `auth != null` пропускают **любую** сессию этого Firebase-проекта,
а анонимный uid Firebase выдаёт отдельный для каждого устройства. Значит, чтобы
база принадлежала одному человеку, все его устройства должны ходить под одним
**постоянным** аккаунтом (email + пароль), а правила должны сравнивать
`auth.uid` с его uid.

Ключевое следствие, из-за которого порядок шагов строгий:

> Правила с пином отсекают устройства, которые ещё живут анонимно.
> **Сначала вход на всех устройствах, потом публикация правил.**
> Обратный порядок выглядит как «синхронизация пропала», хотя данные целы.

До входа и после отказа по правам приложение работает локально — ничего не
теряется; в Настройках показывается код отказа (401/403), а не «нет связи».

## 1. Где взять UID

Три способа, любой:

1. **Firebase Console → Authentication → Users** → колонка `UID` у нужного
   аккаунта (28 символов, буквы и цифры).
2. **В самом приложении**: Настройки → «Аккаунт владельца» → войти — строка
   покажет `UID: …` отдельной линией, чтобы его было удобно выделить мышью.
   Этот способ точнее всего: вы видите ровно тот uid, под которым ходит
   приложение.
3. **Пробегом e2e** (шаг 6 ниже): он печётает `PASS пин в правилах — <uid>` и
   сверяет его с `localId` аккаунта.

Сам uid — не пароль, но в публичном репозитории ему не место: это идентификатор
вашего аккаунта. Поэтому `database.rules.json` остаётся с заглушкой
`OWNER_UID`, а живой uid попадает только в `database.rules.local.json`
(в `.gitignore`).

## 2. Создать аккаунт владельца (Console, 1 минута)

1. Firebase Console → ваш проект `youplanner-d8aaea12…` → **Authentication** →
   **Sign-in method** → включить **Email/Password** (Anonymous оставить
   включённым: он нужен устройствам до входа и не мешает правилам).
2. **Authentication → Users → Add user** → email + пароль (≥ 8 символов,
   сгенерированный менеджером паролей). Это и есть будущий `auth.uid`.
3. Письмо-подтверждение не нужно: для REST-входа достаточно email+пароль.

## 3. Собрать правила локально

```bash
cd "C:/Users/Admin/Desktop/проекты/youplanner-new"

node _tools/set-owner-uid.mjs --uid <ВАШ_UID>
node _tools/set-owner-uid.mjs --check
npm test
```

`--check` печатает `ok: … — uid <ВАШ_UID> в 4 разрешениях` и обязан найти пин
в **каждом** разрешении: `.read` и `.write` на узле данных и на узле копий.
Скрипт в сеть не ходит вообще — ничего не публикует.

Если `--check` ругается «без пина на uid» — шаблон правил испорчен, чините
`database.rules.json`, а не собранный файл.

## 4. Проверить правила, не публикуя (Rules Playground)

Console → Realtime Database → **Rules** → вставьте содержимое
`database.rules.local.json` (кнопка **Publish НЕ нажимать**) → справа **Rules
debugger**:

| Что ввести | Ожидаемый ответ |
|---|---|
| Location `/youplanner-d8aaea12-…/.json`, Read, **без** аутентификации | `false` (deny) |
| Read, authenticated: `{"uid":"<ВАШ_UID>","token":{}}` | `true` |
| Read, authenticated: `{"uid":"любой_другой_uid","token":{}}` | `false` |
| Location `/youplanner-d8aaea12-…-backups/.json`, Read, ваш uid | `true` |

Эмулятор Firebase CLI (`firebase emulators`) в этом окружении недоступен — нет
Java, — поэтому Playground и есть «проверить локально».

## 5. Войти на всех устройствах (до публикации!)

На каждом устройстве, где вы пользуетесь YouPlanner:

**Настройки → Аккаунт владельца → email + пароль → «Войти»**.

Что происходит: `accounts:signInWithPassword` заменяет анонимный refresh-токен
устройства токеном постоянного аккаунта; в localStorage пишутся
`youplanner.fb.refresh` и `youplanner.fb.owner` (`{email, uid}`); пароль не
хранится нигде. С этого момента молчаливый анонимный signUp запрещён: если
сессия потеряна, приложение покажет «нужен вход», а не заведёт лишний аккаунт.

Признак готовности: строка Настроек показывает `Владелец: <email>` и `UID: …`,
совпадающий с тем, что подставлен в правила.

## 6. Опубликовать правила

Console → Realtime Database → Rules → вставить `database.rules.local.json` →
**Publish** — и **отдельно** для второго инстанса (узел копий живёт в том же
инстансе, но проверять надо оба пути):

- `/youplanner-d8aaea12-60e6-4ac9-973c-46c19b387cd9`
- `/youplanner-d8aaea12-60e6-4ac9-973c-46c19b387cd9-backups`

Затем живая проверка (она пишет только служебный `__rules_probe` и тут же
удаляет):

```bash
YP_OWNER_EMAIL='ваш@email' YP_OWNER_PASSWORD='пароль' \
  node tests/e2e/firebase-rules.e2e.mjs
```

Пароли — только из окружения конкретного запуска; в файл, скрипт или коммит они
не попадают. Ожидаемые строки:

```
PASS главный: PUT без auth отвергнут
PASS бэкапы: GET без auth отвергнут
PASS главный: анонимная сессия отвергнута   ← смысл закрепления по uid
PASS пин в правилах — <uid> в 4 разрешениях
PASS uid владельца — <тот же uid>
PASS главный: владелец пишет
PASS бэкапы: владелец читает
```

`FAIL главный: анонимная сессия принята` = правила ещё вида `auth != null`
(не опубликовали или опубликовали не тот файл). `FAIL uid владельца` =
правила закреплены за другим аккаунтом: синхронизации не будет, пока не
совпадёте.

## 7. Проверить в приложении

Открыть Настройки → «Отправить на сервер» → «Обновить с сервера». Успех =
`Отправлено` / `Обновлено`. Если вместо этого «Доступ запрещён (403): нужен
вход владельца» — на этом устройстве анонимная сессия (шаг 5 пропущен) или
опубликованы правила с другим uid.

## 8. Откат

Любой из, по возрастанию радикальности:

1. Console → Realtime Database → Rules → история версий → восстановить
   предыдущую (публикуется кнопкой Publish).
2. Временно вернуть `"auth != null"` — база снова открыта любой сессии этого
   проекта, данные не теряются, синхронизация работает как раньше.
3. Настройки → «Выйти» — устройство возвращается в анонимный режим (его
   refresh-токен стирается). Пока правила закреплены за uid, этот режим
   локальный: синхронизации не будет, пока не войдёте снова.

## 9. Чего здесь сознательно нет

- **Пина на `auth.uid` конкретного устройства** — он отрезал бы остальные
  устройства того же владельца (у анонимного uid он уникален на каждое).
- **Custom-токена с claim `owner`** — требует сервера, который подписывает
  токены; в этом проекте сервера нет (в отличие от telegram-bridge, где
  Mini App-права ровно так и устроены).
- **Публикации правил из кода/CI** — PUT в `/.settings/rules.json` не
  выполняется; это руками в Console.
- Закрепление по uid — **сужение области поражения**, а не «защита от всех»:
  имя узла и Web API Key лежат в клиентском бандле, любой человек может
  прочитать их и зарегистрировать анонимную сессию того же проекта. От этого
  они теперь отрезаны правилом; от чтения структуры дампа — нет.
