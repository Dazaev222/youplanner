## 3. Архитектурные проблемы — СТОП-КРАН (требуют вашего решения, НЕ чинил)

### YouPlanner

1. **Транзакционность применения снимка** (`js/sync/sync.js: applyCloudData`): сырой `localStorage.setItem` без квота-гварда — QuotaExceeded посреди снимка = частично применённые разделы, `SYNC_TS_KEY` не сдвигается (следующая сверка re-apply тот же снимок). Нужна политика транзакционности.
2. **Частичный импорт бэкапа** (`js/data/backup.js: applyBackup`): та же проблема при импорте файла + `data:replaced` не эмитится, отката нет (habits/records уже перезаписаны).
3. **Гонка бэкапов двух устройств** (`js/sync/sync.js: backupCloudSnapshot`): read-modify-write списка бэкапов без блокировки — два одновременных устройства теряют элементы истории (single-flight работает только внутри вкладки). Нужно серверное решение (push/append-узел).
4. **Публичный Firebase-узел без аутентификации** (`js/data/sync.js`): писать/стирать на сервере может кто угодно; локальные данные защищены валидаторами, серверные — нет. Нужны правила доступа RTDB.
5. **Неограниченный рост историй** (sleep/fast/qazaLog): дизайн «история на годы» задокументирован, но квота localStorage конечна — политика чистки на ваше решение.
6. **Производительность**: карточка привычки = ~1500 вызовов `calcProgress` при периоде «Всё время» (по одному на день); `saveSleep` перечитывает и перезаписывает всю историю на каждый input; `sync:applied` перерисовывает всё безусловно. Всё локально фиксуемо, но трогает горячие пути — делал бы по одному с тестами, ночью не стал.

### Telegram Bridge

7. **Гонка whisper-адаптера после таймаута STT** (`core/stt/service.py`): `_run_timed` бросает поток-демон, следующий голосовой запрос переиспользует синглтон-адаптер — «брошенный» поток может ещё крутиться в `model.transcribe` (faster-whisper не документирован как потокобезопасный). Варианты: лок на транскрипцию или флаг занятости.
8. **Блокирующие sends в главном цикле** (`bot/pipeline.py:191-234`): `/help`, `/status`, `/cancel`, отказ busy шлются синхронно в единственном потоке-потребителе апдейтов; при сетевых проблемах (429 retry до 60 с × 3) callback'и не разбираются. Фикс — отправка через dispatcher с низким приоритетом. Бот живой, ночью менять поведение не стал.
9. **Промпт в argv** у ZCode/Qoder-провайдеров (виден в списке процессов) — для однопользовательской локальной машины осознанно, менять по согласованию.

## 4. План фичи Vision (анализ изображений в ассистенте) — только план, кода нет

### 4.1 Текущая архитектура (проверено по коду)

- Запрос: `requestAssistantReply()` (`js/ui/assistant-view.js:657-713`) → POST `https://api.neuraldeep.ru/v1/chat/completions`, payload `{ model, messages }`, где `messages = [{role:'system', content}, ...история 20 реплик]` — всё текстовое.
- Прецедент вложения уже есть: **PDF** живёт в модульной переменной `pdfContext` (не в localStorage, не в истории), прикрепляется к каждому запросу, пока не убран; индикатор-чип с кнопкой-сбросом; тосты о статусе. Vision должен повторить этот паттерн.
- **Сжатие уже реализовано**: `compressBgImage(file)` (`js/data/background.js:96-130`) — `createImageBitmap` с EXIF-фиксом, масштаб по `targetSide()`, лестница WebP→JPEG по качеству до потолка 800 КБ (`BG_BLOB_MAX`). Переиспользуемо почти целиком, но параметры фоновые (до 2048px/800КБ) — для чата нужны свои.
- Модели: в `ASSISTANT_MODELS` уже есть `qwen3.8-27b` с пометкой «зрение» (`assistant-view.js:26`). Ваш Qwen 3.6 Vision — сверить фактический id по каталогу NeuralDeep (llms.txt) перед реализацией; план от id не зависит.
- История: `readHistory()` требует `content` строкой — мультимодальные сообщения (content-массив) в историю не попадут без расширения валидации.

### 4.2 Пошаговый план

**Фаза 0 — рефакторинг без поведения (~30 мин)**
1. Извлечь generic-функцию сжатия из `compressBgImage`: `compressImage(file, { maxSide, maxBytes, ladder })` в `js/data/background.js` (или новый `js/data/image.js`). `compressBgImage` становится тонкой обёрткой со своими параметрами. Тесты зелёные — поведение фона не меняется. Это единственный рефакторинг, всё остальное — добавления.

**Фаза 1 — сжатие для чата**
2. Параметры чата: `maxSide ≈ 1568` (рабочий диапазон vision-энкодеров Qwen), потолок `≈ 400 КБ` на картинку (base64 раздует в ~1.37× → ~550 КБ в payload — приемлемо при контексте 256k). EXIF-поворот уже решён `createImageBitmap('from-image')`.

**Фаза 2 — состояние и UI**
3. Модульная переменная `imageContext = null | [{ dataUrl, name, bytes }]` (по образцу `pdfContext`, до 3 картинок). Не в localStorage, не в историю — перезагрузка сбрасывает.
4. UI: вторая кнопка-скрепка «📷» рядом с PDF-креплением (`#assistant-image-input`, `#assistant-image-indicator` — чип «✕ фото.jpg · 380 КБ» по образцу PDF-индикатора). Повторный выбор заменяет/добавляет, клик по чипу убирает. Во время сжатия — «Сжимаю…» (сжатие быстрое, но честный статус нужен).
5. Гейтинг по модели: добавить флаг `vision: true` в `ASSISTANT_MODELS` (сейчас `qwen3.8-27b`). Если приложено фото, а модель без зрения — тост «Текущая модель не принимает изображения — переключись на qwen3.8-27b» (или авто-подсказка с переключением в модалке модели). Запрос при этом НЕ отправлять — иначе API вернёт непонятную ошибку.

**Фаза 3 — payload и промпт**
6. Формат OpenAI-vision: в ПОСЛЕДНЕЕ user-сообщение (текущий вопрос) `content` становится массивом: `[{type:'text', text: вопрос}, {type:'image_url', image_url:{url: 'data:image/jpeg;base64,…'}}, …]`. Системный промпт дополняется строкой «Пользователь приложил N изображение(ий) — опирайся на них» (по образцу PDF-обёртки в `buildMessages`).
7. `buildMessages()` остаётся синхронным: dataURL готов на этапе выбора файла, `imageContext` только подставляется.
8. Картинка прикрепляется к КАЖДОМУ запросу, пока не убрана вручную (семантика PDF — уточняющие вопросы видят фото). История: пушится только текст вопроса; при желании — маркер `[фото: имя]` для читаемости ленты. `readHistory()` не меняется.

**Фаза 4 — ответы, ошибки, тесты**
9. Ответ обрабатывается как сейчас (content строка). Специфические ошибки API (модель без зрения, картинка слишком большая) — замапить в `friendlyError` человеческим текстом.
10. Тесты: чистые части — структура vision-сообщения (extract-функция, принимающая текст+dataURL → объект сообщения), гейтинг по модели, лимит 3 картинок. Сжатие (canvas) в node-песочнице не тестируется — покрыть скретч-E2E по образцу `.scratch/pdf-test`: фейковый API-роут (page.route), проверка формы payload (image_url присутствует, размер в бюджете), ответ рендерится.
11. Документация: README «Работает» + status.md запись; в sw.js ничего (новых vendor-файлов нет, кэш поднять при выкладке).
